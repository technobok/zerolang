Open design questions -- ideas that have been considered but are not yet decided or implemented. None of them describe shipped behaviour; they are kept so the thinking isn't lost. For the language as it currently exists, see the specification and the ownership model.

1. enum

Enums today are unions or variants whose subtypes carry no data (see the case example in examples/). Value-carrying tags SHIPPED: a data block drives the tag type and per-arm constant values (as { tag: mydata_key.tag }), with collision/overflow errors -- see the spec's Enumerated Types notes. What stays open here is only the per-arm default-value idea below (arm defaults spelled inline on the variant).

How do we differentiate between a static value usable as the tag and a default value for the constructor of that subtype? One option is to drive the tag type from a data block (which can have named members):

t: data { FIRST: 1 SECOND: 2 THIRD: 3 }

myenum: variant {
  FIRST: null
  SECOND: null
  THIRD: null
} as {
  tag: t.tag
}
MyEnum1: union { FIRST: none SECOND: none THIRD: none }

myenum2: variant {
  FIRST: null
  SECOND: null
  THIRD: null
}

# each of these would have a constructor that defaults to 1, 2 or 3
# but you could pass in a different value. The descriminator would always
# be 0, 1, 2
myenum3: variant {
  FIRST: 1
  SECOND: 2
  THIRD: 3
}

2. compile-time numeric constant types

A richer compile-time constant-type lattice than the one currently shipping (the language models integer and float literals with ONE type each, intliteral and floatliteral -- declared types since the literal-type arc, but still one per kind rather than one per value). At unit level:

x: 4

would be equivalent to:

x: cast 4 as 4

so x is specifically of type '4' but also an 'i64'. The const types would live at a synthetic namespace, eg. system.const.i64_4.

Each type has different methods for 'call' which determines their default runtime type, and other conversion methods provided this constant can losslessly be converted to those types. Some rules:

  • default numeric type is i64 for all integer constants that can be stored in an i64. Larger numbers have no 'call' method and must be explicitly converted to a runtime type.
  • default numeric type is f64 for all float constants that can be stored in an f64. Larger numbers have no 'call' method and must be explicitly converted to a runtime type.
  • negative constants have no 'u' methods (eg 'u64') since negative numbers cannot be converted to an unsigned type

The constant types:

  • cip8 - constant positive int that can fit in 8 bits (supported methods: u8 u16 i16 u32 i32 u64 i64 u128 i128 c8 c32) - note, not i8 because it may not fit. Default (result of 'call') is i64.
  • cin8 - constant negative int that can fit in 8 bits (supported methods: i8 i16 i32 i64 i128). Default (retult of 'call') is i64.
  • cip16 - supports methods as for cip8 but NOT u8, i8, c8
  • cin16 - supports methods as for cin8 but NOT i8
  • cip32
  • cin32
  • cip64
  • cin64
  • cip128 - no default (result of call method)
  • cin128 - no default (result of call method)
  • cf16 - constant float that can fit in a f16
  • cf32 - constant float that can fit in a f32
  • cf64 - constant float that can fit in a f64
  • cf128 - constant float that can fit in a f128
  • cc8 - constant character that can fit in 8 bits, always positive (supported methods: u8 u16 i16 u32 i32 u64 i64 u128 i128 c8 c32) - note, not i8 because it may not fit. Default (result of 'call') is c8
  • cc16 - constant character that can fit in 8 bits, always positive (supported methods: u8 i8 u16 i16 u32 i32 u64 i64 u128 i128 c8 c32). Default (result of 'call') is c32

3. arbitrary-precision constant arithmetic

The section above asks what TYPE a constant has. This asks what VALUE the compiler can hold while it works one out, which is a separate question with a separate answer -- and the one that blocks the other, because a per-value type lattice cannot name a value the evaluator cannot carry.

What is true today, measured rather than assumed:

  • the compile-time value of an integer constant is an i64 -- one signed slot on cval -- so a magnitude above 2^63-1 has nowhere to live. The evaluator answers "not a constant" for it, and a definition that yields no value is not one: it takes the ALIAS chase instead and is emitted as the name of its own type. k: 18446744073709551615 emits i64 into the C.
  • the limit is already admitted in a user-facing message -- the constant integer operation overflows hint reads "the compile-time evaluator works in i64; this result does not fit" -- but it does not always fire: 9223372036854775807 + 1 folds to -9223372036854775808 silently.
  • i128 and u128 are real numeric types whose literals cannot express their own range. 340282366920938463463374607431768211455.u128 evaluates to 18446744073709551615 -- truncated to u64 -- with no diagnostic.
  • examples/arbprec_constants.z states that constant arithmetic folds at unbounded precision. It does not: 0xffffffffffffffff + 1 - 1 is not folded at all, it survives as C arithmetic text and agrees only because unsigned C wraps. Bound to a local it prints -1. The example passes because the value is never observed.

Widening the slot is not the answer. i128 would move the wall rather than remove it, and the wall has to be somewhere a constant expression can reach: an intermediate legitimately exceeds every concrete type when the final value does not, which is the ergonomic the coercion rules already promise.

where the digits would live

cval is a valtype on purpose -- it copies out of a stamp table instead of handing back a borrow, so a memoised evaluator can read one entry of a table it is about to write, and a class would make every read hold a lock on the map. So the digits cannot sit inside it.

The mechanism for exactly this already exists and is used by the one payload that already does not fit a scalar slot. A constant string is not stored in the cval; it is INTERNED, and the cval carries strId, a 1-based index into ZTyping.constStrings with the sentinel at row 0. An arbitrary-precision integer would be the same shape -- a bigId into a ZTyping.constBigInts -- which keeps the valtype, keeps the id-keyed table, and stays SQL-dumpable.

what would have to be built

There is no bignum in lib/ or src/, so the arithmetic itself is the cost, and it is the part to decide before anything else:

  • a full arbitrary-precision integer in the stdlib, which the compiler then uses like any other user. The stdlib is not special, so a BigInt that is good enough for the evaluator is good enough to ship -- and a compiler that is its own first user is how every other stdlib type here got tested.
  • a fixed WIDE accumulator (256 or 512 bits) private to the evaluator. Not arbitrary, but it covers every concrete type the language has with room for intermediates, and it is bounded work with no allocation. It moves the wall far enough that nothing realistic reaches it -- while still being a wall, which is the thing this section exists to stop doing.
  • digits held as TEXT and re-read at each use. Rejected: re-deriving a value from its spelling is the shape this compiler keeps removing, and it would put a parse on every constant read.

Whichever is chosen, the range check moves to ONE place -- the coercion boundary, where a value meets a concrete type -- and the evaluator stops having a range of its own. That is what makes constant integer operation overflows a message about the DESTINATION rather than about the compiler.

4. single create constructor for unions

Could a union have a single create constructor that takes one argument of any valid subtype? It would match the first subtype whose type matches the argument. Would fail at compile time if more than one subtype matches the argument type (ambiguous). This would be in addition to the per-subtype constructors (MyUnion.subtype expr).

Result: union { ok: i64  err: String  none: null }

# per-subtype constructor (current)
a: Result.ok 42

# single 'create' constructor (proposed)
b: Result.create 42       # matches ok (i64)
c: Result.create "hello"  # matches err (string)
# Result.create ???       # how to construct none?

Open questions: how to handle null subtypes (no argument)? How to handle generic subtypes where the type may not be known? Is the convenience worth the potential ambiguity?

5. meta namespace

meta.create is the only part of this implemented today -- the canonical constructor for every object type (the one raw allocator; user constructors route through it). The remaining meta.* surfaces below are open proposals, none implemented.

'meta' is a special, dynamic namespace provided by the compiler at compile-time only. All items are readonly (?)

meta can sort-of be used to add additional keywords

  • meta.create - the one true constructor for the current object (since, '.create' is automatically used (see Sugar), can also just call meta ...)

meta.function: current function. Error if not in a function

  • meta.function.name - short name (label)
  • meta.function.path - fully qualified name (dotted)
  • meta.function.reference - the function itself (pointer)... can be used for recursive calls without using the name?
  • meta.function.parent - link to containing object (same as meta.object)

meta.object: containing object (class/record...). Error if not in an object definition.

  • meta.object.name - short name (label)
  • meta.object.path - fully qualified name (dotted)
  • meta.object.reference - the object itself, can be used for self referential structures without using the parent's name
  • meta.object.parent - link to containing unit (same as meta.unit)

meta.unit: details about the current unit

  • meta.unit.name - short name (label)
  • meta.unit.path - fully qualified name (dotted)
  • meta.unit.reference - the object itself, can be used to refer to the current unit without using its name
  • meta.unit.parent - link to containing unit (compilation error if there is no parent unit (at top level))

meta.definition: details about a named definition ('name' - can be a name within the current scope or a fully qualified varname, it is no withing parens and the name is NOT evaluated).

  • meta.definition name - the root of the meta namespace for 'name'.
  • (meta.definition name).name - short name (label)
  • (meta.definition name).path - fully qualified name (dotted)
  • (meta.definition name).reference - this name's definition (why would you ever use this?)
  • (meta.definition name).parent - parent container of this name? (function/object/unit)
  • (meta.definition name).type - type of this name (as a fully qualified string?)

meta.source: details about the current source file

  • meta.source.name - current filename
  • meta.source.path - current filename full path
  • meta.source.line - current linenumber

meta.define: compiler 'definitions' (like c compiler defines/command line -D values)

  • meta.define NAME - return the string value of the definition NAME. The definitions can be passed in on the command line invocation of the compiler (-D name=value)

meta.environment: access to environment variables (should this be done? Or just use defines?)

  • meta.environment 'NAME' - return the string value of the environment variable NAME. The name provided is a string because environment variable names may be very flexible.

meta.compiler: details about the compiler and language

  • meta.compiler.name - name of the compiler
  • meta.compiler.version - version of the compiler
  • meta.compiler.commandline - the commandline passed to the compiler?

meta.language: - details about the language being compiled

  • meta.language.name - name of the language being compiled ('ZeroLang' ?)
  • meta.language.version - version being compiled by the compiler

meta.error: force a compile time error?

6. finalizers, or user-named destructors?

Moved out of spec.pdoc, where it sat as a section describing one model with a TODO at the top saying the other was intended. Neither is implemented as a surface feature: the compiler generates and calls a destructor for any type whose fields need cleaning up, and nothing in the language names it.

The undecided questions, as they stood:

  • One compiler-called finalize, or a user-named destructor? A finalize must be a method taking no arguments; a user-named one can be called explicitly, which raises the next question.
  • May valtypes have one? They are copy-by-value, so a finalizer would run on every copy. Warn and allow, or refuse?
  • May it be private? Good style says yes, and the compiler would still call it at scope exit.
  • May it return a subcomponent of this, handing ownership to the caller? The earlier draft allowed exactly that.
  • During destruction this may be in an inconsistent state, so no method may be called on it and only its subcomponents may be written. How is "not left broken part way through" checked, if at all?

The return-a-subcomponent form the earlier draft described:

MyRefType: class {
    destroy: function {s: this.take} out subreftype is {
        s.subreftype
    }
}

8. deep copy for user-defined reftypes

.copy is implemented for strings, containers, and generic type parameters (where each instantiation clones its concrete payload). On a user-defined class or union it is a compile-time error (E0100): the emitter has no recursive clone generation, and before the error landed the miss produced silently-invalid C.

Implementing it would mirror the auto-destructor machinery -- a per-type _copy walking fields and union payloads, boxing heap members -- and needs decisions on cycles (reject? runtime trap?) and on whether protocol-typed fields can be cloned at all (the vtable knows destroy but not copy today). Until then the idioms are .take for transfer and field-by-field construction for real duplication; the json unit's scalar-only accessors are an example of designing around the gap.

9. bare Option/Result names as their falsy arms

The zero-value rule (spec: Implicit Construction, Zero Values) gives bare type names in runtime value position a zero-argument construction. Unions deliberately stay excluded: a bare (Option u64) could plausibly construct .none -- the falsy arm is tag zero by layout convention, so the zero struct already reads as none -- and the symmetry with numerics/String is attractive. Against it: an Option default hides a meaningful choice at exactly the places the falsy-first design wants it explicit, Result has no payload-less falsy arm (err carries a value) so the rule could never be uniform across tagged sums, and the targeted "select an arm" error currently teaches the arm-construction form. Open: whether payload-less-falsy-arm unions (Option-shaped) should default at all, and if so whether only in binding position. Until decided, every union/variant keeps the arm-selection error.

10. reference yields from generators

A generator's call is declared out T and the lowering wraps T in an Option; a .borrow or .view leaf on that type (call: function out Bag.borrow is { yield this.bag }) is refused today ("a generator cannot yield a reference"). The typecheck collapse maps every reftype element to an owned Option, so the reference leaf was accepted and ignored, and the emitter then moved the yielded field out of the generator as if it were owned -- invalid C and, had it compiled, a use after free. The refusal is the honest interim, not the design.

Supporting it would mean an OptionView-shaped wrapper whose payload points into the generator's own field, a resume slot that stores that pointer rather than a boxed value, and a call that is outx so the caller's binding keeps the generator (and, through its non-owned fields, the source) locked while the yielded reference is live. Open: whether the pin should reach the source through the generator or be taken on the source directly; whether a for loop over such a generator binds its element borrowed (as container iterators do) or copies; and whether a valtype leaf may be yielded by reference at all. Until decided, a generator yields owned values only, and a reference into its captured state is exposed through an ordinary outx method instead.
