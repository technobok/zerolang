1. Testing

This page says what tests the repository has, what each make target runs, and how to add a test of each kind. Every gate needs only the compiler and a C toolchain: the test runner (src/ztestrunner.z), the linter (src/zl.z) and the gate tool (tools/zgate/) are zerolang programs.

2. The tiers

TargetWhat it runsWhen
make checkthe parse-tier lint and the formatter check over every source file (zl lint, zl format --check), and the complexity reportbefore every commit

make pre-pushcheck, test and perf-strictbefore a push
make cievery gate (below)at the end of a batch of work

make doc-check runs the doccode and docpage kinds alone. make style-lint adds the typecheck-tier lint (zl lint --full) to make check's.

2.1. make ci

make ci runs, in order:

  1. perf-strict, alone: the allocation ratchet (see Performance). It runs first and alone because a zc running beside it in the repository root moves its count.
  2. ci-gates, in parallel: the legs make ci-legs lists. They are the per-batch gate's guards (GATE_GUARDS: the lint, the warnings and -Wpedantic checks, the guards over the emitted C, the thread sanitizer, the math and Windows legs), the legs that rebuild the run corpus's C under another toolchain (GATE_SAME_C: full UBSan, mingw-w64 and tcc for Windows under wine, MSVC under wine), and the legs only make ci runs (CI_ONLY: the heavy corpus ci-corpus, clang, -O2, arm64 under qemu, the fuzzer's and the generator's fixed seeds, both build modes, the coverage ratchet coverage-check). A leg whose tools are missing says so and passes.
  3. test-bootstrap: the seed builds a compiler that rebuilds itself to a byte-identical fixpoint, under gcc, clang and the vendored tcc, and the three emit the same C.
  4. windows-due: one line saying when make ci-windows is due.

make ci-windows runs the Windows legs on a real Windows machine and, when they pass, writes tests/known/windows.zd (zgate windows-record), which the commit carries; zgate windows-due reads it. tools/windows/README.md sets one up.

2.2. Fuzzing

make fuzz runs the token-mutation fuzzer, tests/unit/zfuzz.z, against a compiler built with AddressSanitizer. Each case edits the tokens of one corpus program and builds the result. The build must pass, or the compiler must refuse the program with a diagnostic. Anything else is a finding: a crash, a sanitizer report, a hang, a panic, an emitter error or C that the C compiler refuses. A finding is kept in out/fuzz/findings, with the compiler's report beside it.

make fuzz-recheck DIR=<folder> builds every finding under a folder again and lists the ones that still fail. make fuzz-reduce FILE=<finding> OUT=<file> shrinks one finding while it shows the same defect -- runs of lines first, then runs of tokens -- so that what is left can become a fixture.

make fuzz-gen runs the same tool as a generator (zfuzz --generate). Each case is a new program that the generator writes from scratch: typed scalars of every width (i8 to i128, u8 to u128, f16, f32 and f64), every operator, conversions, locals, if and match values, counted loops with break, and functions that call each other and recurse. It declares records, variants, classes and unions of its own: it builds them, reads and writes their fields, compares records and variants with ==, and matches variants and unions (as a statement and as a value, the arm's payload read through the subject's name); it keeps lists -- ListVal of scalars, records and variants, List of a class -- appends to them, reads and replaces their items, walks them with for each and passes them to functions. What it writes keeps an ownership discipline, stated at the head of tests/unit/zfuzz/gen.z, inside which every program is valid. Each program stops, and the generator has a model -- an interpreter of its own -- that says what the program prints and how it exits: values held by value are copied, a class, a union's payload and a list are shared by reference. About one program in ten ends in a planned panic: a division by zero, .orPanic on a failed conversion, or a list read past its end. Each constant expression is also written three ways -- a unit constant, the expression in a body, and a function over parameters -- so that the compiler's folding is checked against the C.

The compiler built with AddressSanitizer emits each program's C once. The C is built and run under five configurations: gcc and clang at -O0 with AddressSanitizer and UBSan, gcc and clang at -O2, and tcc. Every run must print what the model expects and exit as it expects. zl fmt also lays each program out: the layout must be final, zl lint must read it, and the layout must run like the program. A refusal is a finding too. Before a run, the model's integer arithmetic is checked against the output of overflow_methods, whose values are computed outside the compiler. A finding is kept in out/fuzz-gen/findings: the program, and what differed with the output the model expects. make fuzz-gen SEED=7 N=20000 runs a campaign; make ci runs 320 programs of seed 11 (fuzz-gen-ci, about 30 seconds alone).

2.3. Coverage

make coverage measures what the test suite runs of zc, and writes the report out/coverage/coverage.md. It counts in zerolang terms: a line is a line of a .z file, and a function is a zerolang function. The run (zgate coverage) has four steps.

  1. bin/zc emits the compiler's own source with --line-marks (see zc): the C names, in #line directives, the source line each statement and each function came from. gcc compiles that C with --coverage and without the optimiser.
  2. The workload runs against that compiler. It is the suite itself: the test runner's default kinds (what make test runs), the zc command lines the Makefile's rules and guards issue directly, and the programs of the generator's fixed-seed run, emitted and not built. A step that fails fails the run.
  3. gcov reports each line's count. The C of a statement counts on the statement's first line; an instance of a generic counts on the lines of its definition. The C that comes from no statement -- the runtime, the types, the helpers zc writes itself -- is not counted.
  4. The report lists, per file, the counted lines and how many ran; the functions no test enters; and the entered functions with the most lines that did not run.

make coverage-check, a leg of make ci, is the same run with a ratchet: tests/known/coverage.zd lists the functions no test enters, each with a why. The leg fails on such a function that the file does not list: add a test that reaches it, or delete it when nothing can. It fails on a listed function too, when a test enters it now or the build no longer holds it: delete its line in the same change. untriaged is the why of a function nobody has looked at yet. make coverage-known writes the file from a run and keeps each why. The run takes about two minutes. It needs gcc and gcov, so on a Windows host the leg prints that it is skipped.

zgate covprobe out/coverage FILE.z TARGET... answers one question with the build of the last run: does compiling this program reach that? It compiles FILE.z alone and says for each target -- a function's name, or path.z:LINE -- whether it ran. Use it to write the test for a listed function: write the program you think reaches it, and ask.

3. The test runner

A command line it does not accept is refused with exit 2. The kinds, as the runner's header lists them:

4. Adding a test

Each kind reads its cases from tests/fixtures/:

  • A program that runs. A row (program name: dir:) in run_cases.zd, the program at <dir>/<name>.z -- usually tests/fixtures/emitc_corpus/ -- and its output in run_golden/<name>.out. The row's roots names more source roots its units come from; posix: true marks a program that checks what only POSIX has, which a build for Windows lists and does not run. The two matrix generators write their own lists, matrix_cases.zd and cpar_cases.zd. A <name>.exit holds an exit code other than 0, and <name>.<os>.out the output for a system that prints its own.
  • A program the compiler refuses. errors/<name>.z and errors/<name>.err, the error[Exxxx] lines and the count line. A <name>.zcargs gives the compiler flags (--eager for a unit whose error is in code nothing calls).
  • A dump. A row in dump_cases.zd and dump_golden/<name>.canon.
  • A language-server session. lsp_cases/<case>.msgs, one JSON message a line, and lsp_golden/<case>.out; make regen-lsp-goldens rewrites the goldens from a run.
  • A command line. A folder usage/<case>/ with args (the driver's name and its arguments, where $ROOT, $SCRATCH and $HOST stand for the repository, an empty folder of the case's own and the host's target), expected.exit, and expected.err and expected.out for what the driver says. A cwd file holding scratch runs the driver in the scratch folder. --regen-usage rewrites the expected files.
  • An example in the documentation. A #code language=zerolang block in a .pdoc page; see the style guide's "Examples in Documentation".
  • A C test. tests/c/<name>_test.c and tests/c/<name>_test.out.

make regen-goldens rewrites the lexer, parser and program goldens of the examples. A golden that moves is a signal: read its diff before committing it.

Lists of expected failures, each read by one leg: the data files of tests/known/ -- leaks.zd, and one per toolchain (tcc.zd, mingw.zd, ...) naming the cases it refuses or fails and the stage each stops at -- fuzz.zd and fuzzgen.zd, the signatures the fixed-seed runs of the fuzzer and of the generator are known to show, and coverage.zd, the functions of zc that no test enters.

Every list and table the tests keep is a data file: the case lists, the lists of expected failures, the ratchet baselines below, the two matrix tables (matrix_expect.zd, constparity_expect.zd) and the record of the last green Windows run. The runner, zgate and the generators read and write them with the standard library's zd unit, and make check keeps them formatted.

5. Ratchets

A ratchet holds a count at its committed value: a count above its row fails, and a count below fails until the row is lowered in the same commit. A row is raised only with the reason in the commit message.

  • tests/fixtures/arch_baseline.zd -- zl lint --arch findings per rule and file (the arch kind).
  • tests/fixtures/doc_baseline.zd -- undocumented definitions (L016), docs that only repeat their declaration (L024) and a body repeated across a file (L025), under --heavy.
  • tests/fixtures/doccode_baseline.zd -- per page, the examples marked check=none and the checked ones zl fmt would lay out differently.
  • ALLOC_BASELINE in the Makefile -- the self-compile's heap allocations (perf-strict).
  • src/ztestrunner/expected.z -- the pins and the emitted kind's baselines.

6. The per-batch gate

bin/zgate (tools/zgate/, built by make test) gates a batch of commits against a snapshot of an earlier, gated state. Its home, $ZGATE_HOME, holds the snapshots and its lock.

7. Performance

Two binaries hold the same emitted C. bin/zc is the driver, built at -O2. out/zc-perf is the measured one, built by PERFCC at PERFOPT (gcc -O1) and rebuilt by every performance target: -O2 moves the wall time by about 30% and the allocations by nothing, so every measurement is of out/zc-perf. Never time bin/zc for a measurement. Each target below builds what it measures and passes it to zgate perf, which measures and judges.

  • make perf -- the self-compile's line count, wall time (best of five) and peak memory, the parse / typecheck / emit split, and the allocation total when valgrind is installed.
  • make perf-strict -- the allocation ratchet: the heap blocks of one self-compile under valgrind, the same on every run, against ALLOC_BASELINE. A count above it fails: lower the count, or raise the baseline with the reason in the commit. A count below it asks for the baseline to be lowered in the same commit. It refuses a clang-built binary, and it reports the instruction count beside the allocations.
  • make perf-elision -- the allocations an optimising C compiler deletes as write-only: bin/zc.c built twice by clang, once with -fno-builtin-malloc. The difference belongs at zero.
  • zgate ab -- splits a change in allocations into the part the compiler's behaviour made (new compiler, old source) and the part its own source made (new source, new compiler).

Judge speed by instructions, not cycles.

perf stat -e instructions:u counts work, and for one binary on one input it is the same on every run, to a few hundredths of a percent, so a difference of 0.2% can be read. Cycles count how long the core took to do that work, and they move with whatever else runs: a thread on the same physical core, other programs using the shared cache and memory, the scheduler moving the process to another core, whether the kernel could give the heap large pages, and where code and heap fall in memory. Three rounds of the same binary on the same input have differed by 13% in cycles while the instruction count held to 0.01%. A speed claim needs both binaries on the same input: the self-compile cannot separate a slower compiler from a larger source, so compare two compilers on one fixed program. Quote cycles only when both binaries' spreads are tight, the rounds were interleaved and the machine was quiet. Allocations count events, not time, and none of this moves them.
