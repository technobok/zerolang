1. Overview

The declarations themselves live in lib/system/system.z, which is the one place they are written. Every definition, field, arm, generic parameter and own-line parameter there carries its own doc comment, and zls surfaces each on hover; the corpus runner ratchets that coverage under make ci. This page is the prose and the worked examples -- read it for how the unit is meant to be used, and the source for the exact surface.

The system unit holds the types that are part of the language fabric: numeric primitives, booleans, strings, option / result containers, typedefs, and the control-flow natives. Everything in this unit is re-exported unqualified by core -- you write i64 and String, not system.i64 and system.string.

Zerolang has three string types that separate ownership, mutability, and storage concerns: String (mutable, owned, heap-allocated), StringView (readonly view over a source), and str to: N (fixed-capacity, stack-allocated valtype -- defined in collections). All three are length-delimited UTF-8; there is no language-level guarantee of NUL termination. String literals live in .rodata as StringView with zero heap cost.

Option and Result are the two discriminated unions that shape API design across the standard library. Use Option when absence is an expected condition (looking up a map key, reading an environment variable). Use Result t: T e: IoError when an operation can fail for reasons the caller needs to handle (syscalls, parsing).

2. Index

Numeric types

  • i8 / i16 / i32 / i64 / i128 -- signed integer records
  • u8 / u16 / u32 / u64 / u128 -- unsigned integer records
  • f16 / f32 / f64 / f128 -- IEEE 754 floating-point records
  • c8 / c32 -- character code-unit records (UTF-8 byte / Unicode scalar)

Primitive types

  • bool -- variant { false: null true: null }
  • null -- null: record is native
  • never -- never: record is native
  • intliteral / floatliteral -- the compile-time types of a numeric literal
  • Any -- Any: union is native (system-internal; not user-reachable)

String types

  • String -- String: class is native (mutable, owned, heap-allocated)
  • StringView -- StringView: class is native (readonly view with a .borrow on its source)
  • CpIter -- call: function out (optionval t: u32)
  • Splitter -- call: function out (Option T: StringView)
  • LinesIter -- call: function out (Option T: StringView)
  • Text -- protocol { stringView: function {:this} out StringView }
  • StringLike -- union { :StringView :Text }

Option and Result

  • Option -- union { none: null some: t } as { t: AnyRef.generic }
  • OptionView -- union { none: null some: t.borrow } as { t: Any.generic }
  • optionval -- variant { none: null some: t } as { t: anyval.generic }
  • Result -- union { err: e ok: t } as { t: AnyRef.generic e: AnyRef.generic }
  • resultval -- variant { err: e ok: t } as { t: anyval.generic e: anyval.generic }
  • parseerror -- variant { empty: null invalidDigit: null overflow: null }

Byte and Path typedefs

  • Bytes -- class { val: (ListVal u8).typedef }
  • ByteView -- class { val: (ListViewVal u8).typedef }
  • Path -- class { val: String.typedef }
  • PathView -- class { val: StringView.typedef }

Generic primitives

  • Box -- class {} as { t: anyval.generic }
  • typedef -- record is native as { from: Any.generic }
  • tag -- record is native as { t: anyval.generic }

Control flow

  • error -- function as { T: StringLike.generic } in { msg: T } out never is native
  • panic -- function as { T: StringLike.generic } in { msg: T } out never is native
  • return -- function as { t: Any.generic } in { result: t } out never is native
  • break -- compiler-intrinsic
  • continue -- compiler-intrinsic

3. Numeric types

Sixteen numeric record types: five signed integers, five unsigned integers, four IEEE 754 floats (f16 half precision, f32, f64, f128 quad precision), and two character code-unit scalars (c8 a UTF-8 byte, c32 a Unicode scalar value). All are valtypes (records): copied on assignment, no heap allocation, no destructor.

Four are declared in implementation subunits of system (the files under lib/system/system/), one per host-toolchain requirement, because each needs something that not every compiler has -- and a unit is the granularity at which a program says what it needs from one. quadfloat holds f128, whose runtime needs libquadmath; wideint holds i128 and u128, which need a compiler with __int128; halffloat holds f16, which needs one with _Float16. Each carries a require: block, and it applies only to programs that actually reach the subunit: quadfloat's names a library to link, the other two name none, and all three turn away a toolchain that cannot build the type -- by name, before any C is written, instead of letting the C compiler reject a type the program never wrote. The subunits are private to system, which re-exports the four types under their own names, and core re-exports them like the rest, so 1.5.f128 and x.i128 read no differently.

Literals. A numeric literal has a type of its own before context pins it -- intliteral or floatliteral -- and the dotted suffix form is a DECLARED method on that type: 65.u8, 1.5.f32, 0xff.u32. Unpinned, an integer literal falls to i64 and a float literal to f64. Do not write 65u8 (non-dotted form is reserved syntax).

Arithmetic. Every type declares +, -, *, /, % (modulo) as native methods taking a same-type rhs; on the float types % is the C fmod family, exact in-format. Only the integer types declare the bitwise set & (AND), | (OR), ^ (XOR), << and >>; a float has no bit pattern to combine, and an operator that typechecks has to emit code that compiles. The complement is not, a method and not an operator, because zerolang has no unary operators at all.

Shifts. >> is arithmetic on the signed types -- it fills with the sign -- so a logical right shift is spelled x.bits >> n. The count is the same type as the left operand, like every other binop, and a bare literal coerces, so x << 3 is what you write. Over-wide counts are defined, not undefined: a count at or above the type's width yields 0 for << and for unsigned >>, and 0 or -1 by the sign of the left operand for signed >>. Because the count carries the operand's type it can be negative on a signed type; it is compared as unsigned, so a negative count answers the same way an over-wide one does rather than reaching undefined behaviour.

  a: (0.i64 - 8.i64)
  b: a >> 1           # -4   -- arithmetic, fills with the sign
  c: a.bits >> 1      # 9223372036854775804 -- logical
  d: a << 64          # 0    -- at the width, defined
  e: a >> 64          # -1   -- sign fill, defined

Operators resolve as ordinary declared methods -- the system units are the single source of truth -- so an operator on a type that declares none (e.g. bool + 1) is a plain "type has no method" error, and a mismatched rhs (1 + true) is an argument-type mismatch against the method. No implicit promotion: i32 + i64 is a type error; cast first.

Comparison. Every type declares <, <=, >, >=, ==, != as native methods taking a same-type rhs; all return bool. Comparisons are method-driven like arithmetic; a user record or variant that declares none still compares with == / != through generated structural equality.

Conversion. Every type has a method named after every other numeric type. A provably-safe conversion (widening, identity, an integer within a float's mantissa, f32 -> f64) yields the target type directly; a possibly-lossy one (narrowing, sign crossing, float -> integer, f64 -> f32, integer beyond a float's mantissa) yields resultval t: T e: converror so the loss cannot be discarded silently -- unwrap it with .orPanic / .or d: / match. A compile-time-constant conversion is checked statically and stays the bare type. See the language spec's Numeric conversions at runtime for the full rule.

  x: 65.u8
  y: x.i64            # widens u8 -> i64, stays i64
  z: (1000.u64).u8.orPanic  # u64 -> u8 is lossy: resultval, abort on overflow
  f: 3.14.f64
  n: f.i32.orPanic    # f64 -> i32 is lossy: resultval, abort if inexact/out of range

Representation. bits reinterprets the receiver as the same-width unsigned integer. It is the one member here that is not a conversion: every conversion above is a checked VALUE conversion that can fail, and bits is a representation view that cannot -- which is the whole reason both exist. (0.i64 - 8.i64).u64 panics, because -8 is not a u64; (0.i64 - 8.i64).bits is the pattern -8 is stored as. A logical right shift is spelled x.bits >> n, since >> is arithmetic on the signed types.

It is declared on the five signed integers (i8 i16 i32 i64 i128) and the four floats (f16 -> u16, f32 -> u32, f64 -> u64, f128 -> u128), and nowhere else. It is width-preserving, because sending every type to u64 would sign-extend first and an i8 of -8 would read as 0xFFFFFFFFFFFFFFF8. It is one-directional, so the name is unambiguous: i64.bits can only mean u64. Nothing is added to the unsigned types, where it would be the identity.

  a: (0.i64 - 8.i64)
  b: a.bits           # 18446744073709551608 -- cannot fail
  z: (-0.0.f32).bits  # 2147483648: +0.0 and -0.0 compare EQUAL and
                      # differ in bits, so no value conversion sees it

Exponents. The four float types carry scaleB and logB, IEEE 754's own names for the two operations that move a value along its exponent without touching its significand.

x.scaleB n: k is x x 2^k. It is not a multiplication: the exponent moves and the significand does not, so nothing rounds anywhere in the type's range -- which is the reason to have it rather than a loop of x * 2.0. n is an i32 and may be negative.

x.logB is the unbiased exponent of x as an i32 -- the binade it lies in. A subnormal is normalised first, so the answer describes the value rather than its encoding. The two together normalise a value to [1, 2) without a loop, and build an exact power of two without one either.

  x: 3.0
  u: x.scaleB n: 4          # 48.0, exactly
  d: x.scaleB n: (0 - 4)    # 0.1875, exactly
  e: x.logB                 # 1 -- 3.0 lies in [2, 4)
  m: x.scaleB n: (0.i32 - x.logB)   # 1.5 -- normalised to [1, 2)
  p: 1.0.scaleB n: (0 - 24) # 2^-24, with no rounding to reason about

Ranges:

  • i8: -128 .. 127
  • i16: -32768 .. 32767
  • i32: ~-2.1e9 .. 2.1e9
  • i64: ~-9.2e18 .. 9.2e18
  • i128: -2^127 .. 2^127 - 1
  • u8: 0 .. 255
  • u16: 0 .. 65535
  • u32: 0 .. ~4.3e9
  • u64: 0 .. ~1.8e19
  • u128: 0 .. 2^128 - 1
  • f32: IEEE 754 single precision (~7 decimal digits)
  • f64: IEEE 754 double precision (~15-17 decimal digits)

Overflow behavior. Signed overflow follows two's-complement wrap-around (C -fwrapv semantics), unsigned overflow wraps modulo 2^N. No trapping or saturating variants yet.

#~"i128" / #~"u128" caveat. These rely on C compiler support for __int128 (gcc / clang). That reliance is declared rather than assumed: they live in system's wideint subunit, whose require: block rejects a build with tcc and says why, so a program using them fails at type-check with its own message instead of inside the C compiler. Width on platforms without native 128-bit support is determined at C compile time.

4. literal types

The type a numeric literal wears before context pins it. intliteral declares a conversion to each of the sixteen scalars; floatliteral declares only the four float ones, which is what makes 3.5.u8 a missing member rather than a rule written by hand.

Their conversions return the bare target type, never a resultval. On a scalar a lossy conversion can fail at run time and so must be checked; on a literal the value is known at compile time, so it either fits -- and 65.u8 is simply a u8 -- or it does not and the program is rejected where the literal is written.

Neither type reaches emission: the programmer converts explicitly, or context coerces, or the literal falls to i64 / f64.

core re-exports both names, so a unit-level alias may refer to one (lit: intliteral), but create: null means nothing constructs one: a binding that names it bare is refused by the general non-constructible rule, the same one a user record with create: null gets. There is no literal-specific message for it. That is the whole of the usability, and it is meant to be thin -- these are what the checker gives a lexeme, not a surface a program builds with. Contrast Any, which is withheld from the prelude entirely.

5. bool

Two-state valtype declared as a variant with null-payload arms and a u8 tag. It declares the six comparison operators (==, !=, <, <=, >, >=) as native methods returning bool, so bool values compare through the declared methods like any other type. false and true are unit-level names (re-exported by core) resolving to bool.false / bool.true respectively -- the same pattern numeric "literals" follow.

Values. Produced by comparison operators (==, <, etc.), by the literals true / false, or by any expression whose type is bool. Consumed by if / while / match arm guards.

Match. Because bool is a variant with arm names false and true, pattern-matching works directly:

  match (cond)
  case true  then print "yes"
  case false then print "no"

C emission. Despite the variant declaration, bool is emitted as C99 _Bool (from <stdbool.h>) -- TYPEMAP maps it to the primitive short-circuit. Struct-wrapped variant storage is never materialised for bool. Comparisons emit as raw C boolean expressions ((a < b)), if conditionals work with the primitive directly (no .tag access), and match on a bool subject lowers to an if / else if on the primitive.

No bitwise and / or / not methods on bool yet -- short-circuit && / || lives at the expression level; see grammar.

6. null

The unit type. Exactly one value, also spelled null. Used as the payload in variant / union arms that carry no data (Option.none: null, Result.ok: null), and as the return type of functions that don't return a value.

Not the same as C's NULL -- zerolang pointers are non-nullable at the language level; Option handles the "maybe-absent" case.

7. never

The bottom type: the empty type, with no values. Used as the return type of functions that never return normally (error, panic, return). never is a subtype of every type, so an error ... or panic ... call is usable in any expression position.

Control-flow analysis tracks never-returning expressions to determine unreachable-code errors and branch exhaustiveness. See ./spec.htmlspec, the never type.

8. any

The universal supertype: the union of all types -- and not a user-reachable name. Any is retired from the user surface: it is not re-exported by the prelude, and a user spelling of it in any position (a binding, a parameter type, a field type, or an Any.generic bound) is the standard unknown-name error (E0023), exactly as an undefined identifier is, unless the unit defines its own Any. The bounds to write are:

  • AnyRef.generic -- any reftype (class, union, protocol, String). The bound on ListRef.of, Option.t, Result.t / e
  • anyval.generic -- any valtype (record, variant, numeric, str, array). The bound on ListVal.of, optionval.t, Box.t
  • RefHashable.generic -- a reftype that also declares hash and ==. The bound on a hashed position: SetRef.of, the Map reftype keys
  • valhashable.generic -- the valtype counterpart, for SetVal.of and the Map valtype keys

Any itself survives only inside system on parameters that are never consulted (return, typedef) and on the two types that deliberately span both families (Iterator, OptionView -- a borrowed view of a valtype is still a reference). Assigning into a bare Any is not supported -- zerolang does not do runtime type tagging at that level.

9. string

create (zero arguments) is the empty string; the bare type name constructs it implicitly (buf: String), as does each numeric type's create its zero (n: u64). See the spec's Zero Values section.

Mutable, owned, heap-allocated UTF-8 text. Primary string type for building and modifying text. A two-word struct: size (current byte count) plus capacity (allocated buffer size). No separate string-builder type -- String is the builder.

Construction. The most common form is projecting a stringView-typed literal:

  s: "hello".string

This copies the rodata literal into a fresh heap buffer. To accumulate programmatically, start empty and .append:

  s: "".string
  s.append "hello"
  s.append " "
  s.append "world"

Methods.

  • StringView -- view over the whole string. Installs an EXCLUSIVE lock on the string for the view's lifetime (see the note on views below)
  • length / capacity -- u64. length is the current byte count; capacity the allocated buffer size
  • append s: T (StringLike) -- concatenates the arg's bytes. Grows if needed. Accepts any StringLike -- a literal, a substring view, or a String -- with no projection at the call site; a String arg is borrowed, never moved
  • reserve n: u64 -- ensure capacity >= length + n. Pre-allocates so subsequent append calls don't reallocate
  • shrink -- release unused capacity back to the allocator
  • compare rhs: String -- byte-wise memcmp-style; returns -1 / 0 / 1
  • copy -- fresh, independently-owned duplicate. Allocates a new heap buffer; mutating the copy does not affect the original (and vice versa). Use when you have a borrowed String and need to hand an owned value to a destination that requires ownership (a constructor field, a list/map insert) — see ownership.pdoc for the borrow escape rules
  • hash -- 64-bit SipHash-1-3 of the byte contents using a per-process random seed initialised at program start. The same bytes hash to the same value inside one run, but the value changes across runs (DoS resistance, matching Python / Rust / Swift). Not suitable for content-addressed storage; pair it with a deterministic hash for that use case

Non-allocating queries. String declares count, startsWith, endsWith, and contains directly, with the same semantics as the StringView methods of the same name. The rest of StringView's read surface (byteAt, indexOf, trim, split, the parse methods, ...) is reached through an explicit .stringView view -- String declares its own read surface and does not silently inherit StringView's.

Ordering. <, <=, >, >= are byte-wise lexicographic on the UTF-8 bytes. A shorter string is less than a longer string that shares its prefix. Not locale-aware.

Destruction. Scope exit frees the heap buffer. Moved values (.take) are invalidated at the source; the destination destroys.

10. stringView

Readonly borrowed view over UTF-8 text. A 16-byte (pointer, length) pair that can point into a String's buffer, into static .rodata, or into a substring of another view. Always valid UTF-8 (the source guarantees it).

Lock semantics. Creating a view installs an EXCLUSIVE borrow-scoped lock on the source path. The source cannot be reassigned, freed, or have conflicting views taken while the StringView is live. Releasing the view (scope exit or explicit .drop) releases the lock. A view cannot escape into a class field or be returned from a function unless the source is a non-owned parameter -- see ownership. Construction.

  # A literal IS a stringView -- zero-copy into .rodata
  v: "hello"

  # From a mutable string -- installs a lock on s
  s: "world".string
  w: s.stringView

  # A byte-range slice: .substring on String, StringView, or str
  u: w.substring from: 0 to: 3

Methods: non-allocating queries. These inspect the view without touching memory outside its range. isEmpty, isAscii, startsWith, endsWith, contains, indexOf, lastIndexOf, byteAt are all O(n) or O(1); none allocate.

Methods: view-returning slicing. substring, trim, trimStart, trimEnd, stripPrefix, stripSuffix. Returned stringView borrows from the same source as the input -- the lock on the source remains held. ASCII whitespace only (space, tab, CR, LF, VT, FF).

Methods: iteration. split sep returns a Splitter; lines returns a LinesIter; codepoints returns a CpIter. All three are consumed with for piece: sv.split ...: .... splitOnce returns the byte index of the first separator as optionval(u64), useful when you want to slice the view yourself.

Methods: allocating transforms. toLowerAscii, toUpperAscii, replace, replaceFirst, repeated, concat each produce a new owned String. The source view remains unchanged. toLowerAscii / toUpperAscii are ASCII-only ([A-Z] <-> [a-z]); non-ASCII bytes pass through.

+ builds, append accumulates. + is declared on both String and StringView with the same meaning and the same result: a NEW owned String holding both operands' bytes, with neither operand modified. sv.concat other: x is that same operation spelled as a method. Because the meaning does not depend on the receiver's ownership, a + b reads the same whether a is owned or borrowed, and a + b + c chains left to right (binary operators are left-associative and have no precedence).

To accumulate WITHOUT allocating, use append, which writes into the receiver's own buffer and yields nothing:

out: "".string
with it: parts.iterate do for p: it loop out.append p

Building a string with + in a loop reallocates at every step; append -- with reserve when the final size is known -- does not.

Methods: numeric parse. parseI64 / parseU64 / parseF64 consume the whole view (no trailing garbage allowed). Optional leading sign on parseI64 / parseF64; decimal digits only; no underscores, no radix prefixes, no whitespace. Failures come back as parseerror: empty, invalidDigit, overflow. For more flexible parsing, .trim first and split the sign off manually.

Ordering. Same byte-wise lexicographic rule as String.

Hashing. .hash returns a 64-bit SipHash-1-3 of the viewed bytes using a per-process random seed. Same contract as String.hash -- stable within a run, randomised across runs, not a content hash.

#~":text" conformance. StringView is the trivial implementor of the Text protocol -- its .stringView method returns itself. This lets any Text-constrained generic accept a plain view.

11. String iterators

Iterator classes built by StringView.codepoints, .split, and .lines. Opaque to user code -- only the .call method is public. Each .call yields the next item:

  • CpIter.call yields optionval(u32) -- the next decoded codepoint, or optionval.none at end. Ill-formed bytes are replaced with U+FFFD and the iterator advances one byte
  • Splitter.call yields Option(StringView) -- the next split piece, or Option.none at end. Empty separators yield zero iterations
  • LinesIter.call yields Option(StringView) -- the next line (without trailing \n or \r\n), or Option.none at end. An empty trailing line is dropped

Rarely constructed directly: for over the source is the usual form.

  s: "alpha,beta,gamma".stringView
  for piece: s.split ",".stringView loop {
      print piece
  }

12. text and StringLike

The Text protocol is a minimal conformance: any type with a stringView: function {:this} out StringView method can declare :Text in its as block and then accept a Text-constrained argument. Used by APIs that want to read text without caring whether the source is a String, StringView, str to: N, or a user aggregate with an embedded text field.

StringLike is the heterogeneous-union constraint used on generic function parameters: T: StringLike.generic accepts T if T is a StringView (fast path, no method call) or declares :Text conformance (dispatches through the method). Matched in declaration order; see ./spec.htmlspec for the full rule.

13. option

Discriminated union for optional reftype values. Two arms: some holds a t; none holds null. Use Option when absence is a routine expected case (map lookup, env var read, parse position past end).

Constraint. t: AnyRef.generic -- the payload must be a reference type (class / union / protocol / typedef over those). For valtypes, use optionval.

OptionView is the borrowed twin: its some arm carries a t.borrow, a reference into storage owned by someone else -- it is what container readers (get on reftype values, iterator call) hand back. A view of a valtype is still a reference, so one OptionView serves both families; that is why its bound stays Any.generic.

Construction. Via the arm accessors:

  some_result: Option.some "hi".string
  no_result:   Option.none null

Pattern matching. Exhaustive match:

  match (Result)
  case some then print Result.string
  case none then print "(missing)".stringView

Inside a case some then { ... } arm the subject narrows to the payload type: access fields as Result.string (the t field name narrows as the arm label, not as Result.some; see the saved feedback on match narrowing).

14. optionval

Variant (valtype-payload) counterpart to Option. Same semantics, but the payload is stored inline (no heap allocation for the wrapper). Use when the contained t is a valtype -- u64, a record, a variant.

The stringView numeric-query methods (indexOf, lastIndexOf, byteAt) and StringView.splitOnce return optionval(u64) / optionval(u8).

15. result

Two-armed union for operations that can fail. The ok arm carries the success value; the err arm carries the error. Both type parameters are AnyRef.generic -- a union holds reftypes. A valtype success value is spelled with a Box argument -- (Result (Box u64) E: IoError) -- which collapses onto the payload cell: the match arm binds the bare u64, and nothing is stored double-indirected. A payload-less success is (Result null E: ...) -- null satisfies either family bound. The all-valtype counterpart is resultval (a variant, inline storage, with or / orPanic helpers); numeric conversions and parses return it.

Canonical uses.

  • (Result T: File E: IoError) -- io.open return
  • (Result T: String E: IoError) -- io.readText, os.cwd
  • (Result T: null E: IoError) -- side-effectful I/O: io.writeText, io.remove, os.setEnv
  • (Result (Box u64) E: IoError) -- byte-count returns: File.read / write, Conn.read / write
  • (resultval t: i64 e: parseerror) -- numeric parse from StringView.parseI64 (a variant: both arms valtypes)

Like Option, consumed by exhaustive match whose arms narrow the subject.

  match (io.readText path: "a.txt".string)
  case ok  then print ok
  case err then io.eprintln "failed".stringView

16. parseerror

Error variants for the numeric-parse methods on StringView (parseI64 / parseU64 / parseF64). All arms are null payloads, so the error fits inline with no heap allocation:

  • empty -- view is empty, or (for signed parse) contains only a sign
  • invalidDigit -- a non-digit byte appeared (other than the leading sign on signed parses, or the decimal point on parseF64)
  • overflow -- magnitude exceeds the target type's range

17. bytes and byteView

Two typedef classes for binary data: Bytes is an owned, growable buffer; ByteView is a readonly borrowed view into one. The underlying storage is (ListVal u8) / (ListViewVal t: u8) -- bytes are valtypes, so the valtype list family backs them; the typedef wrapping gives binary-data signatures a distinct name and a namespace for bytes-specific methods.

Because the wrapped types are classes, List operations flow through transparently via the typedef backward-compatibility rule: .append, .length, .listView etc. work on a Bytes value. See ./stdlib_collections.htmlthe List family.

View lifetime. ByteView mirrors StringView / ListView lock semantics: creating a view locks its source for the view's lifetime. Views cannot escape into class fields or be returned from a function that doesn't receive the source as a non-owned parameter.

Construction.

  b: Bytes
  b.append from: 72.u8
  b.append from: 105.u8
  v: ByteView.borrow from: b.listView

18. path and pathview

Typedef classes over String / StringView for filesystem paths. The wrapping gives I/O signatures a distinct path name and a place for path-specific methods (join / parent / basename / extension / normalize) as they land. Until then, string operations flow through via the typedef rule.

View lifetime. Same as StringView / ByteView -- a PathView locks its source Path.

19. box

Generic reftype wrapper over a valtype (the bound rejects reftypes -- they are already references). Converts a valtype into a heap-allocated reftype; its C representation is a bare pointer to the element. Box from: copies the value onto the heap and returns the boxed reftype.

The union-arm spelling. A union holds reftypes, so a valtype arm is written (Box T) -- and it collapses: the arm child IS the element, construction takes the bare value, match arms bind the bare element, and the emitted C is exactly the heap cell a union arm always uses. The same collapse applies when a union is instantiated with a Box type argument ((Result (Box u64) E: IoError)).

  r: i64
  b: Box from: r       # b: box(i64)

Construction is routed through the unified call dispatch; see compiler. Destruction frees the heap copy on scope exit.

20. typedef

Zero-overhead wrapper type. Parameterised by the wrapped type. Users don't instantiate typedef directly -- they define a class with a single .typedef field, which the compiler recognises as a typedef marker:

  Path: class { val: String.typedef }

This declares Path as a typedef over String: a distinct type in signatures but with full backward compatibility to String's operations. See ./spec.htmlspec.

21. tag

Generic record that carries a variant / union discriminator's storage type. The tag: tag field in numeric records and user variants tells the compiler how wide the discriminator is. Parameterised by t: tag of: u8 / tag of: u16 / etc. Rarely referenced by user code directly -- the compiler emits the tag field and accesses it internally.

22. error

Compile-time error. Invoking error msg: ... at type-check time emits the message as a compile error and aborts compilation. Used in generic bodies and conditional code paths that must be statically dead; the never return type lets error occupy any expression position.

  f: function as { T: anyval.generic } in { x: T } is {
      if (is T: never) {
          error msg: "never-valued T".string
      }
  }

23. panic

Runtime terminal error. panic msg: ... prints zpanic: <msg> to stderr and exits the process with status 1. Use panic for programmer errors that should never occur at runtime (invariants, unreachable defaults, bounds preconditions the caller is responsible for maintaining); for recoverable errors prefer Result t: T e: E.

The distinction from error: error is a compile-time construct -- an error msg: ... call in a statically-reachable branch aborts compilation. panic is the runtime counterpart, emitted as a call to the shared z_panic helper in the emitted C runtime. All internal unrecoverable exits (OOM, bounds checks, numeric cast overflow, stringView bounds) also funnel through z_panic, so every termination produces a consistent zpanic: prefixed diagnostic.

  check_positive: function {n: i64} out i64 is {
      if n <= 0 then {
          panic msg: "expected a positive integer"
      }
      return n
  }

Panics are terminal: there is no recover mechanism. The never return type ensures any code after a panic is statically unreachable.

24. return

Return from the enclosing function. Spelled as a function for uniformity with the control-flow dispatch model -- return x is a call with a single positional argument.

The never return type ensures the rest of the enclosing block is unreachable and the compiler's dead-code analysis applies.

  f: function out i64 is {
      return 42
  }

Return ownership semantics are tied to the function's declared return-ownership annotation; see ownership for .borrow / .view interactions and the lock-escape rules for view returns.

25. break

Compiler-intrinsic. Breaks out of the enclosing for / do loop. Takes no argument. The never return type propagates through the enclosing block.

  for i: 0.u64 to: 100.u64 loop {
      if i == 50.u64 { break }
  }

Unlike error and return, break has no source definition in system.z; it's registered directly by the compiler via its ControlKind dispatcher and re-exported by core under the system. namespace.

26. continue

Compiler-intrinsic. Skips to the next iteration of the enclosing for / do loop. Takes no argument.

  for i: 0.u64 to: 100.u64 loop {
      if (i % 2.u64) == 0.u64 { continue }
      print i
  }

Same registration mechanism as break.
