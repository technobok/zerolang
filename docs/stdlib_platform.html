1. Overview

The declarations themselves live in lib/system/platform.z, which is the one place they are written. Every definition, field, arm, generic parameter and own-line parameter there carries its own doc comment, and zls surfaces each on hover; the corpus runner ratchets that coverage under make ci. This page is the prose and the worked examples -- read it for how the unit is meant to be used, and the source for the exact surface.

The platform unit is what the compiler knows about the build it is performing: the operating system and architecture it is building for, and the C compiler it will hand the emitted C to.

Every member is a compile-time constant. A read is folded while compiling, so it can drive a unit-level if or a require: block, and a branch it decides never reaches the C.

Each is declared as a zero-argument is native function whose path carries the fold attribute in src/runtime/natives.tbl. The out type is the type, and naming the path in that table is the backing: the compiler answers it while type checking and emits nothing. A path with no answer behind it, or an answer with no row, is an error -- which is what keeps these from being values that merely happen to agree with the build.

  require: unit {
      library: if platform.cc == platform.cckind.tcc then {
          error "this unit needs a compiler with __float128"
      } else {
          "quadmath"
      }
  }

Each kind is named for its values rather than for the member that reads it. That is what keeps platform.platform from ever arising: the member is os, its type is oskind, and an arm is platform.oskind.linux.

Members

  • platform.os -- oskind
  • platform.arch -- archkind
  • platform.cc -- cckind
  • platform.ccmode -- ccmodekind
  • platform.target -- StringView

Kinds

  • oskind -- variant { linux: null darwin: null windows: null other: null }
  • archkind -- variant { x86_64: null aarch64: null other: null }
  • cckind -- variant { gcc: null clang: null tcc: null other: null }
  • ccmodekind -- variant { spawn: null inproc: null }

2. oskind

Host operating-system family.

3. archkind

CPU architecture family.

4. cckind

The C compiler zc will hand the emitted C to, classified by the basename of the resolved path -- the same resolution order zc itself uses: --cc, then <target>-gcc, then $CC, then cc.

Classification is by name alone. Probing --version would add a subprocess to every compile, so a --cc pointing at a wrapper script reads as other and a guard keyed on one compiler will not fire for it.

5. ccmodekind

How zc reaches that compiler: spawn runs it as a child process, inproc loads it into this one. Selected with --cc-mode; the default is spawn.

This is a separate axis from cckind on purpose, so platform.cc == platform.cckind.tcc keeps firing whichever way tcc is reached. Naming the in-process path as a compiler of its own would have made every guard already written quietly stop applying to it.

There is no auto, and zc never falls back: the requested mode is always the resolved one. That is what keeps this constant foldable. An auto would have to probe for a loadable library, and platform is read during type checking -- so a program would typecheck differently depending on a machine's shared-library layout, and the editor would disagree with the build.

6. os

The operating-system family being built for.

  if platform.os.linux then { ... }
  if platform.os == platform.oskind.linux then { ... }

Both spellings fold and agree: value.arm is always a predicate, so the first asks whether the constant holds that arm.

7. arch

The CPU architecture family being built for.

8. cc

The C compiler zc will invoke.

This is not os.buildCompiler, which reports the compiler that built the running zc binary. This one is the compiler that zc is about to run.

9. ccmode

How zc will reach that compiler -- see ccmodekind.

10. target

The --target triple, or the empty string for a native build.

Caveat

os and arch come from --target when one is given and from the host otherwise. A cross --cc used without --target therefore leaves them describing the host while the C compiler targets something else.

They are folded from a parse of the triple, not from substring tests: each - separated component is matched whole against the arm names and their aliases, and a triple naming no operating system or two of them is refused at the flag rather than folded. See the cross-compilation section of zc.pdoc for the vocabulary.

zl and zls never see a --target — they resolve the triple as empty — so a require: guard keyed on a cross target fires in zc build and stays silent in the editor.
