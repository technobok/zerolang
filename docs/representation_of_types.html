This document specifies the memory representation and allocation strategy for all types in Zerolang.

Overview

1. Design Principles

  1. Stack by default. Every user-defined type -- record, class, variant, union, protocol instance, facet instance -- lives on the stack. The struct that describes the object is a local variable or a field inside another struct. No malloc / free for the struct itself.
  2. Heap for data buffers only. The only heap allocations are Box (a single object on the heap), List data buffers, String data buffers, and union subtype data. The controlling struct for List and String (length, capacity, pointer) still lives on the stack.
  3. Ownership tied to type class. Valtypes (records, variants) are freely copyable. Reftypes (classes, unions, protocol instances) are single-owner and cannot be copied -- only borrowed or taken.
  4. Flat valtypes. Valtypes may only contain other valtypes as fields. They cannot contain String, List, Box, or any other type that requires heap cleanup. This guarantees that valtypes are always trivially copyable and never need a destructor.
  5. Reftypes may own heap resources. Reftypes (classes, unions, protocol instances) may contain String, List, Box, or other reftype fields. However, a reftype is not required to own heap resources -- a class with only valtype fields is valid. Such a class still has identity and single-owner semantics but needs no destructor.
  6. Locks live on reftypes. The non-owned field mechanism is available to reftypes (classes) only. Valtypes (records, variants) cannot hold locks.

The container rows cover both element families: ListRef / ListVal, SetRef / SetVal, the four Map forms and the two IdMap forms share one C shape per kind -- the families differ in what the element slots hold (owned reftype pointers vs inline valtype values) and in the accessor/iterator surface, not in the container struct itself.

Map and Set are the one heap-allocated container: create returns a pointer, so a map-typed field holds a pointer the owner destroys rather than storage the owner contains. IdMap / IdSet are stack structs like List, which is what lets an empty one cost no allocation at all.

Note: "enum" is not a separate type. Enums are variants or unions where every subtype is null -- the struct collapses to just a tag discriminator.

3. Method Receiver (this)

For all type instances with methods, this is always passed as a pointer at the C level -- T* for a mutable (.borrow) receiver, const T* for a readonly (.view) receiver. This applies to records, classes, unions, and any other type with methods. The pointer convention ensures:

  • Methods can mutate fields and have those mutations persist across calls.
  • Method bodies work identically for stack-allocated and boxed instances -- Box(T) is already a pointer, so calling a method on a boxed value passes the pointer directly without &.

At call sites, the emitter generates &var to pass the address of a stack variable to a method:

/* zerolang: counter.increment c */
z_counter_increment(&zv_c);

Type Specifications

4. Records (Valtypes)

Records are product value types. They are stack-allocated, freely copyable, and never need a destructor.

4.1. Memory Layout

A record is a C struct with all fields inline:

typedef struct {
    int64_t x;
    int64_t y;
} z_point_t;

4.2. Field Restrictions

Record fields must be valtypes: numeric types, bools, other records, variants, function references. Records cannot contain String, List, Box, Map, classes, unions, or any type that requires heap cleanup. This restriction is enforced by the type checker.

Records cannot have non-owned fields. Locks require identity (single-owner semantics) which valtypes do not have.

4.3. Construction

meta.create returns the struct by value:

static z_point_t z_point_meta_create(int64_t x, int64_t y) {
    z_point_t _this = {0};
    _this.x = x;
    _this.y = y;
    return _this;
}

4.4. Ownership

Records are freely copied on assignment and passed by value to functions. Each copy is independent. When a record falls out of scope it is simply forgotten -- no destructor runs.

5. Variants (Valtypes)

Variants are sum value types (tagged unions). They are stack-allocated with inline subtype data, freely copyable, and never need a destructor.

5.1. Memory Layout

A variant uses an inline C union sized to the largest subtype:

typedef enum {
    Z_SHAPE_TAG_CIRCLE,
    Z_SHAPE_TAG_RECT,
} z_shape_tag_t;

typedef struct {
    z_shape_tag_t tag;
    union {
        double circle;            /* radius */
        z_rect_t rect;            /* inline record */
    } data;
} z_shape_t;

The tag enumerators are spelled from ids, as type names are: the type's id and the arm's position among the arms (Z_T42_TAG_0), so two arms whose names differ only in case, or two sums of one name in different units, never share one. The readable-names emitter mode appends the type's and the arm's names (Z_T42_TAG_0_shape_circle); the samples here keep the shorter illustrative spelling.

Members are spelled the same way. A member of a struct the compiler generates -- a record's or class's field, a variant's arm in data, a union's inline arm slot, a protocol's or facet's vtable slot, a constructor's parameter -- is named by a letter for its family and its position among the type's members of that family: f0, a1, i0, s2, p0. No source name is part of it, so no member can collide with a C keyword, a libc macro (errno, st_mtime) or another member, and the readable-names mode appends the source name after the ordinal (a0_circle). Here, too, the samples keep the source spelling. The runtime's own layouts (String, List and the other is native types) keep their members' names: they are the runtime's C, not generated.

The struct size is sizeof(tag) + sizeof(largest subtype). For enum-pattern variants (all subtypes are null), the union is omitted entirely and the struct is just { tag }.

5.2. Field Restrictions

Variant subtypes must be valtypes. They cannot contain String, List, Box, classes, unions, or any type requiring heap cleanup. This ensures variants are trivially copyable and need no destructor.

5.3. Ownership

Variants are freely copied (struct copy captures tag + active data). No destructor is needed. When a variant falls out of scope, it is forgotten.

6. Classes (Reftypes)

Classes are product reference types. They are stack-allocated. They have single-owner semantics: they cannot be copied, only borrowed or taken.

6.1. Memory Layout

A class is a C struct with all fields inline, stored on the stack:

typedef struct {
    z_string_t label;    /* string struct (stack), data buffer (heap) */
    int64_t value;
} z_named_t;

There is no malloc for the struct itself. The struct lives in the stack frame of the declaring scope.

6.2. Field Types

Classes may contain any field type: valtypes, other reftypes, String, List, Box, and Map. A class is not required to have heap-backed fields -- a class with only valtype fields is valid. Such a class still has identity and single-owner semantics (cannot be copied) but needs no destructor.

6.3. Construction

meta.create returns the struct by value (not a pointer):

static z_named_t z_named_meta_create(z_string_t label, int64_t value) {
    z_named_t _this = {0};
    _this.label = label;
    _this.value = value;
    return _this;
}

At the call site, the class variable is a stack local:

z_named_t n = z_named_create(z_string_new("test"), 42);

6.4. Destructor

A class destructor is emitted only if the class has fields that require cleanup (string, list, box, map, or other reftypes with destructors). The destructor cleans up those fields but does not free the struct itself:

static void z_named_destroy(z_named_t* p) {
    if (!p) return;
    z_string_free(&p->label);   /* free string data buffer */
    /* NO free(p) -- struct is on the stack */
}

If a class has no heap-backed fields (only valtypes), no destructor is emitted and the variable is not added to the scope cleanup list.

6.5. Ownership Transfer (.take)

Taking a class copies the struct (C struct assignment) and zero-initialises the source. Zero-initialisation sets all pointer fields to NULL, preventing double-free when the source's scope cleanup runs:

z_named_t d = zv_c;                         /* struct copy */
zv_c = (z_named_t){0};                      /* invalidate source */

6.6. Re-pointing a borrow

A borrowed local is a pointer to its source, aliased to its deref ((*__borrow_b)); a borrowed parameter is the pointer itself. A reassignment of a borrow stores a new address and frees nothing:

__borrow_zv_b = &zv_d;                      /* b = d */

A borrow re-pointed at an owned value refers to its COMPANION, an owned local declared empty beside the borrow and destroyed with the borrow's scope. The value runs first, the companion's old value is freed, and the borrow takes the companion's address:

z_named_t zv_c = (z_named_t){0};            /* declared with b */
...
z_named_t _rr0 = z_named_create(...);       /* b = Named ... */
z_named_destroy(&zv_c);
zv_c = _rr0;
__borrow_zv_b = &zv_c;

A borrow held by value -- a view, a borrowed protocol box, a map's own pointer -- is stored whole instead.

6.7. .drop

.drop calls the destructor (if present) and zero-initialises the struct:

z_named_destroy(&zv_n);
zv_n = (z_named_t){0};

6.8. Scope Cleanup

When an owned class variable falls out of scope, the destructor is called (if the type has one). The cleanup code passes &var to the destructor:

z_named_destroy(&zv_n);

6.9. Function Returns

Functions returning a class return the struct by value. C compilers apply NRVO (Named Return Value Optimisation) in practice, avoiding unnecessary copies.

6.10. Parameter Passing

Borrow parameters receive a pointer (the caller passes &var); view parameters receive a const pointer. Take parameters receive the struct by value (the caller copies the struct and zero-initialises its source); .hold is take with a readonly binding, and an outx declaration marks a return that pins its non-owned arguments.

6.11. Swap

Swapping two class variables swaps the entire struct:

{
    z_named_t _tmp = zv_a;
    zv_a = zv_b;
    zv_b = _tmp;
}

6.12. Non-Owned Fields on Classes

Classes may have non-owned fields. A class with non-owned fields:

  • Holds compile-time locks on the targets of its non-owned fields for the lifetime of the class instance.
  • Cannot be stored as a field of another type (prevents the lock from outliving its target).
  • Can be moved via .take -- ownership and locks transfer to the new name.
  • Can be passed to .borrow and non-owned parameters.
  • When the instance falls out of scope, locks are released (and the destructor runs if present).

Classes with non-owned fields are normal owned instances. A class cannot be duplicated, so no two copies can hold the same lock.

Non-owned fields are immutable after construction.

7. Unions (Reftypes)

Unions are sum reference types. The struct itself is stack-allocated; a payload lives in a heap cell its void* slot points at, or -- for an inline arm -- in the slot itself.

7.1. Memory Layout

A union is a tag and an 8-byte slot on every target -- 16 bytes on a 64-bit one. The tag is stored in the type the declaration asks for (as { tag: u16.tag }), and in a uint8_t when it asks for none; a C enum beside the struct names its values. The C backend spells the slot a void*. A union with an inline arm overlays it with each inline arm's own member, in an anonymous union, and asserts that each one fits:

typedef enum {
    Z_RESULT_TAG_OK,
    Z_RESULT_TAG_ERR,
} z_result_tag_t;

typedef struct {
    uint8_t tag;
    union {
        void* data;      /* the heap cell of a cell arm (`err: String`) */
        int64_t i0;      /* the inline arm `ok: i64` */
    };
} z_result_t;
_Static_assert(sizeof(int64_t) <= 8 && _Alignof(int64_t) <= 8, "union arm payload wider than its 8-byte slot");

A union with no inline arm has the bare void* data member in place of the anonymous union. The struct is 16 bytes on the stack whatever its arms hold.

7.2. Subtype Data

A union's arm layout is what its declaration writes: a null arm carries no payload, a marked arm (.view / .borrow / .hold) is reference-family whatever it points at, and the rest are:

  • A bare valtype arm that fits the slot (size and alignment no wider than a pointer): the value itself, in its member of the slot. No allocation, nothing to free. A wider one is a compile error that hints (Box T).
  • A (Box T) valtype arm, or a Box type argument: a heap cell holding a copy of the value; the Box collapses to the element.
  • A reftype arm (classes, strings and the rest): a heap cell the value is moved into, invalidating the source.
  • For null subtypes: data is NULL.

Because union subtypes can be reftypes, a union may indirectly contain String, List, Box, and other heap-backed fields within its subtypes.

7.3. Destructor

The destructor switches on the tag, cleans up the active arm and frees its heap cell, but does not free the union struct. A union whose slot is null holds nothing to free:

static void z_result_destroy(z_result_t* u) {
    if (!u) return;
    if (!u->data) return;
    switch (u->tag) {
        case Z_RESULT_TAG_ERR:
            z_string_free((z_string_t*)u->data);
            free(u->data);
            break;
        default: break;
    }
}

An inline arm and a null arm have no case: there is nothing to free.

7.4. Construction

Construction is a compound literal. A cell arm's value is copied into a new heap cell (z_xmemdup); an inline arm's value is stored in its member of the slot, with no allocation:

z_result_t e = ((z_result_t){ .tag = Z_RESULT_TAG_ERR, .data = z_xmemdup((z_string_t[1]){ s }, sizeof(z_string_t)) });
z_result_t r = ((z_result_t){ .tag = Z_RESULT_TAG_OK, .i0 = 42 });

A null arm leaves data null.

7.5. Match / Case

A match switches on the tag. In each case the subject's name reads the arm's payload: a cell arm's through the cast slot, an inline arm's from its member:

switch (r.tag) {
    case Z_RESULT_TAG_OK: {
        /* r reads r.i0 */
        ...
        break;
    }
    case Z_RESULT_TAG_ERR: {
        /* r reads (*(z_string_t*)r.data) */
        ...
        break;
    }
    default: break;
}

8. Protocol Instances

Protocol instances are existential type wrappers. The wrapper struct is stack-allocated. The wrapped data may be a borrowed pointer or an owned heap copy.

8.1. Memory Layout

typedef struct {
    void (*method1)(void*, ...);
    void (*method2)(void*, ...);
    ...
} z_printable_vtable_t;

typedef struct {
    void* data;                       /* pointer to implementation */
    z_printable_vtable_t* vtable;     /* pointer to static vtable */
    void (*destroy)(void*);           /* destructor (NULL if borrowed) */
} z_printable_t;

The protocol struct (3 pointers = 24 bytes) is on the stack.

8.2. Borrowed vs Owned

  • Borrowed (Proto obj, Proto obj.borrow, or the implementation's label, obj.reader): data points to the source variable (via &var). destroy is NULL. The protocol instance does not own the data.
  • Owned (Proto obj.take, Proto.create from: obj.take, or an unmarked source handed to a place that owns it): data points to a heap-allocated copy of the implementation. destroy is set to a cleanup function that frees the copy. For reftype implementations, the cleanup function calls the implementation's destructor before freeing.

8.3. Destructor

The protocol destructor calls destroy if set, then does not free the protocol struct (it is on the stack):

static void z_printable_destroy(z_printable_t* p) {
    if (!p) return;
    if (p->destroy) p->destroy(p->data);
    /* NO free(p) -- struct is on the stack */
}

Since the wrapped data may be a reftype that contains String, List, Box, etc., protocol instances may indirectly own heap resources.

9. Facet Instances

Facet instances are value-type existential wrappers. They are stack-allocated with inline data and are freely copyable.

9.1. Memory Layout

typedef union {
    z_impl1_t _impl1;
    z_impl2_t _impl2;
} z_iterable_data_u;

typedef struct {
    z_iterable_vtable_t* vtable;      /* pointer to static vtable */
    z_iterable_data_u data;            /* inline data union */
} z_iterable_t;

The data is stored inline (not via pointer). The facet struct size is sizeof(vtable pointer) + sizeof(largest implementing type).

9.2. Restrictions

Because facets are valtypes, their implementations must be valtypes (records, variants). They cannot wrap reftypes (classes, unions) and therefore cannot indirectly contain String, List, Box, or other heap-backed fields. No destructor is needed.

10. box(T)

Box is a generic type that heap-allocates a single instance of a valtype (its bound is anyval.generic; a reftype is already a heap pointer). The C representation is a bare pointer to the inner type. As a union arm or union type argument, (Box T) collapses to the element and the arm is a heap cell -- see the union section.

10.1. Memory Layout

For Box(point) where point is { i64 x, i64 y }:

z_point_t* b;    /* points at a heap-allocated z_point_t */

10.2. Transparency

Boxed items support all field and method access directly. The compiler handles the indirection. There is no automatic unboxing: passing a boxed item to a function requires the function to accept exactly that boxed type.

Since this is always a pointer in methods, all method bodies work on both boxed (heap pointer) and unboxed (stack, via &var) instances without modification.

10.3. Destructor

The box destructor frees the heap allocation. A boxed element is a valtype, and valtypes own no heap, so the destructor is free(v):

static void z_Box_pt_destroy(void* v) {
    if (!v) return;
    free(v);               /* free the box allocation */
}

10.4. Construction

A box is made from its value: Box from: v, or through an instance of Box -- an alias of one (BP from: v with BP: (Box point)) or its own spelling ((Box point) from: v). The value must be of the instance's element type. The compiler allocates the cell and copies the value into it where the box is built:

z_point_t* b = (_Box0 = (z_point_t*)z_xmalloc(sizeof(z_point_t)), *_Box0 = p, _Box0);

The source is a valtype, so it is copied, not consumed -- the standard valtype rule. A box has no empty value: an instance named with no value (b: BP) is refused.

10.5. Swap

Swapping two boxed items of the same type is a pointer swap:

{
    z_point_t* _tmp = zv_a;
    zv_a = zv_b;
    zv_b = _tmp;
}

Swapping a boxed item with an unboxed item of the same underlying type is not supported. This would require a move-in/move-out dance that is error-prone. A program that needs it unboxes and boxes again.

11. list(T)

List (the alias of ListRef; ListVal is the valtype-element twin with the identical layout) is a generic growable array. The struct lives on the stack; only the data buffer is heap-allocated. Emitted C names are id-mangled (z_t1014_t); the readable spellings in this document's samples correspond to the opt-in readable-names emitter mode.

11.1. Memory Layout

typedef struct {
    uint64_t length;
    int64_t* data;        /* heap-allocated data buffer */
    uint64_t capacity;
} z_list_i64_t;

Field order: length first, data second, capacity last. This order is chosen so that the first two fields (length, data) match the ListView layout, enabling zero-cost casting from List* to ListView*. Capacity is last because it is not present in views.

The struct (24 bytes) is on the stack. The data pointer references a heap-allocated buffer sized to capacity * sizeof(element).

11.2. Construction

create returns the struct by value (not a pointer):

static z_list_i64_t z_list_i64_create(uint64_t _capacity) {
    z_list_i64_t _this = {0};
    _this.capacity = _capacity;
    if (_capacity > 0) {
        _this.data = (int64_t*)calloc(_capacity, sizeof(int64_t));
    }
    return _this;
}

11.3. Destructor

The destructor frees the data buffer (and element destructors for reftype elements). It does not free the struct:

static void z_list_i64_destroy(z_list_i64_t* p) {
    if (!p) return;
    free(p->data);
    /* NO free(p) -- struct is on the stack */
}

For reftype elements:

static void z_list_string_destroy(z_list_string_t* p) {
    if (!p) return;
    for (uint64_t i = 0; i < p->length; i++) {
        z_string_free(&p->data[i]);
    }
    free(p->data);
}

11.4. Growth Formula

Unchanged: new_cap = cap + (cap >> 1) + 4 (approximately 1.5x + 4).

11.5. Methods

All methods (append, insert, extend, get, set, pop, grow) take this as a pointer. Call sites pass &var.

11.6. Element Creation

An element is constructed on the stack, and append copies it into the data buffer. The copy costs as much as the element's size.

12. listView(T)

ListView (and ListViewVal, its valtype-element twin) is a generic window into a list. It is a class (single ownership) whose production pins the parent list SHARED. It is read-only: get is its only element accessor. Writing an element in place is the owner's job (ListRef.getMut, set, iterateMut), and a view cannot change the sequence either.

12.1. Memory Layout

typedef struct {
    uint64_t length;
    int64_t* data;        /* pointer into parent list's data buffer */
} z_listview_i64_t;

Field order matches the first two fields of List: length first, data second. This enables zero-cost casting from a z_list_i64_t* to a z_listview_i64_t* -- the memory is reinterpreted without copying.

A slice from: to: reaches the same layout by arithmetic rather than by cast: length becomes to - from and data advances by from elements. The emitted C is one compound literal behind a bounds check, so a sub-range costs two registers and no allocation.

12.2. Ownership

Listview is a class (reftype): single ownership, cannot be copied. It holds a .view on the source list, preventing mutation of the list while the view exists; other readers stay legal. When the listView falls out of scope, the lock is released.

Listview does not need a destructor (no heap allocations of its own). The data it points to is owned by the parent list.

12.3. Locking

The listView holds a compile-time lock on the source list:

nums: ListVal i64
nums.append from: 10
nums.append from: 20
nums.append from: 30
v: nums.listView           # v locks nums
print "\{v.get i: 0}"      # OK: read through view
# nums.append from: 40     # ERROR: nums is locked by v
# when v falls out of scope, nums is unlocked

12.4. Methods

  • get(i: u64) -- bounds-checked readonly access (T.view on ListView, a copy on ListViewVal)
  • slice(from: u64, to: u64) -- a narrower window over the same storage; offsets are this view's, and it pins this view, so the list stays pinned while the narrower window lives
  • length() out u64 -- number of elements in the view

12.5. Zerolang Definition

ListView: class is native as {
    T: AnyRef.generic

    get: function {t: this.view i: u64} outx T.view is native
    slice: function {t: this.view from: u64 to: u64} outx type is native
    length: function {t: this.view} out u64 is native
}

13. map(K,V) / set(T)

Map (the four key/value families MapRR / MapRV / MapVR / MapVV) and Set (SetRef / SetVal) are compact dictionaries: a dense, insertion-ordered entry array plus a sparse index table of positions into it. Iteration order is therefore insertion order and is stable across runs regardless of the hash seed.

They are the one heap-allocated container: create returns a pointer. A map-typed field holds a pointer the owner destroys, not storage the owner contains -- which is why a map field can be read through a readonly receiver where a stack-struct container's cannot.

13.1. Memory Layout

typedef struct {
    uint8_t  alive;        /* 0 once removed: a tombstone */
    uint64_t hash;         /* stored, so a probe compares before calling ==  */
    K        key;
    V        value;
} z_map_entry_t;

typedef struct z_map_t {
    uint64_t capacity;     /* indices slots, a power of two */
    uint64_t length;       /* LIVE entries */
    uint64_t entries_len;  /* entries[] high-water mark: live + tombstones */
    uint64_t entries_cap;  /* entries[] allocation */
    int64_t* indices;      /* EMPTY(-1) / DELETED(-2) / entry position */
    z_map_entry_t* entries;
} z_map_t;

A set is the same shape without the value column. length and entries_len differ only because removal leaves a hole: length counts live entries, entries_len counts slots used.

13.2. Construction

create returns a z_map_t*. A capacity under 8 is rounded to zero and allocates neither array; the header itself is always allocated.

13.3. Destructor

Frees indices, frees entries (running the element destructors for owning key/value families first), then frees the struct.

13.4. Growth Formula

The index doubles when ((entries_len + 1) * 3) >= (capacity * 2) -- a 2/3 load factor. Growth compacts: tombstones are dropped and the surviving entries are re-slotted, which is what reclaims them.

13.5. Probing

hash & (capacity - 1), then linear. The stored hash is compared before the key so a full comparison runs only on a hash match. Integer keys hash through z_hash_u64 (the splitmix64 finalizer); strings and byte-range keys through SipHash, or a faster non-cryptographic mixer under --fast-hash.

13.6. Methods

get / getMut / set / has / remove / length / capacity / iterate / iterateItems / create. getMut hands back a pointer to the entry's value; the key, whose hash decides the slot, is never reachable through it, so no write through it can leave the entry in the wrong bucket.

14. idmap(K,V) / idset(T)

IdMap (IdMapR / IdMapV) and IdSet are the append-only, id-keyed siblings. The key is bound to an unsigned scalar by idkey (u8 / u16 / u32 / u64 / c8 / c32, and any typedef over one of them), and there is no remove and no delete: the whole table is freed at once.

Three properties follow from that contract, and none is available to a Map. Nothing is ever removed, so entries[0 .. length-1] are all live and the array has no holes. The slot is computed from the key alone, so no hash column is stored. And the struct lives on the stack, like a List, so an empty one costs no allocation at all.

14.1. Memory Layout

typedef struct {
    K key;
    V value;
} z_idmap_entry_t;

typedef struct z_idmap_t {
    uint32_t  length;      /* live entries; ALSO slots used, ALSO next index */
    uint32_t  capacity;    /* indices slots, a power of two */
    uint32_t* indices;     /* pos + 1, with 0 for empty; NULL in small mode */
    z_idmap_entry_t* entries;
} z_idmap_t;

24 bytes, the same as a List. An id set is the same shape with a bare items array in place of entries.

One counter does three jobs -- live count, slots used, and the next insertion index -- because there are no holes to tell those numbers apart. indices is uint32_t holding pos + 1 so that zero means empty; with no removal there is no DELETED sentinel to distinguish, which is what allows the narrower cell.

14.2. Small Mode

Below an index size of 16 no indices array is allocated at all and lookup scans the dense entries instead. indices == NULL is the discriminator, so the indexed path pays no extra branch -- it replaces the capacity == 0 early return a Map's find already had.

The ceiling is on capacity, which is always a power of two, so the constant has four reachable settings and no others: 8, 16, 32 and 64, admitting 5, 10, 21 and 42 entries. 16 is the measured optimum -- 8 is marginally worse and 32 and 64 cost 1.4% and 3.0% of the compiler's instructions to save 0.3% and 0.6% of its bytes. This is the one constant in the container that cannot be chosen from the allocation column, which improves monotonically as it rises. The scan stays competitive further than the usual advice about lists and maps suggests, because that advice is about a hashed map with an owned key and this scan is == over raw scalars with no hash and no allocation.

Because this crossing is inside the container, a caller never writes one: a reader asks one field, and the threshold test is written once.

14.3. Construction

create returns the struct by value. An empty one allocates nothing: no header, no index, no entries.

14.4. Destructor

Frees indices and entries (running the value destructors for the reference family first) and does not free the struct -- it is on the stack, exactly as List is.

14.5. Growth Formula

entries is sized at capacity * 2 / 3, which is also the index's load factor, so "entries is full" and "the index must grow" are one event and no separate entries_cap field is needed. The test carries no division: cross-multiplied it is ((length + 1) * 3) >= (capacity * 2), the same growth point a Map reaches. Growth doubles the index and re-slots; there is nothing to compact, because entries never has holes.

14.6. Indexing

(key * 0x9E3779B97F4A7C15) >> 32, masked by capacity - 1.

Identity (key & mask) was measured and rejected. It is optimal for a dense run of ids -- one table's worst probe fell from 74 to 1 -- but a table holding a sparse subset of a wide id space folds unrelated groups onto each other, because the mask keeps only the low bits: over a self-compile identity cost +77% probe steps and took the worst run from 74 to 749. The golden-ratio multiply-shift costs one imul plus one shift and beat the splitmix64 finalizer it replaces on both total steps and tail. The shift is not optional: bit i of a product depends only on bits 0..i of the operands, so a multiply's low bits -- exactly the ones the mask reads -- are barely mixed, while the high half carries every input bit.

14.7. Methods

get / getMut / set / has / keyAt / valueAt / length / capacity / create, plus iterate on a set and iterateItems on a map. No remove and no delete -- if you need either, you want a Map.

getMut is a Map's: a writable reference to the value, which the slot does not depend on. It earns its place on the value family, whose get returns an optionval -- a copy -- so an update would otherwise have to read the value out, change it and set it back. Both forms declare it and share one emitted function, exactly as ListRef.get (a view) and ListVal.get (a copy) already share one getMut; what differs is the declared return.

The ordinary borrow rules still apply: two live views of one container conflict, so a getMut result and a later lookup want separate scopes.

keyAt and valueAt read by position rather than by key. Position is a coordinate here in a way it is not in a Map: entries is dense and insertion-ordered, so slot i is a plain array index and nothing can perforate the sequence. They exist for the walk an iterator cannot serve -- one whose body has to reach the object that OWNS the container, which an outstanding iterator borrow forbids for the whole loop. keyAt answers a bare key, because the idkey bound makes one a scalar and 0 past the end is the "no id" every id space already spells; valueAt answers exactly what get answers, because a value is neither always a scalar nor always a copy.

15. list

A static list's name, as a value, is a view of the list's static array:

  typedef struct z_list_u8_t {
      uint64_t length;
      const uint8_t* data;
  } z_list_u8_t;

16 bytes on the stack, copied by value. data points at the list's static const array, which the program carries once the list is indexed at run time or used as a value; nothing is allocated, freed or locked. get is a function of the mono that checks the bound and panics past it, and iterate hands the window to the StaticIter cursor, whose call yields a StaticView of the element.

16. string

String is a growable UTF-8 byte buffer. The struct lives on the stack; only the data buffer is heap-allocated.

16.1. Memory Layout

typedef struct {
    uint64_t size;          /* byte count of current content */
    char* data;             /* heap-allocated data buffer */
    uint64_t capacity;      /* allocated buffer size */
} z_string_t;

Field order: size first, data second, capacity last. This matches the field order of List (length, data, capacity) for consistency. The first two fields (size, data) match StringView layout, enabling zero-cost casting.

The struct (24 bytes) is on the stack. The data pointer references a heap-allocated buffer. Strings are null-terminated (for C interop) but size tracks the actual content length.

16.2. Construction

static z_string_t z_string_new(const char* s) {
    z_string_t str = {0};
    if (s) {
        str.size = strlen(s);
        str.capacity = str.size + 1;
        str.data = (char*)malloc(str.capacity);
        memcpy(str.data, s, str.capacity);  /* includes null terminator */
    }
    return str;
}

16.3. Destructor

Frees the data buffer only:

static void z_string_free(z_string_t* s) {
    if (s && s->data) free(s->data);
}

16.4. Growth Formula

Unchanged: new_cap = cap + (cap >> 1) + 16 (approximately 1.5x + 16).

17. stringView

StringView is a class: a read-only view into a String, with single-owner semantics and a .borrow on the source string.

17.1. Memory Layout

typedef struct {
    uint64_t size;          /* byte count of the viewed region */
    const char* data;       /* pointer into string's data buffer */
} z_stringview_t;

Field order: size first, data second. This matches the first two fields of String in order, name and type, enabling zero-cost casting from z_string_t* to z_stringview_t*.

17.2. Ownership

Stringview is a class (reftype): single ownership, cannot be copied. It holds a .borrow on the source string (when created from a string variable). Stringviews created from string literals point into static .rodata and do not lock anything (static data has infinite lifetime).

Stringview has no destructor (no heap allocations).

17.3. Methods

  • length -- the byte count, a u64
  • string -- an owned String copy of the viewed bytes
  • == and != -- content comparison

The full list is in the system unit's reference.
