1. Overview

The declarations themselves live in lib/system/tokenize.z, which is the one place they are written. Every definition, field, arm, generic parameter and own-line parameter there carries its own doc comment, and zls surfaces each on hover; the corpus runner ratchets that coverage under make ci. This page is the prose and the worked examples -- read it for how the unit is meant to be used, and the source for the exact surface.

The tokenize unit exposes the compiler's own lexer as a public API -- the analogue of Python's tokenize module. It turns zerolang source text into a stream of Token values classified by a toktype tag. The stream is lossless: it includes the whitespace, comment, and end-of-line trivia tokens the parser discards, so a formatter or source-rewriter can reconstruct exact layout.

Stability: preview. This surface ships alongside the zl linter/formatter and may change. It is a thin re-export of the compiler front-end (lib/system/zlexer.z); the raw zlexer.Tokenizer carries additional internal state.

Accessed via qualified names only -- tokenize.scan ..., tokenize.Tokenizer.create ....

3. tokenizer

The raw scanner. create takes ownership of the source string and a file number fsno (used only to stamp emitted tokens for diagnostics -- pass the zero value zvfs.fsno for a standalone buffer). Each call to token returns the next Token, including wsTok / commentTok / eolTok trivia, terminated by an eofTok token that repeats if called again.

  tk: tokenize.Tokenizer.create source: src.copy fsno: zvfs.fsno
  for true loop {
      t: tk.token
      match (
          t.toktype
      ) case eofTok then {
          break
      } else null
      # ... inspect t ...
  }

Most callers want scan (below) rather than driving the tokenizer by hand.

4. token

One lexical token. toktype is its toktype classification; text is its spelling INTERNED in the pool the scan was given, and zast.poolTextAt reads it back -- for a wsTok that is the run of spaces, for a commentTok the comment text. A token carries an id rather than its own copy because nearly every spelling in a source file has been seen before, and the pool copies only on first sight. lineno / colno are 1-based, and width is the token's byte count, which is what a diagnostic underlines.

5. tt

toktype is a variant with one arm per token kind. Trivia arms wsTok, commentTok, and eolTok carry the between-token layout; eofTok terminates the stream. The remaining arms classify keywords, identifiers, literals, and punctuation. Match on it to dispatch:

  match (
      t.toktype
  ) case wsTok then {
      null
  } case commentTok then {
      null
  } case eofTok then {
      done = true
  } else null

6. scan

Tokenize source into its full raw token stream -- whitespace, comments, and EOL trivia included -- terminated by the eofTok token. The one-call convenience over Tokenizer.

The pool outlives the scan, so the caller owns it and reads spellings back from it afterwards.

  pool: tokenize.StringPool.create
  toks: tokenize.scan source: src.copy :pool
  print "tokens: \{toks.length}"
