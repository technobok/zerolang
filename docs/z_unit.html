1. Overview

z is the unit that says what a build is. The compiler writes it, before the build begins, from the values the build uses after every flag: the target, the unit, the switches. A program reads them as ordinary constants of an ordinary unit:

  main: function is {
      if z.build.os.linux then print "on linux"
      print "built as \{z.build.main} for \{z.build.triple}"
  }

There is no answer machinery behind it and nothing native about it: the values are constants written into a file, so a unit-level if and a require: block fold on them like on any other constant, and a branch they decide never reaches the C.

  require: unit {
      library: if z.build.os == z.build.oskind.windows then {
          "ws2_32"
      } else {
          ""
      }
  }

2. Where it lives

The files are generated into the compiler's own folder, .zerolang/, which sits beside a project's project.z (see zc.pdoc). Outside a project it is a folder of the user's cache directory ($XDG_CACHE_HOME/zerolang/, else ~/.cache/zerolang/), so nothing is ever written beside a lone source file. Each target has a folder of its own, so builds for several targets sit side by side:

  .zerolang/
    .gitignore                    -- `*`: the folder is disposable
    targets/x86_64-linux/
      z.z                         -- publishes `build` and `project`
      z/build.z                   -- the build's values

z/project.z is not a file of that folder: the project's own project.z is mounted there, alone, so z.project.main is the main the project file sets. A file is rewritten only when its text changes, and the build reads the text it generated, not the copy on disk, so two builds running at once never read each other's values.

The generated layer is bound between the source roots and the stdlib: a project's own unit named z shadows it, exactly as a user unit shadows the stdlib's.

3. z.build

  • os -- the operating system the build is for, an oskind
  • arch -- the architecture the build is for, an archkind
  • triple -- the --target triple as given (or the project's target), else the host's, as <arch>-<os>
  • main -- the unit the build compiles
  • sourceDirs -- the source roots, the first searched first, each relative to the project directory ("" for one outside it): a stringdata
  • outputDir -- where the executable goes when -o names none
  • release, fastHash, readableNames, eager -- the switches, true or false
  • zcVersion -- the version of zc that wrote the file
  • oskind -- variant { linux: null darwin: null windows: null other: null }
  • archkind -- variant { x86_64: null aarch64: null other: null }

value.arm is always a predicate, so z.build.os.linux and z.build.os == z.build.oskind.linux fold alike.

No value names an absolute path: a path is relative to the project directory, so the file has the same shape on every machine. The header comment lays out where each root of the build comes from, and names the C toolchain the build used -- in the comment only. The toolchain is the C backend's business, and no constant a program can read names it.

Caveat

os and arch come from --target (or the project's target) when one is given and from the host otherwise. A cross --cc used without --target therefore leaves them describing the host while the C compiler targets something else.

The triple is parsed, not substring-matched: each - separated component is matched whole against the arm names and their aliases, and a triple naming no operating system or two of them is refused at the flag. See the cross-compilation section of zc.pdoc for the vocabulary.

4. z.project

The project's own project.z, when there is one: z.project.sourceDirs, z.project.main, and every other setting the file gives, as written. A setting the file leaves out is not a member.
