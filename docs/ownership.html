This document describes the ownership and pinning model for Zerolang. It covers owned and borrowed variables, pinning and the locks that enforce it, non-owned fields on classes, escape analysis, iterators, protocol instances and the lifetime guarantees the compiler enforces.

1. For Most Code

For most code, ownership works automatically. All function parameters borrow by default -- for valtypes (records, numbers) a borrow is a copy (the original is still valid); for reftypes (classes, unions) a borrow is a reference (the caller still owns it). Return values are owned. The compiler handles this without annotation. A programmer writing normal functions, records and classes rarely needs to think about ownership at all.

The defaults:

  • Pass a record to a function? It is borrowed (copied). The original is still valid.
  • Pass a class to a function? It is borrowed. The function can use it, and the caller still owns it.
  • Return a new object? It is owned by the caller.
  • Variable falls out of scope? Classes are destroyed. Records are forgotten.

Top-level data items never fall out of scope and are never locked -- they are immutable and freely shared across the whole program.

The advanced concepts below -- non-owned fields on classes, escape analysis -- are needed only when writing iterators, views, or other types that hold references to external data. Most code never needs them. When ownership rules are violated, the compiler provides specific error messages with hints suggesting how to fix the problem.

2. Ownership Overview

Every variable in Zerolang has an ownership state tracked by the compiler at compile time. Two axes -- owned vs borrowed, and writable vs readonly -- give the four markers (.take / .hold on the owned side, .borrow / .view on the borrowed side). On the ownership axis there are exactly two states:

  • owned (taken) -- the variable owns its value. It is responsible for the value's lifetime. When the variable falls out of scope the value is destroyed (for reftypes) or forgotten (for valtypes). An owned variable has full permission: it may be stored, swapped, passed to any parameter type, returned, or explicitly destroyed.
  • borrowed -- the variable has temporary access to a value it does not own. It cannot copy, take, store, swap, or destroy the value. It can call methods on it, read and write fields, and pass it to other .borrow parameters. When the borrowed variable falls out of scope the borrow ends: the reference is simply forgotten without destruction, and any locks held by this variable are released.

Ownership forms a permission hierarchy on its axis: take > borrow (and readable-only .view / .hold are the readonly counterparts on the second axis). An owned variable can always be used in a context that expects a borrow (automatic downgrade). A borrowed variable can never be used in a context that expects a take (error: insufficient permission).

this within object methods is always borrowed.

2.1. Valtypes and Reftypes

There are two major families of types with different runtime behaviour (although the ownership model is uniform: all parameters default to .borrow).

Value types (valtypes) are freely copyable. The primitives are the numeric types; the user defined compound value types are record (product value type) and variant (sum value type). Each copy is an independently owned value. Record fields are restricted to pure value data -- a record cannot contain String, List, Box, Map, or any other heap-backed type.

Function references are also valtypes. A function reference is a small, copyable pointer to immutable program text. Using .take on a function name produces a copy of the address -- no invalidation occurs because definitions are immutable. Function references can be freely copied and reassigned without ownership concerns.

Reference types (reftypes) are interacted with via a reference. The user defined compound reference types are class (product reference type) and union (sum reference type). Reftypes are single-owner: they cannot be copied. Only one variable owns a reftype instance at a time; any additional variables that refer to it are borrowed.

All user-defined types -- records, classes, variants, unions, protocol instances and facet instances -- are allocated on the stack. Only Box and the backing buffers of String, List and similar containers live on the heap. A class lives inline on the stack, but copying is disallowed: the single stack slot for a class is its identity.

2.2. Defaults

All function parameters default to .borrow. Return values default to .take. There is no distinction between valtype and reftype defaults.

ContextValtype defaultReftype default
In parametersborrow (copy)borrow (reference)
Out return valuestaketake

For valtypes, .borrow performs a copy -- the source is NOT invalidated. For reftypes, .borrow passes a reference -- the source is NOT invalidated. .take must be explicitly written on parameter definitions when ownership transfer is intended.

The defaults can be overridden by explicitly specifying .take, .borrow or .view, subject to the restriction that .view is only valid on reftypes and generic type parameters (not on known valtypes).

2.3. Passing Conventions

  • Valtypes are always passed by value (the full value is copied). The exception is this in methods which is passed by reference so that methods can act on the fields in the value directly.
  • Reftypes are always passed by reference (a pointer to the stack slot where the instance lives).

3. Owned Variables

An owned (taken) variable has full permission over its value.

3.1. What an owned variable can do

  • Pass to a .take parameter -- transfers ownership to the callee
  • Pass to a .borrow parameter -- temporary loan, ownership returns after the call
  • Assign to a new name -- transfers ownership to the new name (old name is invalidated for reftypes; for valtypes, a copy is made and both names are valid)
  • Store in a field of an object
  • Swap with another owned variable of the same type
  • Return from a function (as .take or .borrow)
  • Destroy explicitly via .take as an unused expression

3.2. Implicit take

When a variable is passed to an explicitly declared .take parameter, the compiler automatically applies .take at the call site even if the programmer does not write it explicitly. The programmer can write .take explicitly to make the transfer visible in the source. After the call, the variable name is invalidated (for reftypes) or a copy was made (for valtypes). Note that .take must be explicitly written on the parameter definition -- parameters default to .borrow.

3.3. A bare bind is a move

Binding an owned reftype to a new name with no ownership method (q: p) is the same transfer as the reassignment q = p: the new name owns the value, the old one is invalidated, and a later read of it is cannot use 'p' after ownership transfer. The emitted code moves the struct and zeroes the source, so the source's scope-exit destroy is a no-op rather than a second free.

The same rule reaches a match arm's payload: inside case some then the subject name IS the payload, so s: opt moves the payload out of the box and the subject is invalidated for the rest of the scope. Use .copy to keep the subject usable, or read it through a view. (A bare return of that payload is refused, because it would escape the arm's scope while the subject still owns the value.)

3.4. Scope exit

When an owned variable falls out of scope without being consumed:

  • Reftype: the instance is destroyed (destructor called, memory freed)
  • Valtype: the stack value is simply forgotten (no action needed)

4. Borrowed Variables

A borrowed variable has temporary, restricted access to a value it does not own. Both valtypes and reftypes can be borrowed. For reftypes, borrowing passes a reference without transferring ownership. For valtypes, borrowing passes a copy -- the copy is an independent owned value at the C level, but the compiler treats it as borrowed to maintain a uniform ownership model.

4.1. What a borrowed variable can do

  • Call methods on the value (including mutating methods via this)
  • Read and write fields (through the borrowed reference)
  • Pass to a .borrow parameter in a function call
  • Pass to a .borrow parameter in a function call

4.2. What a borrowed variable cannot do

  • Cannot be passed to a .take parameter (error: insufficient permission)
  • Cannot call .take on it (error: cannot take a borrowed variable)
  • Cannot be stored in a field of another object
  • Cannot be swapped
  • Cannot be reassigned -- the name must remain bound to the same borrowed value for its full scope (shadowing in inner scopes is permitted)

4.3. Scope exit

When a borrowed variable falls out of scope:

  • The borrow ends. The reference is forgotten. The underlying object is not destroyed.
  • Any locks held by this variable are released. The locked targets become available for use again.

5. Naming

Instances also have a naming attribute that determines whether they are addressable by the programmer:

  • named -- the object is associated with a name (a label). Named instances include unit-level items, function parameters within the body of the function, and local variables.
  • unnamed -- the object is anonymous. Typically the result of a function call that is not assigned to a label.

Unnamed instances are transient. Unless they are assigned to a name or passed to a .take parameter in a function call, they are destroyed at the end of the current statement.

6. The Ownership Methods

Ownership is two independent axes, not one: who owns the value and may it be written. Crossing them gives the four markers, and every parameter, field and local sits in exactly one cell.

  • .take -- owned and mutable. The callee takes the value from the caller and may do anything with it.
  • .hold -- owned and readonly. Moved in, then frozen: the callee owns it but may only read it.
  • .borrow -- not owned and mutable. A reference the callee may write through; the caller keeps ownership.
  • .view -- not owned and readonly. A reference the callee may only read.

Mutable is the default. An unmarked reftype parameter behaves as .borrow. Readonly is opt-in, which is what makes .view worth writing.

There are no compound specifiers -- a marker names one cell and nothing else.

Returns take .take, .takex, .hold, .borrow or .view. .borrow and .view hand back a reference into the receiver; .takex hands back an owned value that pins its non-owned sources for its own lifetime. .borrowx and .viewx do not exist.

A receiver is #~.borrow" or #~".view", and nothing else." An object cannot own itself, so .take and .hold are meaningless there. A bare :this receiver is .borrow; marking one requires an alias, as in {t: this.view}, because :this.view is not a spelling the language has.

#~.lock" is retired." It was a second name for .borrow plus, on a parameter, the pin that .takex now states on the return. The word still parses to .borrow so existing sources keep their meaning, but it should not be written in new code.

These markers appear in two contexts: as type attributes on function parameters, fields and returns, and as inline methods on runtime instances.

6.1. .take

As a parameter attribute (type.take): the function takes ownership from the caller. The caller must provide an owned variable. The function body may do anything with the value: store, swap, pass on, return, or destroy it. Destruction happens at scope exit if the value is not otherwise consumed.

As a return attribute (out type.take or just out type since take is the default): the function returns a new owned value to the caller.

As an inline method (x.take): takes ownership from the variable x. The name x is invalidated after the call. If the result is not assigned or passed, the instance is destroyed. .take can only be called on an owned variable. Calling .take on a borrowed variable is always an error.

6.1.1. .take in Conditional Arms

If .take is called on a variable with a destructor inside any arm of an if or match, the compiler ensures the variable is consumed in all arms:

  • In arms where the programmer calls .take: ownership transfers normally (the slot is already zeroed).
  • In arms where the programmer does not call .take: the compiler auto-destroys the variable after the block.
  • After the if/match, the variable is invalidated -- using it is a compile error.

If no arm takes the variable, it remains valid after the if/match and no auto-destroy is inserted.

conn: connection.open "db"
if ready then {
    process from: conn.take     # programmer takes ownership
} else {
    log "not ready"             # compiler auto-destroys conn
}
# conn is invalid here

6.1.2. Ownership Transfer Inside Loop Bodies

A for loop body executes zero or more times. Ownership transfer of a variable declared outside the loop is therefore structurally always wrong: after the first iteration the variable is already consumed, so the second iteration would try to transfer an invalid value.

The compiler rejects .take, .drop, .box, or passing an outer-scope variable to a .take parameter inside any reachable point of a for-loop body, with the diagnostic:

cannot transfer ownership of '<name>' inside a loop body
(executes 0+ times; on later iterations '<name>' would already be
consumed)

Variables declared inside the loop body are unaffected: each iteration produces a fresh binding, so taking the local is fine.

a: Crate value: 1
for i: 3.iterate loop {
    a.take              # ERROR: outer-scope variable
    b: Crate value: 2
    c: b.take           # OK: b is body-local
}

The rule fires regardless of whether the alias optimiser would otherwise silently elide the transfer at runtime -- the source intent is rejected at typecheck.

6.2. .borrow

As a parameter attribute (type.borrow or just type since borrow is the default for all parameters): the function borrows the argument. The function body can call methods and access fields but cannot store, take, or destroy the value. Ownership remains with the caller. For valtypes, borrowing means a copy is made -- the source is not invalidated. For reftypes, borrowing means a reference is passed.

As a return attribute (out type.borrow): the function returns a borrowed value. At least one input parameter must be non-owned (.borrow or .view) so the returned value has a locked parent to live in. The returned reference points into the locked parameter's data.

As an inline method (x.borrow): valid on all types. For reftypes, returns a borrowed reference to x and exclusively locks x for the lifetime of the borrowed reference. For valtypes, returns a copy of x without locking (valtypes have no identity to lock). .borrow can be called on either owned or borrowed variables. When locking applies, the lock is placed on the root variable of the path, not on any intermediate field (see Borrow-scoped Locking below).

6.3. .view

As a parameter attribute (type.view): the callee receives a reference it may only read. The caller keeps ownership and, because the pin is shared, keeps reading the argument across the call -- several .view references to one value coexist, where a .borrow excludes everything else.

As a receiver ({t: this.view}): the method is readonly for its whole body. This is not a separate check. The alias holds a shared lock on itself, and the ordinary lock rules then refuse every way of mutating through it: writing a field, calling a mutating method, passing the receiver to a mutable parameter, and the same three through a field of the receiver. A .view method may call other .view methods on the same receiver, because shared locks coexist.

Readonly is deep: a reftype read off a readonly path is itself readonly, so depth does not launder the restriction. A value derived from a readonly reference -- a valtype field read, a comparison, arithmetic -- is a fresh value that aliases nothing and carries no restriction.

6.4. .hold

Owned and readonly: the value is moved in as .take does, then frozen. A hold binding may be rebound only from another owned value (h = y.hold); a plain h = y is an error, and a view never rebinds.

6.5. .takex

A return marker. The result is owned -- it carries a destructor and may be moved -- and the non-owned sources it was built from stay pinned for as long as it lives.

This is the one thing .borrow and .view cannot express. A constructor such as BufWriter.create to: Writer.borrow ... out this.takex hands back an owned value whose sink field is a reference into its argument, so the argument must outlive the result. Without the marker nothing pins it and the field dangles the moment the caller drops the source.

.hold has no x twin: .holdx does not exist, because no construction has yet needed a pinned readonly owned return.

6.6. .copy

An inline method only (not a parameter or return attribute). x.copy produces a fresh, independently-owned duplicate of x. The new value shares no heap data with x; mutating one does not affect the other, and both are freed separately at scope exit.

.copy is the canonical way to break a borrow chain when you need to hand an owned value to a destination that requires ownership (a constructor field, a list/map insert) but only have a borrowed source:

store: function {s: String} out Crate.bag is {
    # `s` is borrowed from the caller; the box wants to own its label,
    # so clone the data into a fresh allocation.
    return Crate label: s.copy
}

Compare with .take (transfer the source's ownership to the destination, invalidating the source) and inline .borrow (alias the source via a lock, no allocation).

6.6.1. Which types have a .copy

Whether x.copy exists depends on the type's family, and it is a deliberate split -- not a gap waiting to be filled.

  • Valtypes (record, variant, facet) have one by default: the byte copy their assignment already performs. A valtype can never contain a reftype, so copying its bytes copies the whole value and the two are independent afterwards. Writing .copy is therefore never required -- it is how a reader says "a duplicate is intended here" rather than "an alias".
  • Reftypes (class, union) have none: the compiler never synthesizes one. A duplicate of a reftype is a design decision -- which fields are cloned, which are shared, what a nested container means -- so the author writes the method. Until one exists, x.copy on such a type is a compile error naming the type.
  • The standard library's are ordinary methods: String.copy and the container copies are declared is native like any other member. They are not a special case in the language.

Both defaults are overridable, and both by the same mechanism -- a copy member in the as block. Member lookup finds it first, so it wins over the valtype default:

Tagged: record {
    n: i64
} as {
    copy: function {t: this} out Tagged is {
        return (Tagged n: t.n + 100)   # the default byte copy is replaced
    }
}

Inner: class {
    n: i64
    label: String
} as {
    copy: function {t: this.view} out Inner is {
        return (Inner n: t.n label: t.label.copy)   # a reftype's only copy
    }
}

A valtype may also strike the default off by defining the member as null, the same way ==: null opts out of synthesized equality. .copy on such a type is then an error, which is what a type that must never be duplicated silently wants:

Handle: record {
    fd: i32
} as {
    copy: null      # duplicating a file descriptor is a bug, not a copy
}

StringView is a view, not an owner: it is copied by assignment, and .string is what allocates an owned String from it.

6.7. .drop

An inline method only (not a parameter or return attribute). x.drop ends the lifetime of variable x immediately, as if it fell out of scope at that point. The name x is invalidated and any subsequent use is a compile error.

  • For owned reftypes (classes, unions, strings): the destructor runs and the pointer is set to NULL (scope-exit cleanup becomes a safe no-op).
  • For owned valtypes (records, enums, integers): just invalidates the name. No destructor call is needed.
  • For borrowed variables (any type): ends the borrow and releases any locks the variable holds on other variables. The source variable becomes unlocked and available again. No destructor is called (the owner is responsible for cleanup).
  • .drop is always a statement, never a value expression.
  • y: x.drop is a compile error.
  • Use .take when you need to transfer the value to a new name.
  • Use .drop when you want to end a lifetime without producing a value.

Error conditions:

  • Cannot drop a variable that has active locks held by another variable.
  • Cannot drop a top-level definition (static lifetime).
  • Cannot use .drop on a non-variable path like x.field.drop.

Example -- early cleanup without nesting:

h: Crate label: "hotel" value: 8
print "h alive: \{h.label}"
h.drop
print "h dropped -- no 'with' nesting needed"

Comparison with .take: both coexist. Standalone x.take continues to work for destroying an owned value. .drop additionally works on borrowed variables (ending the borrow), whereas .take on a borrowed variable is always an error.

7. Ownership on Generic Arguments

Ownership specifiers apply uniformly to every argument position in zerolang, including generic arguments at type-use sites. When you write (Foo of: T.take) or out (Iterator Gives: T.take), the .take is a real ownership annotation -- not silently stripped.

7.1. Default rule

Generic arguments follow the same default-borrow rule as ordinary function parameters: a generic argument with no ownership suffix defaults to .borrow. .take must be explicit.

For valtypes, ownership annotations are no-ops at the physical level: .borrow copies and .take is the same operation, so all three forms (bare, .borrow, .take) behave identically.

7.2. Iterator's gives: and accepts:

Iterator is the canonical generic type that interprets ownership on its generic arguments. The generator desugarer uses the annotation on gives: to select the synthesised .call return wrapper, and the annotation on accepts: to select the resume-input ownership. See the Generator functions section of the language specification for the full table.

accepts: borrow forms (bare and .borrow) install a lock on the caller's value: argument for the duration of each .call. The body's name: yield v binding is a pointer alias into the caller's storage and is valid only for one yield window; using name past the next yield is a compile error. To persist the resumed value across yields, declare accepts: U.take — the synth class then owns the value for the iterator's lifetime.

7.3. Strict consistency for user-defined generic types

When you specify an ownership suffix on a generic argument of a user-defined generic type, the compiler checks that every body-use of that generic parameter has the same effective ownership. The walk inspects each method's parameter and return type. If any use disagrees with the user-specified annotation, the call is a compile error pointing at the suffix and listing the conflicting uses.

# Single-use generic: 'of' appears only in .borrow position
Sink: class { tag: i64 } as {
    of: Any.generic
    inspect: function {item: of.borrow} is { }
}

use_ok: function {s: (Sink of: String.borrow)} is { }
                          # ^ matches Sink.inspect's .borrow — OK

use_err: function {s: (Sink of: String.take)} is { }
                          # ^ conflicts with Sink.inspect's .borrow — error

For heterogeneous-use generics (a type whose generic parameter appears in both .borrow and .take positions inside the body), no annotation passes the check. Users write the bare form and each use site applies its own default. The stdlib List and Map fall into this category -- write (List T: String), not (List T: String.take).

7.4. Aliasing for repeated patterns

When the same ownership-annotated iterator return type appears in multiple generator signatures, give it a unit-level name and reuse the alias. Unit-level instantiation creates a compile-time alias (see the generic-units section of the language specification).

MyIter: (Iterator Gives: String.take)

gen1: function out MyIter is { yield "a".string }
gen2: function {n: i64} out MyIter is { ... }

8. Pinning and Locks

A non-owned binding or argument pins its source: SHARED for readonly views, EXCLUSIVE for mutable borrows. Pinning is an orthogonal compile-time mechanism that prevents aliasing and enforces mutation-safety for outstanding borrows, with zero runtime overhead. The machinery that enforces pins is called locking, and "lock" is the word compiler diagnostics use (e.g. "shared lock held by 'it'"); this chapter uses "pin" for the relationship a view or borrow establishes, and "lock" for the enforcement records the compiler tracks.

The whole model is three rules. Everything below is these worked out in detail; if the detail ever seems to say something else, these win.

  1. Every call pins its receiver -- SHARED for this.view, EXCLUSIVE for this.borrow (and a bare :this is this.borrow). A field write or a swap is the same thing at statement scope. There is no separate rule for mutation: a mutator is simply a call with an exclusive receiver, and no carve-out for readers.
  2. The pin is released on return -- unless the return carries a reference (borrow, view) or pins its sources (takex), in which case it transfers to the binding and lives exactly as long as it does.
  3. Shared and shared coexist. Exclusive coexists with nothing. A holder never conflicts with itself.

This is Rust's discipline applied to references, and it was chosen deliberately over a more permissive alternative that would have needed two concepts and given up both the aliasing guarantee and the "nobody observes a half-built object" guarantee.

Consequences worth stating outright, because they surprise people: an iterator pins its container for its whole lifetime with the strength its receiver declares. iterate is declared on a .view receiver, so it pins SHARED: other readers -- including further iterate walks over the same container -- stay legal while it runs, and only writes are refused. iterateMut and iterateItems are declared on .borrow receivers, so they pin EXCLUSIVELY, refusing everything else: xs.length inside an iterateMut loop is refused; hoist it, or use an index loop, whose element binding dies each iteration. Passing the element out is fine in both cases and must stay so.

Zerolang enforces every pin with one lock primitive, used in two lifetime patterns, which this document refers to as:

  • Call-scoped Locking -- locks held only during a function or method call, used to prevent aliasing between arguments and receiver. Acquired by the call-dispatch machinery; released automatically when the call returns.
  • Borrow-scoped Locking -- locks held for the full scope of a borrowing variable (.borrow, .stringView, .listView, non-owned fields, returned values of .takex and reference-returning functions). Acquired when the borrow is bound; released when the borrowing variable falls out of scope or is explicitly dropped with .drop.

Both use the same EXCLUSIVE/SHARED states and the same storage; they differ only in lifetime and acquisition policy.

8.1. Lock Keys Are Paths

Lock targets are paths, not bare variable names. A lock path is a tuple (root, f1, f2, ..., fn) where root is a bound variable (including this) and f1..fn are addressable descents: field names, labels, or numeric indices. Array indexing extends the path exactly like a field access -- arr.0 and arr.1 are distinct leaves, not a special case. Method calls terminate the path: a method's return value starts a fresh path rooted at the call's result binding. Valtype leaves skip locking (the read is a copy; there is no identity to protect).

8.2. Lock States

Each path can have locks placed on it:

  • unlocked -- no locks held on this path (default)
  • exclusive -- full control over the path and its entire subtree
  • shared -- intent access along the path; other shared locks on overlapping paths are permitted but exclusive acquisition on any overlapping path is not

Conflict rule. Two locks conflict exactly when their paths overlap (one is a non-strict prefix of the other) AND the combination is not permitted by multi-granularity semantics:

  • Same path: conflict iff at least one is exclusive. Two shared locks on the same path dedupe.
  • Strict ancestor/descendant: the ancestor shared is intent shared -- it permits any lock (shared or exclusive) on a descendant. An ancestor exclusive, by contrast, owns the whole subtree and conflicts with any descendant lock.
  • Sibling paths (no prefix relation): never conflict.

Intent-shared on ancestors is the rule that makes the standard acquisition pattern (shared on every intermediate prefix plus exclusive on the leaf) self-consistent.

A reftype can only appear once as an argument or as a receiver in a single function call (enforced by the Call-scoped Locking algorithm below, on both axes: argument-versus-argument and argument-versus-receiver). This prevents aliasing and is the property docs/spec.pdoc calls 'no aliasing for reftypes'. Top-level data items are exempt -- they are immutable and never locked.

8.3. Call-scoped Locking Algorithm

When a function is called, locks are taken on argument paths and the receiver path, then released when the call returns:

  1. Each argument is processed left to right.
  2. If the argument is a top-level data item, no lock is taken (immutable, freely shared).
  3. For an argument whose source is a path (root, f1, ..., fn) resolving to a reftype leaf, a shared lock is taken on every intermediate prefix ((root,), (root, f1), ..., (root, f1, ..., fn-1)) and an exclusive lock is taken on the leaf (root, f1, ..., fn). The intent-shared ancestors permit sibling paths to be locked independently by later arguments.
  4. For an argument written as x.borrow (and similarly for stringView/listView), the call-scoped lock targets the source path -- the parent of the lifting suffix -- not the syntactic path with the suffix appended. m.borrow passed as an argument locks path (m,), not (m, borrow). This holds for every ownership and access marker, at any depth: the path builder classifies each dotted segment by name, so rec.field.borrow locks (rec, field) and this.private.borrow locks (this,). Position cannot decide this -- in the latter, both trailing segments are markers.
  5. If the requested lock conflicts with an outstanding lock on an overlapping path (see Conflict rule above), it is an error.
  6. If the argument is a sub-call, locking is applied recursively. After the sub-call, its argument locks are cleared or assigned to the sub-call result.
  7. After all arguments are processed, locks are taken on the receiver path -- shared on each intermediate prefix, exclusive on the leaf. For a bare-receiver call x.method, this is exclusive on (x,). For a method call via a field path this.sub.method, it is shared on (this,) and exclusive on (this, sub), leaving other fields of this freely accessible inside the call.
  8. The call is made.
  9. After the call, for a reference-carrying or .takex return, the leaf locks of its non-owned sources transfer to the returned value and become Borrow-scoped Locks held by that returned value. All other argument and receiver locks are released when the call scope pops.

for loops over a reftype iteration target take the lock the iterator's receiver declares, held for the duration of the body: iterate (a .view receiver) pins the target SHARED, while iterateMut and iterateItems (.borrow receivers) pin it EXCLUSIVELY. Either way the pin prevents mutation of the container or iterator from outside the loop. Per-iteration method dispatch takes and releases an exclusive lock on the iterator for each call. See the pin lifecycle walkthrough below for a worked example.

8.4. Per-Call Atomic Processing

The locking algorithm above is implemented through a per-call sub-scope model: every call -- not only those whose result is bound to a name -- opens its own scope while the typechecker processes it, and pops that scope when the call resolves. The sub-scope owns three things:

  • A call identity (call:<nodeid>). Locks taken while processing this call -- on the receiver, on argument source paths, or by recursion into nested calls -- carry this identity as their Holder, which is what scopes their release. It grants no exemption: every acquisition is checked against every outstanding lock, whoever holds it. Self-composition needs no exemption, because the prefixes an acquisition takes are shared and an existing shared ancestor is intent-shared -- so a prefix never blocks the leaf it was taken for. What remains is the one-appearance rule: two overlapping exclusive locks across one call mean the same reftype was reached twice, and that is an error. A mutable receiver plus an argument borrowing inside it (f.poke side: f.a.borrow) is therefore rejected -- inside the callee, this.a and side would alias. Two different calls get different identities and live in their own sub-scopes. Call identities are never named in a diagnostic; a conflict across calls reports the paths instead.
  • A list of synth temps (_t0, _t1, ...) for any argument that is not a bare name or literal. Each non-trivial argument is rewritten in place to a fresh AtomId(_tN) reference, with the original expression hoisted into a synth _tN: <expr> Assignment that lives in the sub-scope. Temps are ordinary variables in their sub-scope, so the existing scope-exit machinery releases their locks and runs destructors on un-taken reftype temps when the sub-scope pops. No special per-temp lifetime metadata is required.
  • A drained preamble of synth Assignment statements. Source-order is preserved by the left-to-right argument walk: the temp counter is monotonic, so the temp for the first argument always sorts before the second.

When an argument is itself a call, the typechecker recurses: the inner call opens its own sub-scope, hoists its own arguments, and pops on resolution. Lock effects propagate naturally through the parent-scope mechanism -- locks the inner call's return value carries become locks on the outer-scope binding (after rewriting the inner call's call-identity Holder to the outer call's identity where applicable), exactly as they would for any nested expression.

A method whose return is locked to its receiver or to a parameter declares the source as a non-owned parameter -- e.g. function {t: this.borrow} out T.borrow for a receiver-bound borrow, or function {s: T.borrow} out T.borrow for an explicit arg. The standard non-owned-param transfer at call resolution propagates the source lock into the outer scope. The shorthand :this cannot carry a marker directly, so receiver-locked methods must spell the parameter out (any non-this name works, e.g. t or h; using the literal this as the parameter name self-binds and is rejected). There is no syntactic special- case for .byteView / .listView / .stringView -- they are ordinary native methods declared in lib/system/*.z with the standard marked-receiver alias, and the standard transfer drives the propagation uniformly.

8.5. Borrow-scoped Locking

A Borrow-scoped Lock -- the enforcement record behind a pin -- is acquired whenever a variable is bound to a borrow or view construct: .borrow, String.stringView or str.stringView (both produce a StringView class borrowing the source), the analogous List.listView, a with name: Path do body whose right-hand side is a bare name or dotted path (borrow by default, same rule as function parameters), the transfer from non-owned parameters to a return value, and non-owned fields on classes. The lock targets the source path:

  • shared on every intermediate prefix of the source path. For v: rec.field.stringView the intermediate is (rec,).
  • exclusive on the leaf of the source path. For v: rec.field.stringView the leaf is (rec, field); for v: s.stringView the leaf is (s,).
  • held for the full scope of the borrowing variable; released automatically on scope exit or via .drop.

Path-scoped placement preserves all the safety properties of the previous root-only model (any access that overlaps the locked path is caught -- see Mutation-Site Enforcement below) while allowing sibling paths to be borrowed or mutated independently. A method that takes a view over this.a can, in the same block, mutate this.b -- the two operations target disjoint paths.

8.6. Lock Enforcement

While an exclusive Borrow-scoped Lock is outstanding on some path P, every operation whose target path overlaps P is rejected -- both reads and writes. Overlap means P is a prefix of the target path or vice versa; sibling paths do not overlap.

  • reading the locked path or any descendant of it (p.f, p.f.sub) -- a whole-record read of an ancestor (p) also overlaps and is rejected.
  • reassignment or field reassignment on an overlapping path (p.f = v, or p = ... for any ancestor).
  • swap with either side on an overlapping path.
  • method calls whose receiver path overlaps the locked path.
  • further .borrow, .stringView, .listView, .take, or .drop on an overlapping path.
  • passing a value with an overlapping path as an argument.

Sibling-path accesses remain permitted: while (p, f) is exclusively locked, reading or writing (p, g) is fine. The only code that can access the locked sub-tree is the lock Holder (the borrow or view variable) through its own interface.

This path-scoped approach prevents aliasing through field reads (which would create references that bypass the lock) while supporting field-granular independence -- essential for classes whose methods need to read one of their fields and mutate another in the same body.

match does not lock its subject. Match arms are mutually exclusive and the subject is evaluated once, so there is no aliasing or re-evaluation concern. .take is allowed on the match subject inside arm bodies for ownership transfer. See .take in Conditional Arms for the auto-destroy rule when .take appears in some but not all arms.

if does not lock anything. Condition expressions are evaluated like any other expression: any intermediate locks taken during evaluation are released before control enters the branch body. There is no variable-binding form for if in Zerolang. However, .take in an if arm triggers the same auto-destroy rule as match.

with does not lock its target either. The with name: value do expr form is sugar for a scoped name binding; lock handling is delegated to the assignment semantics of name: value and to operations inside expr that take their own locks via the function-call algorithm. When name falls out of scope at the end of with, any locks it holds -- including those transferred from non-owned fields of the bound value -- are released.

8.7. Lock Release on Scope Exit

When a variable falls out of scope, every pin it holds ends: all locks it holds on other variables are released. If the variable is borrowed, the borrow ends. If the variable is owned, it is destroyed (reftypes) or forgotten (valtypes).

8.8. Temporary Expressions in Lock Context

The compiler rejects .borrow, .stringView, .listView, and any non-owned marker on temporary expressions (i.e. expressions whose result has no named variable) -- a temporary has no scope to pin against. The programmer must assign the value to a variable first:

# ERROR: cannot create view from temporary expression
# v: "hello".string.stringView

# OK: assign first, then view
s: "hello".string
v: s.stringView

A future version of the compiler may support automatic temporary variable creation to keep lock-context expressions alive, but for now explicit naming is required.

8.9. Binding Aliases

Certain bindings do not produce a new storage location at all — the compiler emits the new name as an alias for the source expression. The existing Borrow-scoped Lock guarantees the source slot stays valid and unmutated for the alias's lifetime, so there is no observable difference between "fresh copy" and "alias" semantics, and the alias saves the copy.

Aliasing applies to:

  • with name: Path do body whose RHS is a bare name (with a: c do ...), a dotted-valtype path (with v: r.f do ...), or inline .take / .borrow on either (with a: c.take do ...).
  • Inline .take or .borrow in a plain assignment (d: c.take, y: r.f.borrow).

Aliasing does NOT apply to:

  • Call or constructor right-hand sides -- the returned value must materialize into a real local.
  • Dotted paths that dereference a reftype pointer at any step (e.g. b.label where b is a class) -- keeping the local pins the pointer in a register so the programmer's load-once intent is preserved.
  • Plain x: y assignments without .take or .borrow -- these retain their existing copy-or-transfer semantics.

The generated C contains /* alias: name => source */ comments at the substitution site for readability; references to the alias name in the body emit as the source expression directly.

9. Borrow Escape Rules

Borrowed values cannot escape into positions that require ownership. The type-checker rejects these statically with a hint pointing at the remediation (.copy, .take, or a non-owned destination).

9.1. Returning a borrowed parameter as owned

A function declared out T returns an owned value. Returning a borrowed parameter directly would alias the caller's heap data:

identity: function {s: String} out String is {
    return s          # error: 's' is borrowed; the caller still owns it
}

Remediations:

  • return s.copy -- clone into a fresh owned string.
  • Annotate the parameter as s: String.take -- the caller transfers ownership in, and the function may pass it through.
  • Declare the function as out String.borrow with a non-owned parameter -- the caller receives a borrow tied to the locked source.

The check fires only for stack-reftypes (string, file, bufreader, user classes) returned as a bare AtomId. Projections (s.copy, s.field) and explicit annotations (s.take, s.borrow) opt out as documented above.

9.2. Storing a borrowed parameter into an owned aggregate field

A constructor field declared with no .borrow annotation expects an owned value. Storing a borrowed parameter into it would alias the caller's heap data the same way:

make_box: function {name: String} out Crate is {
    return Crate label: name    # error: 'name' is borrowed
}

Same remediations as above. The exemption mirrors the borrowed_record / listiter pattern: a .borrow-annotated parameter projected into a matching non-owned field is the canonical borrow-Holder pattern (see Classes with Non-Owned Fields below) and is allowed.

10. Classes with Non-Owned Fields

Some classes need to hold a locked reference to another object -- most commonly iterators and views. A class field can be declared non-owned -- .borrow or .view -- to express this:

MyIter: class {
  state: i64
  target: container.private.borrow
} as {
  create: function {target: container.private.borrow} out this.takex is {
    return meta.create state: 0 target: target
  }
}

The field stores a locked reference to external data. The reference is locked for the entire lifetime of the class instance. When the instance falls out of scope, the locks held by its non-owned fields are released together with the instance itself.

Classes are single-owner: they cannot be copied, only moved via .take. This is what makes non-owned fields safe on classes -- there is no way to duplicate the handle that holds the lock, so there is no way for two live instances to share (and race on) the same locked target. No separate separate mechanism is needed.

10.1. Rules for Non-Owned Fields

A field marker sets two independent things, and they are checked in different places.

The slot. .borrow and .view are not owned, so the slot is static: it is set in meta.create, carries no destructor, and the constructor locks its argument. .take and .hold are owned, so the slot may be reassigned and does carry a destructor. Which cell a field is in is therefore visible in its behaviour, not just its type.

The contents. .view and .hold freeze what the field points at; .take and .borrow do not.

  • Non-owned fields are only allowed on classes. A record with one is a compile error -- records are pure valtypes and are freely copied, which would duplicate the lock.
  • The field type must match the corresponding constructor parameter type. If the field is MyClass.private.borrow, the constructor parameter must be too.
  • .private controls access level (friend access to private members); the ownership marker controls ownership. These are orthogonal and combine.
  • A .private handle can only be PRODUCED by the value's own type (its methods) or forwarded by a holder of an existing handle; external code holding a value only publicly cannot take its .private (error E0102).
  • A class that has any non-owned field cannot appear as a field of another user-defined type. A non-owned field is only valid when its Holder's lifetime is scoped by the same block as the target; nesting inside another object's field would allow the Holder -- and its lock -- to outlive that scope.

Non-owned fields are set at construction time and cannot be reassigned -- Cannot reassign '.borrow' field -- because only the construction-time escape check can prove the target outlives the instance. The reference must remain valid for the entire lifetime of the instance. Owned fields such as iteration counters can be freely mutated.

A constructor that returns such an instance should declare out this.takex, so the sources its non-owned fields point into stay pinned for the result's lifetime. Without it nothing holds them and the fields dangle.

10.2. Moving a Class with Non-Owned Fields

A class with non-owned fields is a normal owned instance. It can be moved via .take: the instance (and the locks it holds) transfer to the new name; the old name is invalidated. What it cannot do is be copied, which for classes is true of every instance regardless of whether it has non-owned fields.

10.3. C Representation

All user-defined types are stack-allocated at the C level. A class lives inline in the stack frame where it is constructed; the single owner variable names that slot. Passing a class to a function passes a pointer to that slot so that methods can mutate it; returning an owned class returns the value by move (the caller's stack slot receives the bytes).

The .borrow annotation has no special C-level encoding. A non-owned field has the same C representation as a non-non-owned field of the same type:

  • A non-owned field storing a reftype is a stored pointer into the source variable's stack slot -- the normal C representation for a borrowed reftype field.
  • A non-owned field storing a valtype is an inline value (records cannot contain heap-backed types, so there is no pointer dance; the valtype is stored by value).

In both cases the field layout is identical to a non-non-owned field. The .borrow annotation tells the compiler to track a lock on the source variable for the lifetime of the instance, and prevents the field from being reassigned. There is no runtime encoding of "this is locked" anywhere -- the locked status is tracked entirely by the compiler.

The C call convention for .borrow parameters is unchanged from non-.borrow parameters of the same type:

  • Reftype .borrow parameter -- the pointer is passed by value (the reftype's normal C calling convention).
  • Generic .borrow parameter -- passed using the convention of whatever concrete type the generic parameter monomorphizes to (reftype: pointer; valtype: value). .borrow on a known valtype is a compile error.

10.4. Unions, Protocol Instances, Variants

Unions are represented as a {tag, void*} struct on the stack. The tag discriminates the active subtype; the void* points to the subtype data which is heap-allocated for the subtype's value. The struct itself lives inline with the owning variable.

Variants are pure valtypes laid out as {tag, union-of-payloads} entirely on the stack, with no heap storage.

Protocol instances and facet instances are stack-allocated like any other user-defined type. A protocol instance wraps its source either by borrow (leaving the source locked for the wrapper's lifetime) or by take (consuming the source into the wrapper).

10.5. Restrictions with Generics

A container names its element family: classes and unions go in the reference-element containers (List of: MyIter is exactly what ListRef accepts), records and other valtypes in the valtype twins (ListVal). Using the wrong family is a compile-time bound error. What remains restricted is the non-owned-field rule: a class with a non-owned field cannot be nested as a field of another type.

Generic functions that only .borrow their generic parameter are fine. The restriction only applies when the generic type or function would need to copy the class.

10.6. Protocol and Facet Restrictions

Classes can be used as sources for protocol and facet wrappers. A class with non-owned fields can be borrowed into a protocol instance via the label or .borrow form -- the protocol wrapper holds a borrow on the source, and the lifetime rules propagate as usual. Taking a class with non-owned fields into an owned protocol instance (consuming it with .take) is also permitted: the class -- and the locks it holds -- move into the wrapper.

11. Escape Analysis for Pins

The compiler must verify that borrowed return values -- and owned returns that carry non-owned fields -- trace back to non-owned (.borrow or .view) parameters of the current function. This ensures the pinned data stays alive for the lifetime of the returned value.

11.1. Reftype Borrow Returns

For a reftype borrow return, the returned reference must point to data living inside a .borrow parameter. The compiler traces the return expression back through field accesses to verify it originates from a locked parameter.

# OK -- return value is a field of the locked parameter
get_child: function {t: MyClass.borrow} out child.borrow is {
  return t.child
}

# ERROR -- cannot return local variable as borrowed
bad: function {t: MyClass.borrow} out child.borrow is {
  c: child
  return c
}

# ERROR -- no non-owned parameter
bad2: function {t: MyClass} out child.borrow is {
  return t.child
}

11.2. Classes with Non-Owned Fields

A factory that constructs a class with a non-owned field and returns it as an owned value must initialise the non-owned field from a .borrow parameter. The compiler verifies the construction arguments of the returned instance trace back to the locked parameter of the enclosing function.

# OK -- target field traces to b which is non-owned
iterate: function {b: this.borrow} out MyIter is {
  return MyIter target: b.private
}

# ERROR -- b is not non-owned
bad_iterate: function {b: this} out MyIter is {
  return MyIter target: b.private
}

The locks on the .borrow parameter transfer to the returned instance: the caller receives an owned class whose non-owned field keeps the source locked for the returned instance's lifetime.

11.3. Cross-Function Pin Chains

When a function returns a borrowed value that holds pins, and the caller passes that value to another function, the pin chain must be maintained. The compiler verifies that each link in the chain connects to a non-owned parameter.

# OK -- both functions lock their input and return a borrow
inner: function {t: MyClass.borrow} out child.borrow is {
  return t.child
}

outer: function {t: MyClass.borrow} out grandchild.borrow is {
  x: inner t         # x borrows from t, pin on t
  y: x.grandchild    # y borrows from x
  return y            # OK: pin chain traces to t which is non-owned
}

12. Simple Ownership Examples

Before the advanced iterator pattern, here are the common ownership scenarios that cover most code.

12.1. Owned Valtypes (the common case)

point: record { x: i64 y: i64 }

# Valtype default: borrow (copy). Both p and q are independent owned values.
p: point x: 1 y: 2
q: p                 # copy -- p is still valid
q.x = 99             # does not affect p

# Passing to a function: borrowed (copied) by default
print_point: function {pt: point} is {
  print "\{pt.x}, \{pt.y}"
}
print_point p        # p is copied into the function, p still valid

12.2. Owned and Borrowed Reftypes

Crate: class { label: String value: i64 }

a: Crate label: "alpha" value: 1   # a is OWNED

# Reftype default: borrow. peek does not take ownership.
peek: function {b: Crate} out i64 is {
  return b.value
}
v: peek a                        # a is borrowed, still valid after call

# Explicit .take transfers ownership. a is invalid after this line.
consume: function {b: Crate.take} is {
  print b.label
}
consume a                        # a is implicitly taken (ownership transferred)
# a is invalid here -- compile error if used

# Explicit .take to destroy
b: Crate label: "beta" value: 2
b.take                           # destroys b immediately

# Borrow with lock: return a reference into the locked parameter
peek_label: function {b: Crate.borrow} out String.borrow is {
  return b.label
}
c: Crate label: "gamma" value: 3
s: peek_label c                  # s borrows from c, c is locked
print s                          # OK
# c cannot be used here (locked by s)
# when s falls out of scope, c is unlocked

12.3. Compiler Error Messages

The compiler provides specific error messages for ownership violations, including the location of the conflicting operation and a hint suggesting how to fix it. For example:

  • Attempting to use a variable after it has been taken reports which call consumed it and suggests using .borrow if the variable is still needed.
  • Attempting to pass a borrowed variable to a .take parameter reports that the variable is borrowed and suggests restructuring ownership.
  • Attempting to use a locked variable reports which variable holds the lock and where the lock will be released (scope exit).
  • Returning a borrow without a non-owned parameter to borrow from suggests marking the source parameter .view (readonly) or .borrow (mutable).
  • Declaring a non-owned field on a record reports the specific field and suggests making the enclosing type a class.

13. Iterator Pattern

The iterator pattern is the most common complex use of the ownership system. It demonstrates non-owned fields on classes, pinning, private access, and scope-based pin lifecycle.

The iterator's constructor uses meta.create (the internal raw allocator of the enclosing type) to allocate the instance. This is the only legal form of construction inside the constructor body -- writing return BagIter pos: 0 target: target would recurse into the user-defined create and is a compile-time error. See the spec's "Implicit Construction" section for the full dispatch rule.

13.1. Components

An iterator system has three components:

  1. Container -- the iterable object (typically a class). It has an iterate method that returns an iterator. The method pins this -- shared for a readonly walk (the stdlib's iterate declares a .view receiver), exclusive for a mutating one -- so the container cannot be modified while iteration is in progress.
  2. Iterator -- a class that maintains iteration state. It holds a .private.borrow field referring to the container for access to internal state, and has a call method that returns the next item. Because classes are single-owner, nothing in the program can duplicate the iterator and race on the container.
  3. Iterated value -- the value produced on each iteration. Can be owned (a copy) or borrowed (a reference into the container that locks the iterator).

13.2. Full Example

The canonical class-based iterator (also in examples/ListIter.z):

# --- Container ---
Bag: class {
  a: i64
  b: i64
  c: i64
  count: i64
} as {
  public: unit { :count :iterate }

  # Factory method: locks 'this', returns an owned iterator.
  # The lock on 'this' transfers to the returned iterator via its
  # non-owned field.
  iterate: function {b: this.borrow} out BagIter is {
    return BagIter target: b.private
  }
}

# --- Iterator (class) ---
# The 'target' field is .private.borrow: it holds a locked reference
# to the container's private namespace for the iterator's lifetime.
# The class is single-owner: nobody can copy it, so the lock is safe.
BagIter: class {
  pos: i64
  max: i64
  target: Bag.private.borrow
} as {
  create: function {target: Bag.private.borrow} out this is {
    return meta.create pos: 0 max: 3 target: target
  }

  # Returns an owned i64 (copy from container).
  call: function {it: this} out (optionval t: i64) is {
    if it.pos < it.max then {
      if it.pos == 0 then {
        it.pos = it.pos + 1
        return (optionval.some it.target.a)
      }
      if it.pos == 1 then {
        it.pos = it.pos + 1
        return (optionval.some it.target.b)
      }
      it.pos = it.pos + 1
      return (optionval.some it.target.c)
    }
    return (optionval.none i64)
  }
}

# --- Usage ---
main: function is {
  b: Bag a: 10 b: 20 c: 30 count: 3

  # 'with' creates the iterator and scopes its lifetime.
  # The 'for' loop calls the iterator on each iteration.
  with iter: Bag.iterate b: b do for x: iter loop {
    print "iter: \{x}"
  }

  # After the with/for:
  # - iter fell out of scope (class destroyed)
  # - lock on b released
  # - b is available again
  print "Bag count: \{b.count}"
}

13.3. Pin Lifecycle in the For-Loop

The iterator may be created explicitly with with before the for loop; the for-loop dispatch also accepts an iterable directly (it synthesises the .iterate call) or an inline constructor call (it creates the hidden binding itself). The explicit form is:

with iter: container.iterate c: c do for x: iter loop { ... }

The pin lifecycle step by step, for a readonly stdlib walk over a list xs:

with iter: xs.iterate do {
  # iter: OWNED iterator on caller's stack
  # xs: pinned SHARED by iter (via its non-owned field)
  # readers on xs (length, get, another iterate) stay legal
  # while iter is alive; writers are refused

  for x: iter loop {
    # Entry:
    #   iter.call is invoked (iter is the receiver)
    #   exclusive lock on iter during the call
    #   result checked -- the call returns (OptionView of), a
    #     borrowed view; none terminates the loop
    #   x: READONLY borrowed view of the container's element,
    #     pinning iter while it lives (for a valtype element x
    #     reads as the value, but stays readonly)
    #   call-scoped lock on iter released (call complete)

    print x

    # End of loop body:
    #   x falls out of scope -- its pin on iter is released
    #   next iteration begins -- iter.call invoked again
  }
}
# iter falls out of scope:
#   class is destroyed
#   pin on xs released
# xs is writable again

The Bag example above differs in exactly two places. Its iterate declares a .borrow receiver, so BagIter pins the bag EXCLUSIVELY -- b cannot be used at all while iter is alive. And its call returns owned optionval copies rather than borrowed views, so each x is an owned i64 holding no pin once the call completes. A call that returns a borrowed view instead keeps a pin on the iterator, preventing the next call until the value falls out of scope at the end of each loop iteration.

13.4. Views

The same pattern underlies views. A view is a small class holding a .private.borrow field into its source -- for example the StringView and ListView types in the standard library (StringView is readonly; ListView also offers getMut for in-place element writes). Because the view is a single-owner class, the source stays safely pinned for the view's lifetime and no copy of the view can outlive it. See examples/ListView.z and examples/borrowed_record.z for worked examples.

14. Container Views and Pins

A Map.get over a reftype value does not copy the stored value out -- it returns an OptionView whose payload is a borrowed reference into the map's own storage (the valtype-value forms MapRV / MapVV return optionval, a copy, no pin). List.get hands back the element's of.view directly. The same is true of iterator yields, MapEntry pairs from iterateItems, and the stringView / listView / byteView families. These are all views: cheap, non-owning windows into a parent container.

Two rules make views sound, and the compiler enforces both:

  • A view's payload cannot be moved out. Binding it to a new name, reassigning it away, marking it .take, or passing it to a taking parameter are all rejected with E0200. Moving the payload would drain the map's stored value in place -- the map would keep answering some with an empty husk. Call .copy on the payload to keep an owned copy; reading it in place (interpolation, .stringView, .length, comparisons, method calls) is always fine.
  • A live view pins its parent. The binding holds a SHARED path-scoped lock on the container for its whole scope. Readers may overlap; a writer may not.

The pin model is many readers or one writer; an iterator pins with the strength its receiver declares:

  • Any number of live views and reader calls (get, has, length, copy, ...) coexist on one container.
  • A writer call (Map.set / remove, Set.add / delete, List.append / pop / getMut / ..., String.append) is rejected while any view or iterator on that container is live. A set can rehash and reallocate; every live payload pointer would dangle.
  • A plain iterate is a reader: its receiver is .view, so other readers -- including get and further iterate walks -- stay legal while it runs; only writers are excluded. iterateMut is the mutating walk; iterateItems is readonly by design (a key is hashed -- writing through an entry would put it in the wrong bucket) but still pins exclusively. Both hold the container exclusively for their lifetime: no other access until the loop ends.

A method is a reader when its receiver is declared .view, which any class may do:

Counter: class {
    n: u64
    value: function {c: this.view} out u64 is {
        return c.n
    }
}

The receiver then pins itself readonly for the whole body, so the call takes a SHARED lock instead of an exclusive one. The stdlib containers declare it on length, capacity, contains, has and iterate, and String and StringView declare it on their queries. get, getMut and listView do not: they return a borrow into the container, and a readonly receiver must not hand out a writable alias.

m: (Map String V: String)
m.set key: "a".string value: "x".string
m.set key: "b".string value: "y".string

g1: m.get key: "a".string        # SHARED lock on m, held by g1
g2: m.get key: "b".string        # fine: readers coexist
n: m.length                      # fine: reader call
match (
    g1
) case some then {
    kept: g1.copy                # OK: copy to keep
    # stolen: g1                 # E0200: cannot move payload out of a view
} case none then {}
# m.set key: "c" ...             # E0200: writer while g1/g2 live
with it: m.iterateItems do for e: it loop {

}
# pair values with the iteration instead:
with items: m.iterateItems do for e: items loop {
    print "\{e.key}: \{e.value}"
}

The same discipline covers strings: sv: s.stringView pins s SHARED, so s.append (which may reallocate the buffer sv points into) is rejected while sv is live.

User-defined functions are treated conservatively: passing a container to any function pins it exclusively for the call, because the compiler does not look into the callee's body. Read a value out first (scope the view in a bare { } block and .copy what you need) when you must hold data across such a call.

15. Protocol Objects

Protocol instances can be created in three ways, each with different ownership semantics:

  • Borrowed via label (r: obj.protocolname) -- preferred borrow form when the type declares the protocol with a named label in its as block. Returns a borrowed protocol instance. The protocol instance lives on the caller's stack for the duration of the binding and is forgotten on scope exit; the underlying data is not destroyed. The source variable is locked exclusively for the lifetime of the protocol instance and becomes accessible again when the protocol instance goes out of scope.
  • Owned via create (r: proto.create from: obj.take, or the bare-name shorthand r: proto obj.take): returns an owned protocol instance. The source object is consumed (taken). On scope exit, both the protocol instance and the underlying data are destroyed. Bare-name routes through proto.create via the unified call dispatch; see the spec's "Implicit Construction" section.
  • Borrowed via borrow (r: proto.borrow from: obj.borrow): explicit borrow form for when the label shorthand is not available (e.g. the implementing type does not name the conformance). Semantically equivalent to the label form -- the protocol instance lives on the stack until it falls out of scope, the underlying data is not destroyed, and the source variable is locked exclusively.

.take used to be registered as an alias for .create on protocol, facet and typedef types. It has been removed: the canonical construction verb is .create, and .take on these types now produces a migration error pointing at .create and .borrow. .take remains available as the inline ownership method on runtime instances (obj.take) as before.

The from: parameter of a protocol's synthesised .create is declared TAKE, so the compiler applies the standard ownership-transfer rules uniformly: writing r: Reader.create from: o invalidates o afterward, with no call-site .take required (writing o.take is accepted and equivalent). The same rule applies to typedef.create. Facet .create is a value-copy (facets are inline-data value existentials), so its from: source remains valid after the call.

A borrowed protocol wrapper carries no ownership over the source; the source's storage lives where it was declared. Consequently, a borrowed wrapper cannot escape the scope of its source: the compiler rejects returning it, storing it in a record field, and passing it to a TAKE parameter. Use the owned form (.create) for a self-contained wrapper that is safe to return or store. These restrictions mirror the existing locked-reference escape rules from the previous section.

Boxing (b: Box from: val) copies its valtype source onto the heap -- the standard valtype rule, no ownership transfer (Box.t is bounded anyval.generic; a reftype is already a heap pointer and is rejected).

Boxing a conformer and then passing the box to proto.create is not supported: .create already heap-allocates the owned copy internally, so composition is unnecessary. The conformance check rejects proto.create from: (Box from: x) with a hint steering the user to the direct form.
