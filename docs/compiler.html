1. Introduction

A document showing the compiler architecture overview.

2. Virtual File System

A simple readonly Virtual File System (VFS) is used to present a unified source tree to the compiler.

The VFS allows union or bind mounts to mount one filesystem over another. The VFS tree presented to the compiler is usually the system directory with the user source directory union mounted over this. In this way, user units are found first, shadowing system units. This offers some backwards compatibility - future system modules that may be released that collide with user modules will be hidden by them. The user modules would need to be refactored/renamed to make use of the new system modules.

The VFS allows abstraction over a source tree that may be arbitrarily complex while providing a simple interface to the compiler. The VFS tree can be built from multiple physical filesystems or can be built from alternate data stores (such as databases or remote systems).

3. Tokenizer

The Tokenizer splits a single top level unit aquired from the VFS (usually represented by a file) into a stream of tokens. Every part of the source becomes part of a token and so the original source could be recreated by concatenating all of the tokens returned by the tokenizer.

The tokenizer splits the file into tokens such as:

  • horizontal whitespace (spaces and tabs only)
  • end of line
  • comments
  • identifiers
  • keywords
  • delimiters such as (, ), { and }
  • dot operator: .
  • parts of string literals (raw and interpolated)
  • numeric literals
  • error tokens

The tokens have a type, the string contents and an identifier for the file that they are contained within and the location (line and column) within that source file.

The Tokenizer follows the ITokenizer protocol which provides a single 'token' method. This allows alternate tokenizers to be provided or allows filtering or logging to be inserted.

4. Lexer

The Lexer provides another layer over the Tokenizer to ease the job of the parser which will follow.

The Lexer filters comments and whitespace as these are not used by the parser. It also keeps a small stack to maintain context for handling end-of-line (EOL).

In Blocks (the top level of a unit or a brace delimitered block), multiple EOL's are coalesced into a single EOL token. In parenthesized expressions, all EOL's are ignored. In string literals, all EOL's are passed through as-is and form part of that string literal.

The Lexer buffers one token of lookahead, and never copies it out. A rule that wants to know what comes next asks peekType for the token type or peekPos for a tokpos -- a valtype spanning the token: fsno, line, column, and the text's byte width, which is everything a diagnostic needs from the text without the text itself. A rule that must read the characters asks peekText for a StringView and makes its own owned copy if it needs one.

The split follows the two lifetimes. A tokpos copies out, so a rule can capture where its construct began and still report an error against it a hundred lines and several advance calls later. A peekText view pins the Lexer and must not be live across advance, accept or acceptAny, because those overwrite the buffer it points into. Consuming a token is free either way: accept / acceptAny move the buffered text out rather than duplicating it.

5. Parser

The parser creates an abstract syntax tree (AST) from the source units supplied. It begins with the 'core' system unit and the user 'main' unit and parses each, loading further units as they are referred to.

The parser resolves no names. After a unit is parsed, one walk over its body (collectExterns) collects the identifiers the unit refers to but does not bind -- biased to over-collect, since a spurious name simply fails to name a file -- and for each such name the VFS is asked for <name>.z: first in the directory named after the current unit (an implementation subunit), then in the source tree and the system library. A unit found this way is parsed the same way, recursively, until the worklist is empty. Whether a name actually denotes a unit, a type, or a variable is the type checker's question, asked in the environment it builds from the finished AST; a public: block's entries count as references, so a listed hidden subunit loads on the strength of the listing alone.

The parser returns the first syntax error found immediately. It does not attempt to reset and continue.

6. Generator Desugaring

A function whose body contains at least one yield and whose declared return type resolves to the stdlib Iterator protocol is a generator. Generator lowering (helpers in src/zgenerator.z, driven by lowerGenerators in src/ztypecheck.z) rewrites every such function into a pair: a synthesised class implementing the iterator protocol and a factory function that constructs an instance with all parameters captured. The lowering runs early in the typecheck pass, after unit types are registered and before bodies are checked, so the rest of the typechecker sees only ordinary class + function code.

The trigger is syntactic: a body containing yield and a declared return whose head is spelled Iterator. Lowering rebinds the original function to its factory and appends the synth class to the unit body; frozen AST nodes are never mutated.

Pipeline placement:

  Lex -> Parse -> Typecheck (lower generators, then resolve + check) -> Emit

6.1. Synthesised class shape

For a generator F: function {p1: T1 ...} out (Iterator gives: G accepts: K) is { ... body ... } the pass produces approximately

  F_iter: class {
      state: i64               # state-machine cursor
      p1: T1                   # captured params (with original ownership)
      <crossing-locals>: ...   # locals whose live range crosses a yield
      _resume_input: K         # only when takes is non-null
  } as {
      create: function {p1: T1 ...} out this is {
          return meta.create state: 0 :p1 ... <local-defaults>
      }
      call: function {:this} out (option-wrapper-for-G) is {
          # original body, references to promoted names rewritten to this.<n>;
          # carries synthOrigin = "generator-call" so the emitter routes it
          # through the state-machine codegen below.
      }
  }

  # original F is replaced with a factory of the same signature:
  F: function {p1: T1 ...} out F_iter is { return F_iter :p1 ... }

The synthesised class name is <funcname>_iter for standalone generators and <typename>_<methodname>_iter for methods. Numeric suffix on collision.

6.2. Liveness (which locals get promoted)

A local must become a class field iff its live range crosses a yield -- otherwise its C-stack slot in .call is gone between invocations. crossingLocals in src/zgenerator.z runs a structural traversal applying two rules:

  • Yield-count rule -- track a running yield counter (pre-bump for the yield's own expr). For each local, record first_def_yc and max_use_yc. If max_use_yc > first_def_yc, the def-to-use path crosses a suspension.
  • Yielding-loop rule -- any reference to a local inside the body of a for loop whose body contains a yield is treated as crossing (the next iteration's read sits "after" the previous iteration's yield).

Parameters are always promoted (the factory captures them into the synth class). Non-crossing locals stay as ordinary C locals inside the generated .call body.

6.3. State-machine codegen

The emitter (src/zemitterc.z) routes any function whose synthOrigin == "generator-call" through a dedicated state-machine path. Helpers emitGenPrologue, emitYieldStmt, and emitGenEpilogue assign one state number per yield (entry = 0, terminal = -1) and emit:

  switch (this->state) {
      case 0:  goto L_entry;
      case 1:  goto L_resume_1;
      ...
      default: goto L_done;
  }
  L_entry:
      /* original code up to first yield */
      this->state = 1;
      return OPTION_SOME(<yield expr>);
  L_resume_1:
      /* if takes != null: bind local from this->_resume_input */
      ...
  L_done:
      this->state = -1;
      return OPTION_NONE;

C17 goto plus switch arbitrates cleanly; no GCC extensions. The yield-state numbers are pre-allocated from the function's yield count (fnYieldCount) so the prologue, body fragments, and epilogue agree.

6.4. Termination + bidirectional value flow

A bare return anywhere in the body or fall-through past the last yield transitions to the terminal absorbing state. return <value> is rejected during desugaring. Code placed after the last yield runs on the call that crosses into terminal; it does not run on early drop, where class destruction releases locks and destroys owned fields via the standard class-lifetime path.

For accepts: K generators, buildCallMethod adds a value: K parameter; the generated prologue emits an entry-time store of value into this->_resume_input (destroying any prior owned value first). Expression-form yield (x: yield v) in the body reads this->_resume_input after the resume label so x binds to the caller's most recent input. The first reachable yield must be statement form -- the desugarer rejects expression-form first-yields, reflecting that the resume-input slot is undefined before the first .call value: arrives.

7. Semantic Analyser (Type/Ownership/Lock checking)

The Semantic Analyser assigns a type to each node in the AST. It compares types of definitions, assignments and arguments being passed to ensure the types are compatible.

A stack of nodes being typechecked is maintained as checking proceeds. This allows the type checker to catch circular dependencies.

7.1. Demand-Driven Resolution

The type checker is demand-driven: it starts from main and resolves definitions as they are referenced. Types, functions, and definitions that are never reachable from main are never type-checked. This ensures the compiler only processes what is needed, and circular dependencies are detected when a name is encountered that is already on the resolution stack.

There is one environment. Every unit's top-level names are indexed before any resolution (the declaration tree: each unit is a frame whose children are its definitions, each carrying its resolution state -- not yet touched, demanded, being resolved, resolved). A reference resolves by walking the frames from the inside out: the enclosing namespace, the current unit, then the prelude (core, whose members are re-exports); the first match wins, and a qualified unit.member names its unit directly and walks nothing. The declaration a reference finds is what it demands -- never a bare name -- so a name defined in two units can only ever reach the one the reference could see, and the standard library is resolved by exactly the same rule as any other unit. Demanded declarations are queued in discovery order and resolved from the top level, each one's body scanned for further references only once its own resolution completes.

The rule holds for the unit being compiled exactly as it does for its dependencies, which is why that unit must declare a main at all (E0039): without a root there is nothing to demand from. What a type DECLARES is resolved either way -- its generic parameters, the interfaces it conforms to, and the namespaces and inline templates that scope it -- because those are properties of the declaration rather than of anything walking a body.

Resolution is outside-in: a type resolves before its fields, its fields before its method signatures, and no method body is walked until that completes. A body walked ahead of its owner would bind this to no type at all, and every check that hangs off the receiver would quietly stop asking.

7.2. Monomorphization

Generic types are instantiated through monomorphization. When a generic type (e.g., List(String)) is used, the type checker creates a concrete copy (a monomorphized type) with the generic parameters replaced by concrete types. The monomorphized type name is mangled (e.g., list__string) to produce a unique C identifier.

Generic method bodies are deep-copied during monomorphization and type-checked with the concrete type arguments in scope. This ensures that each instantiation is independently validated.

Compiler-injected methods on collections (.append, .set, .get, .byteview, .listview, .stringview, .iterate, .each, .length, and friends) are not synthesised by the monomorphizer. They are declared with the is native form in lib/system/system.z and lib/system/collections.z; the monomorphizer clones those declarations alongside everything else. Resolution flows through the standard child-lookup path -- there is no syntactic special case in the type checker for these names, and a user-defined member of the same name on a non-collection type resolves normally. Methods that return a borrowed reference into a parameter or receiver declare that source as a non-owned parameter (e.g. function {t: this.borrow} out T.borrow); the standard .borrow-param transfer at call resolution drives the call-site locking, with no name-based pattern matching.

A no-user-arg method dotted path (v: s.stringview, p1.distance inside string interpolation) is auto-called when read in value position. The coercion lives in checkDotted and is gated by a coerce-to-return flag that checkCall clears when resolving its callable -- so explicit method calls (obj.method named: arg) see the function type and dispatch normally instead of falling into construction-of-return-type. Path resolution itself is context-free: it always returns the FUNCTION type for a method path. The behaviour is identical for is native and user-defined methods.

7.3. Ownership and Lifetime

The ownership status of each expression is determined using a 2-state model: OWNED (the variable owns the instance and is responsible for its lifetime) or BORROWED (a temporary reference; the variable does not own the instance).

Function parameters carry ownership annotations: take (caller transfers ownership to callee), borrow (callee gets a borrowed reference), or lock (callee locks the argument for the duration of the call). See docs/ownership.pdoc for the full specification.

7.4. Scope Environment

All variable state -- type, ownership, lock state, type narrowing, and taken (consumed) status -- is tracked in a unified scope-based environment. Entries are held in a flat List ZEntry on the symbol table, with each scope recording its start index rather than owning a dictionary. Scopes are small (measured maximum of approximately 6 entries in practice) so linear scan outperforms hash lookup.

A ZEntry carries: the variable name, its resolved type, whether it is a definition or a shadow overlay, optional ownership info, optional lock state, optional type narrowing (narrowedSubtype and excludedSubtypes), and optional taken state.

Three scope kinds are used:

  • BLOCK -- language constructs (function, do, for, if, with, match, match arm). Can contain variable definitions.
  • CALL -- pushed before processing call arguments, popped after the call returns. Lock entries placed here are released automatically when the scope is popped.
  • OVERLAY -- per-statement state changes. Contains shadow entries that record a new state (lock, narrowing, taken) for a variable defined in an outer scope.

State changes follow an immutability principle: new shadow entries are created in overlay scopes rather than modifying existing entries. The scope chain is the history. Scope exit (via popTo) naturally releases all state from that scope -- locks vanish, narrowing resets, taken markers are merged into the parent.

Each scope carries a monotonically increasing scopeId for tracing and SQL output.

7.5. Lock Checking

Lock keys are paths -- tuples of name ids (root, f1, f2, ..., fn). Overlay rows (ZEntry) are keyed by the root local's declaration so the linear scan stays cheap; the full path lives on ZEntry.lockPath and is consulted to apply the prefix-overlap conflict rule. Two lock scopes exist:

  • Call-scoped locks -- taken on function arguments during a call. A call scope is pushed before argument processing. For each reftype argument, SHARED locks are taken on every intermediate prefix of the source path and EXCLUSIVE on the leaf. The receiver path locks identically. After the call returns, the scope is popped and all call-scoped locks are released. For non-owned parameters, the leaf lock transfers to the return value (installed as a borrow-scoped lock in the parent scope).
  • Borrow-scoped locks -- taken when .borrow, .view, .stringview, .listview, a with-binding, or a .borrow-param transfer creates a borrowed binding. SHARED entries are placed on each intermediate prefix and EXCLUSIVE on the leaf in the scope where the borrow variable is defined. The locks persist for the lifetime of that scope (released on scope exit or explicit .release).

Conflict check (multi-granularity): same-path locks dedupe when both SHARED and conflict when either is EXCLUSIVE; a strict ancestor SHARED is intent-shared and permits any lock on descendants; a strict ancestor EXCLUSIVE conflicts with any descendant. Sibling paths (no prefix relation) never conflict. Enforcement for access / mutation sites uses the same prefix-overlap test: any EXCLUSIVE whose path prefix-overlaps the target path is a conflict.

Key code: tryLock / findExclusiveLock / lockAcquireConflict in src/zenv.z; lockCallArg / installBorrowLocks and the path-tuple builders and access-check helpers in src/ztypecheck.z.

All parameters default to .borrow regardless of type family. For valtypes, .borrow means a copy (no lock, source not invalidated). For reftypes, .borrow means a reference (source not invalidated). .borrow on a known valtype is a compile error -- valtypes are pass-by-value so identity-based locking is meaningless. Generic type parameters are exempt because they may monomorphize to a reftype.

7.6. Numeric Literal Coercion

Bare numeric literals are typed as one of two compiler-internal singletons during typecheck: literalInt or literalFloat (both flagged isLiteral on ZType). Constant expressions built from them stay literal-typed too — the binop folder operates at unbounded integer precision when both operands are literal, with no intermediate range check. A literalInt only becomes a concrete numeric when one of the following fires:

  • Typed-location coercion via the literal-coercion helpers in src/ztypecheck.z. The helper reads nodeConst, applies the rule appropriate to the source/target combination (int→int range check; int→float exact mantissa; float→float round-trip; float→int rejected outright), and on success rewrites nodeType to the target. Wired sites: call arguments (checkCall), function implicit return (checkFunctionBody), reassignment RHS (checkReassignment), match-arm numeric patterns (checkCase), and if-/match-expression branch unification.
  • Bind-site materialisation via materialiseLiteral. Called from checkAssignment and unit-name resolution so a literal-typed RHS never escapes into long-lived storage (ZVariable.ztypeId, the resolution cache). Also wired into generic-arg inference (inferGenericConstruction, checkBoxConstruction) so the monomorphization key is keyed on the concrete default (e.g. id_i64, not id_literal_int).
  • Default-resolution late pass -- a final walk invoked from the module-level typecheck entry point after resolution returns. Walks ZTyping.nodeType and blindly replaces any remaining literal-typed entry with its concrete default (i64 for literalInt, f64 for literalFloat). No range check fires here — that is the coercion sites' job. Guarantees the emitter never sees a literal pseudo-type.

Method dispatch on literal-typed receivers (e.g. 5.iterate) follows the existing typedefBaseId walk. An early pass points literalInt.typedefBaseId at i64 and literalFloat.typedefBaseId at f64, so the operator-method lookup in checkBinop and child-name lookups elsewhere resolve through the concrete type without per-site isLiteral guards.

typesCompatible treats literal-vs-concrete-numeric as structurally compatible so multi-arm constructs unify cleanly; the range check happens at the typed-location coercion sites, not in the compat check.

Three typechecker gaps cover the remaining sites: record/class field-init type validation, data-block element type unification, and separable parameter defaults.

7.7. Type Narrowing

Type narrowing for union and variant types is tracked through scope-based overlay entries. When a match arm narrows a variable to a specific subtype, a narrowing entry is placed in the arm's scope. When the arm scope is popped, the narrowing resets automatically.

Post-match exclusion works by recording which subtypes were handled by diverging arms (arms that return or break). After the match scope is popped, exclusion entries are placed in the parent scope. Subsequent access to an excluded subtype produces a compile error.

Assignment-based narrowing (e.g., x: Result.ok 42) also places a narrowing entry in the current scope. Reassignment resets the narrowing.

If all branches of an if or match diverge, the parent scope is marked unreachable and subsequent statements are reported as dead code.

7.8. Synthesis Toolkit

The type checker may need to introduce nodes that did not appear in the parsed source -- temporaries introduced by per-call argument hoisting and the generator-lowering rewrites. These nodes are synthesised inline in src/ztypecheck.z (there is no separate synthesis module):

  • Fresh temp names -- a monotonic counter, ZTyping.nextTempId, yields names of the form _t0, _t1, ... in the order they are requested. The monotonicity matters: tests rely on the numeric suffix to assert source-order evaluation of call arguments.
  • Node construction -- synthesised AST nodes are built with a fresh node id, a defaulted source location, and a synthOrigin stamp.
  • Symbol-table registration -- a synth temp's ZVariable is registered in the current scope so downstream resolution finds it.

Every synthesised node carries a synthOrigin field (and ZVariable carries one in the symbol table). The field names the rewrite that introduced the node (for example, "anf" for per-call argument hoisting). It is persisted in the SQL dump (src/zsqldump.z) so rewrite provenance survives into post-mortem inspection.

Current consumers:

  • hoistArg in src/ztypecheck.z -- per-call atomic processing rewrites every non-trivial call argument to a synth temp inside a per-call sub-scope. See docs/ownership.pdoc:Per-Call Atomic Processing for the model.

8. Code Generator

The code generator (C emitter) walks the fully typed AST and emits C source code. The output is compiled by a C compiler (gcc/clang) to produce a native executable.

The emitter targets the C17 language standard (-std=c17 -Wall -Wextra). Emitted code relies only on designated initializers, fixed-width <stdint.h> types, and <stdbool.h>; no C23 features (typeof, constexpr, #embed) are used.

The emitter produces several output sections in order: struct/type definitions, forward declarations, function typedefs, function bodies, and a main() entry point. Each section is collected separately and assembled at the end.

8.1. Runtime-backed stdlib units

Six stdlib units -- system, core, collections, io, os, cli -- are runtime-backed: their types (String, File, the collections, the numerics) and their is native functions are implemented by the hand-written C runtime under src/runtime. The emitter never generates structs or type-method bodies for them (isEmittableFileUnit excludes the six from every type-emission pass); instead native FREE functions are declaration-driven: one emitter (emitNativeFreeFnCall) derives the C symbol z_<unit>_<name> from the resolved declaration and lowers every argument from the declared parameter types (StringView / StringLike params take a by-value view, class and borrowed-List params pass by pointer, take params pass the owned value, scalars pass verbatim) -- for both the dotted (io.remove) and bare same-unit call shapes. The C implementation lives in a conventionally-named fragment _Z_<UNIT>_<UPPER_SNAKE(name)>.inc under src/runtime/natives. Adding a native to a convention unit is a declaration plus a fragment -- no emitter edits; a new native-bearing unit is one line in isNativeRuntimeUnit (system/collections natives keep bespoke legacy symbols and their own legs). The make native-guard ratchet (run in make ci) asserts each is native declaration's fragment exists (with a small exceptions list for the stream/statement specials and two renames) and that every referenced _Z_* fragment is on disk.

Bodied free functions in these units are ordinary emitted zerolang (io.removeTree is the living example). They are demand-gated end to end, as every unit's are: resolved when a reference reaches them and walked with every other resolved body; the emitter correspondingly skips undemanded bodies in emitFnsIn and the literal pool, so an unused stdlib body cannot drag runtime fragments or unmaterialized monos into unrelated programs. Sibling natives may be called bare or dotted -- both shapes resolve through the declaration-driven native emitter -- and .take references to bodied stdlib functions work like any function reference (natives themselves have no reference form; they are call-only). A type method with a .z body in these units is a compile error (E0100): the type's methods belong to the C runtime.

8.2. C Name Generation

C names are the emitter's business -- the type checker composes none. At the start of emitC a single pass over the type registry fills a tid-indexed table on Ctx.cnames, and every emission site reads it back through ctxCname (a hole minted by allocType gets ). The table is built once from a frozen model, so a name cannot go stale, and one function composes every name, so a definition and its references cannot disagree.

The composer is zemitterc.cnameOf. Outside the table builder only two sites call it, both naming a symbol that no registered type owns: the flattened {base}.{member} of a dotted member access, and an as-block constant's {type}.{label}. Variable names go through ztypes.mangleVarName (C-keyword mangling of the emitted identifier only). The emitter-guard Makefile ratchet (run by make ci) pins the emitter's by-name resolution sites at their current floors, holds composeCname in the type checker at zero, and caps the z_t{id} spelling at the composer itself.

9. Id-based naming

A type's (and a non-native function's) C name is its monotonic id under the z_ namespace prefix: the type point with id 525 becomes z_t525_t, its add method (a function type of its own, id 527) z_t527. Derived symbols append a literal suffix to that base -- z_t525_create, z_t525_destroy, z_t525_meta_create. Because the id is unique by construction, names cannot collide: there is no dedup set and no on-collision suffix.

--readable-names switches the table to cnameOf, which appends the source name to the same base -- z_t525_point_t, z_t527_point_add. Nothing else changes, because the id is the unique part in both schemes and the name is pure decoration; it costs about 16% of the emitted file. A method's owner name comes from ZType.ownerTid, the id newType is handed at mint: the registry stores the id, never a composed string.

Three kinds of symbol keep a source name in both schemes. The hand-written runtime ABI -- native functions (z_io_open, z_String_create, ...) and the C entry point z_main -- must match C written by hand. Local variables go through mangleVarName; embedding a variable id is a separate, not-yet-applied step. And an as-block constant is named z_t{owner_id}_{type}_{label}, because several constants share their owner's id and only the label separates them.

The hand-written runtime (src/runtime/*.inc / *.c.tmpl / src/runtime/natives/) is authored with the canonical type spelling z_@Name@: each @Name@ is a hole. A fragment is read once per emit (cached by path in Ctx.tmplCache) and fillHoles rewrites it in a single scan, binding every hole to the id-named cname the registry gives that canon (collection monos, z_CpIter, parse-result monos included); a hole naming nothing the loader can resolve is fatal. Pure-C helpers (z_panic, z_xmalloc, z_siphash_*) spell no hole and are untouched.

9.1. Type Emission

Each zerolang type maps to a C representation:

  • Records → C structs (stack-allocated value types)
  • Classes → C structs, stack-allocated and passed by pointer; single-owner, with a generated destructor when they own heap-backed fields
  • Unions → tagged struct (tag + void* to data), stack-allocated; the active subtype's data is heap-allocated behind the void*
  • Variants → tagged struct with inline data union (stack-allocated)
  • Protocols → vtable struct + instance struct (dynamic dispatch via function pointers)
  • Facets → vtable + inline data union (value-type dynamic dispatch)
  • Enums → integer constants with a tag enum type

9.2. Memory Management

The emitter implements ownership-based memory management without a garbage collector.

String data buffers are heap-allocated and freed via z_String_free(). Class instances with owned fields are freed via generated z_<type>_destroy() functions that recursively free those fields.

The emitter tracks variables that need cleanup in a per-function scope. At scope exit (function return or fall-through), all owned variables are destroyed in reverse declaration order. Each type carries needsFieldCleanup, destructorName, and isHeapAllocated metadata set by the type checker, so the emitter delegates cleanup decisions to the type system.

Temporary values (intermediate results within a statement) are tracked separately and freed at the end of each statement. When a temporary is assigned to a named variable, ownership transfers and the temporary is removed from the free list.

The .take operation transfers ownership from one variable to another, nullifying the source to prevent double-free.

9.3. Unrecoverable Errors

All runtime-terminal exits route through a single helper emitted in the stdlib preamble of every program:

  static _Noreturn void z_panic(const char* msg) {
      fprintf(stderr, "zpanic: %s\\n", msg);
      exit(1);
  }

User-level panic msg: ... lowers to a direct call to this helper. Internal unrecoverable exit sites -- allocation failure in z_xmalloc / z_xcalloc / z_xrealloc, bounds checks on arrays, lists, listviews and stringviews, numeric cast overflow, empty-list pop -- all funnel through z_panic too, so every termination produces a zpanic: <msg> line on stderr and an exit code of 1.

Formatted messages (bounds with indices, numeric cast overflow) use a small stack buffer and snprintf at the call site to build the full message before invoking z_panic. The helper itself takes a plain const char* -- no variadic <stdarg.h> is pulled in. _Noreturn is C17 and lets GCC's control-flow analysis eliminate any "control may reach end of non-void function" diagnostics in callers that panic on every path.

Source location (.z file + line) is intentionally not included in the zpanic: output; the panic message text itself is the post-mortem link back to the emitting site.

9.4. Collection Choice

Compiler data structures follow a measured policy. Id-keyed tables (node stamps, declarations, registries) are IdMap / IdSet: a stack struct that costs no allocation while empty, a dense insertion-ordered entry array with no tombstone and no stored hash, and a slot taken from the key's own bits. Nothing is ever removed from one, which is what buys all three. A Map is what remains for the keys an id space cannot express -- a String, or a composite record -- and it is the only container of the two that is a heap object.

The representation crossing is inside the container, not in the code that uses it. An IdMap below its small-mode ceiling has no index array at all and find scans the dense entries; past it the index appears and the scan becomes a probe. So a declaration's namespace is one field that answers both questions asked of it -- children.get is the lookup and the same entries in order are the walk -- where it was once a list plus a lazily built by-name map, and every reader carried the crossing as a branch.

Small, per-instance state that deletes (the emitter's narrowing and alias lists) stays an assoc-list: at a handful of entries a linear row scan beats a probe, and an append-only container cannot serve it at all. Hot String-keyed lookups are avoided outright: resolution goes through interned ids and two-argument (unit, name) probes rather than composed "unit.name" key strings.

9.5. Stamp-Driven Emission

The emitter is a mechanical typed-AST-to-C pass: it reads what the type checker stamped and compares by id, never re-resolving names. An atom reference carries atomVariableId (a local) or atomUnitDefId (a unit definition); a call carries its callKind, which routes constructions to their owning handler ahead of the probe chain. Member types are canonicalized at the end of typechecking (canonicalizeShellChildren), so a field or parameter type id is the real defining type, not a name-minted shell. Ownership, mono-origin and String/StringView tests compare enum values and cached canonical ids (declOwnershipOfId, originIsTid, ctx.strTid / svTid). The residual by-name sites -- generic-template re-emission, the probe-chain fallbacks -- are counted and pinned by emitter-guard. Internal impossibilities (an unresolvable typedef base, an unspellable field type) panic with a zemitterc: message instead of emitting a silent fallback type.

10. Bootstrapping & self-hosting

The compiler is self-hosted: it is written in zerolang (src/*.z) and compiles itself. Building and testing it require only a C toolchain -- no Python, and no shell scripts.

10.1. The bootstrap chain

The sources are compiled by a seed: bootstrap/zc.c, a committed, self-emitted C dump of the compiler. cc bootstrap/zc.c alone yields a working zc.

  • make bin/zc builds the seed (out/zc-seed), then uses it to emit and compile the current src/*.z into bin/zc, the live self-hosted compiler.
  • make test-bootstrap proves the loop converges: the seed builds a compiler, which rebuilds itself to a byte-identical fixpoint (b2 == b3).
  • make bump-seed regenerates bootstrap/zc.c from a fresh bin/zc when the sources have drifted far enough that the seed lags.

10.2. Building and testing

The test runner and the style linter/formatter are themselves zerolang programs (src/ztestrunner.z and src/zl.z), so the whole build-and-test pipeline is portable to any platform with a C compiler.

  • make check -- the fast style gate (zl lint: the parse/token/whitespace checks -- empty clauses, first-argument elision, redundant for while, trailing whitespace, final newline, colon and blank-line spacing).
  • make style-lint -- adds the typecheck-tier redundant numeric-suffix check (zl lint --full) and a formatter check (zl fmt --check).
  • make test -- the self-hosted corpus runner (src/ztestrunner.z): behavioural, leak, negative, dump and differential kinds, all driven via os.spawn.
  • make ci -- the full gate: style-lint, the corpus runner under --heavy (adds the self-host ASan and byte-identity fixpoint kinds), and the seed bootstrap.
