1. Introduction

The compiler, zc, turns a program's units into C and hands the C to a C compiler. Its stages run in this order, each taking what the one before it gives:

  1. the Virtual File System presents the source roots as one tree;
  2. the Tokenizer and the Lexer turn a unit's text into tokens;
  3. the Parser builds the syntax tree of every unit the program names;
  4. Generator Desugaring prepares each generator for the checker;
  5. the Semantic Analyser checks types, ownership and locks, and records what it finds;
  6. the Code Generator writes the C.

Each section below says what its stage takes and gives, and links to the page that owns its detail. zc gives the command line.

2. Virtual File System

A simple readonly Virtual File System (VFS) is used to present a unified source tree to the compiler.

The VFS allows union or bind mounts to mount one filesystem over another. The VFS tree presented to the compiler is usually the system directory with the user source directory union mounted over it, so a user unit is found first and shadows a system unit of the same name.

The VFS allows abstraction over a source tree that may be arbitrarily complex while providing a simple interface to the compiler. The VFS tree can be built from multiple physical filesystems or can be built from alternate data stores (such as databases or remote systems).

3. Tokenizer

The Tokenizer splits a single top level unit aquired from the VFS (usually represented by a file) into a stream of tokens. Every part of the source becomes part of a token and so the original source could be recreated by concatenating all of the tokens returned by the tokenizer.

The tokenizer splits the file into tokens such as:

  • horizontal whitespace (spaces and tabs only)
  • end of line
  • comments
  • identifiers
  • keywords
  • delimiters such as (, ), { and }
  • dot operator: .
  • parts of string literals (raw and interpolated)
  • numeric literals
  • error tokens

The tokens have a type, the string contents and an identifier for the file that they are contained within and the location (line and column) within that source file.

The tokenize unit gives the tokenizer and the lexer to programs; its page owns their detail.

4. Lexer

The Lexer provides another layer over the Tokenizer to ease the job of the parser which will follow.

The Lexer filters comments and whitespace as these are not used by the parser. It also keeps a small stack to maintain context for handling end-of-line (EOL).

In Blocks (the top level of a unit or a brace delimitered block), multiple EOL's are coalesced into a single EOL token. In parenthesized expressions, all EOL's are ignored. In string literals, all EOL's are passed through as-is and form part of that string literal.

The Lexer buffers one token of lookahead, and never copies it out. A rule that wants to know what comes next asks peekType for the token type or peekPos for a tokpos -- a valtype spanning the token: fsno, line, column, and the text's byte width, which is everything a diagnostic needs from the text without the text itself. A rule that must read the characters asks peekTextId for the text's id in the name pool, where every token's text is interned.

Everything the Lexer hands out copies out: a tokpos and a pool id are both plain values, so a rule can capture where its construct began, or what it was called, and still use it a hundred lines and several advance calls later. Consuming a token is free: accept / acceptAny move the buffered token out rather than duplicating it.

5. Parser

The parser creates an abstract syntax tree (AST) from the source units supplied. The ast unit gives the parser and the tree to programs; its page owns the tree's shape. It begins with the 'core' system unit and the user 'main' unit and parses each, loading further units as they are referred to.

The parser resolves no names. After a unit is parsed, one walk over its body (collectExterns) collects the identifiers the unit refers to but does not bind -- biased to over-collect, since a spurious name simply fails to name a file -- and for each such name the VFS is asked for <name>.z: first in the directory named after the current unit and lying beside its file (an implementation subunit), for every name and a core name too, then in the source tree and the system library. A unit found this way is parsed the same way, recursively, until the worklist is empty. Whether a name actually denotes a unit, a type, or a variable is the type checker's question, asked in the environment it builds from the finished AST; a public: block's entries count as references, so a listed hidden subunit loads on the strength of the listing alone.

The parser returns the first syntax error found immediately. It does not attempt to reset and continue.

A parse has two phases: the prelude -- core and every unit it names, read as .z whatever kind of file the parse reads -- then the main unit and what it names. Parses in one process share the prelude through a zparser.PreludeStore (Parser.parseShared): zc checks a project's project.zd and then builds each program, zl lint --full checks each file it is given and its project, and each parse after the first reads on from a copy of the tree the first one kept after its prelude. It does so only when every lookup that found the prelude's files -- each name walked from the root, or the folder beside a unit's file -- finds the same files on disk in that parse's own file view; otherwise (a source root holding a unit of the same name, another stdlib) it reads the prelude itself. zl fmt, which rewrites files as it goes, and zls, which runs for as long as the editor does, keep nothing.

6. Generator Desugaring

A generator declaration is a class whose call suspends. Generator lowering (helpers in src/zgenerator.z, driven by lowerDeclaredGenerators in src/ztypecheck/memberaccess.z) prepares each one: it adds what the suspension transform needs to the declaration the author wrote, so the rest of the typechecker sees an ordinary class. The lowering runs early in the typecheck pass, before the definitions are indexed and before bodies are checked; frozen AST nodes are never mutated.

Pipeline placement:

  Lex -> Parse -> Typecheck (lower generators, then resolve + check) -> Emit

6.1. What the pass adds

A generator is a DECLARATION, so the class is the author's and the pass adds only what the suspension transform needs. For

G: generator { f1: T1 ... } as { call: function {in: K} out E is { ... } }

it produces approximately

  G: generator {
      f1: T1                   # the author's fields, untouched
      state: i64               # state-machine cursor, appended
      _fc_N: i64               # one per suspending counted `for`
      _yv_N: K                 # one resume slot per suspension point
      _resume_input: K         # only when `call` declares an input
      <local>_N: T             # one per body local, minted by the checker
  } as {
      call: function {:this in: K} out (option-wrapper-for-E) is {
          # the author's body with its yields intact and the call-built
          # iterables of its suspending `for each` loops hoisted into locals
          # (any other new iterable the checker keeps in a state field) --
          # the state machine is the emitter's job
      }
      create: function {f1: T1.take ...} outx this is {
          return (meta.create state: 0 :f1 ...)
      }
  }

The receiver and the wrapper are injected into the author's call; the create is generated from the is fields, with each parameter's ownership following the field it fills. The pass runs BEFORE the definitions are indexed, because it appends fields to a definition the author wrote and indexing binds a definition's members where it stands. Numeric suffix on collision.

6.2. Body locals

The body resumes in a later call, so nothing it keeps may live on the C stack of .call. The pass rewrites no local: to the checker a body local is an ordinary local, with its own variable, scope, moves and invalidation, and only where it is stored differs. Binding a local in a generator's call body, the checker mints a field of the instance for it -- one per variable, named <name>_N so it collides with nothing else the instance holds, typed by the variable's own type (bindGenLocal and mintGenField in src/ztypecheck/valuechecks.z) -- and records it in genLocalFieldOf. The emitter stores into the field where the local is bound and spells every later use of the local as the field (emitGenLocalBind in src/zemitterc/stmtblocks.z). A binding frees what the field held before -- a loop body binds its locals afresh on every pass -- and the instance's destructor frees what the field holds last.

Two kinds of local are not kept. A yield value (a: yield e) lives in its resume slot. A borrow of a place -- another local, a field, an element -- is a pointer into it, stays a C local, and may not be in scope at a yield (reportBorrowsAtYield). A view is a value like any other, and is kept. The payload a suspending loop binds, the iterable it constructs and the owned value of a suspending with are the checker's fields as well (mintForSpillFields, withValueField).

6.3. State-machine codegen

The emitter (src/zemitterc/forloops.z) routes any function whose synthOrigin == "generator-call" through a dedicated state-machine path. Helpers emitGenPrologue, emitYieldStmt, and emitGenEpilogue assign one state number per yield (entry = 0, terminal = -1) and emit:

  switch (this->state) {
      case 0:  goto L_entry;
      case 1:  goto L_resume_1;
      ...
      default: goto L_done;
  }
  L_entry:
      /* original code up to first yield */
      this->state = 1;
      return OPTION_SOME(<yield expr>);
  L_resume_1:
      /* if takes != null: bind local from this->_resume_input */
      ...
  L_done:
      this->state = -1;
      return OPTION_NONE;

C17 goto plus switch arbitrates cleanly, with no compiler extension. The yield-state numbers are pre-allocated from the function's yield count (fnYieldCount) so the prologue, body fragments, and epilogue agree.

6.4. Termination + bidirectional value flow

A bare return anywhere in the body or fall-through past the last yield transitions to the terminal absorbing state. return <value> is rejected during desugaring. Code placed after the last yield runs on the call that crosses into terminal; it does not run on early drop, where class destruction releases locks and destroys owned fields via the standard class-lifetime path.

For accepts: K generators, buildCallMethod adds a value: K parameter; the generated prologue emits an entry-time store of value into this->_resume_input (destroying any prior owned value first). Expression-form yield (x: yield v) in the body reads this->_resume_input after the resume label so x binds to the caller's most recent input. The first reachable yield must be statement form -- the desugarer rejects expression-form first-yields, reflecting that the resume-input slot is undefined before the first .call value: arrives.

7. Semantic Analyser

The semantic analyser, the typechecker, takes the syntax tree and gives the model the code generator reads: a type for each node, and the ownership, lock and narrowing facts of every body (ZTyping), beside the type registry. It is demand-driven: it starts from main and checks only what a reference reaches. The typechecker owns its detail:

  • demand-driven resolution and cycle detection;
  • monomorphisation -- each instance of a generic definition checked from its own copy;
  • ownership and lock checking;
  • numeric literal coercion and type narrowing;
  • the nodes it synthesises.

The ownership rules as a program meets them are in Ownership.

8. Code Generator

The code generator (C emitter) walks the fully typed AST and emits C source code. A C compiler -- gcc, clang, tcc, mingw-w64 or MSVC -- compiles the output into a native executable.

The emitter targets the C17 language standard (-std=c17 -Wall -Wextra). The one thing beyond C17 the output may need is the type of an expression, for a temporary whose type the emitter has no C text for: the Z_TYPEOF macro spells it typeof under C23 and __typeof__ otherwise, which each of those compilers takes in C17 mode.

The emitter produces several output sections in order: struct/type definitions, forward declarations, function typedefs, function bodies, and a main() entry point. Each section is collected separately and assembled at the end.

8.1. The files of the emitter

The emitter is one unit, zemitterc, written in fifteen files: the unit's own file and the fourteen implementation subunits of the folder src/zemitterc/. A subunit reads the unit's definitions by their bare names; the unit's other files name it as file.name. emitC, the one entry point, is in emitplan.z and listed in the public: block of src/zemitterc.z as emitC: emitplan.emitC.

FileWhat it holds

emitplan.zwhat is written and in what order: units, functions, reach, C names

nativerows.zthe native rows and templates a program uses: keys, holes, fills

Two values travel through it. prog: Program is the program as the checker left it -- the tree, the type registry and the checker's tables, read-only -- and every function that reads the program takes it. ctx: Ctx is what the emission has written and decided so far; its parts are records of their own (ctx.pieces, ctx.reach, ctx.stmt, ctx.gen, ctx.order, ctx.known, ctx.narrow, ctx.literals, ctx.typeDefs, ctx.plan), and a function that touches only one part takes that part in place of ctx.

Reading order: emitC (emitplan.z) for the order things are written in; stmtblocks.z and values.z for a function body; callorder.z and argforms.z for a call; the rest by concern.

8.2. The backend contract

The front end -- lexer, parser, type checker, generator lowering -- knows no backend. It hands one over a checked program: the AST, the type registry and the ZTyping model, every value it can answer already a constant of the program, and the set of units the program reaches (ZTyping.unitsReached). What it decides holds for every backend: whether a program is legal, the language's own sizes (a union's slot is 8 bytes on every target). It knows nothing of the target: the drivers resolve the triple (src/ztarget.z) and write what the build is for into the generated z unit (z.build.os, z.build.arch), whose values are ordinary constants the checker folds like any other. It never reads a toolchain. The test runner's pins kind holds its code to no C spelling, no triple parse and no read of the target.

A backend supplies the rest:

  • an implementation of every is native declaration, refusing at the declaration one it has none for -- the C backend's are the rows of each unit's nativec.zd, which zc carries in itself (see Native Units);
  • its representation of each type, holding every value the language's rules admit -- the C backend gives a type the C compiler lacks (i128, u128, f16) a struct and helper functions, and the C preprocessor, not zc, picks between that and the compiler's own type;
  • what a reached unit needs of its toolchain, and the refusal of a toolchain that lacks it, by name and before anything is compiled -- the C backend's are a unit's links, sources and refusals in its nativec.zd: system.quadfloat needs __float128, which tcc and MSVC have none of and only x86-64 targets have, and links libquadmath; sqlite needs its vendored C source compiled (a source with its defines), which the driver builds into its object cache with the compiler that links.

8.3. Runtime-backed stdlib units

Five stdlib units -- system, core, collections, io, os -- are runtime-backed: their types (String, File, the collections, the numerics) and their is native functions are implemented in C by the rows of each unit's nativec.zd (lib/system/<unit>/nativec.zd), which zc carries in itself. The emitter never generates structs or type-method bodies for them; instead native FREE functions are declaration-driven: one emitter (emitNativeFreeFnCall) derives the C symbol z_<unit>_<name> from the resolved declaration and lowers every argument from the declared parameter types (StringView / StringLike params take a by-value view, class and borrowed-List params pass by pointer, take params pass the owned value, scalars pass verbatim) -- for both the dotted (io.remove) and bare same-unit call shapes. The C implementation is the fragment of the function's row, keyed by its name, in its unit's nativec.zd. Adding a native to a convention unit is a declaration plus a row -- no emitter edits; a new native-bearing unit is a nativec.zd of its own and a place in the foundation's order (system/nativec.zd), which is the order emitRuntimeUnit walks. The make native-guard ratchet (run in make ci, zc natives check rows) asserts that each is native declaration of a unit with rows has a row, that every hole a text spells names a declared type, arm or member, and that the numeric conversions' rows are the ones the numeric rule gives.

A class's native methods are rows of their own, keyed <Class>.<method> in its unit's file, whose fragment defines <Class>_<method> called with the receiver's address and each argument by one rule decided by its type (a value view by value, an owned collection by address); a protocol slot takes the same, so a native method fills a vtable as it is. An entry of the unit's classes (with live and destroy) makes a class the runtime's: its struct is written ahead of the fragments that read it, once the class is live or used, and destroy is the C that releases what the declaration cannot show (an fd, a database handle). io.File, net.Listener / net.Conn and sqlite's classes are all this one mechanism. A row names its unit and type by spelling, and applies only to a declaration that is native or declares something native, so a user unit that shadows a stdlib one by name gets none of its rows.

Bodied free functions in these units are ordinary emitted zerolang (io.removeTree is the living example). They are demand-gated end to end, as every unit's are: resolved when a reference reaches them and walked with every other resolved body; the emitter correspondingly skips undemanded bodies in emitFnsIn and the literal pool, so an unused stdlib body cannot drag runtime fragments or unmaterialized monos into unrelated programs. Sibling natives may be called bare or dotted -- both shapes resolve through the declaration-driven native emitter -- and .take references to bodied stdlib functions work like any function reference (natives themselves have no reference form; they are call-only). A type method in these units may be a .z body, and u8.times and its seven siblings are: they construct an intrange and hand it back, and they emit and run like any other method.

A method body is demanded per MEMBER, as a free function is: resolving a type walks only the bodied members the program uses (bodiedMemberDeferred), asked from usedMemberDecl. A walk MINTS whatever the body constructs, so walking every member of every type a program touches would land those types in its C -- every program touches the scalars, so a bodied u8.times would be walked and emitted by every compile. Code that is never reached must parse; it is not typechecked, and zl lint --full and --eager check it.

A use is any reference that reaches the member, not only a dotted read: an operator, a construction (a written create), a call or for over a callable object (its call), a list's contains, == and sort (the element's == or compare), a Map or Set key (its hash and ==), the generated == every value type is emitted with (each part's own), and a function field naming a sibling method. A implementation uses every member its spec names, on the implementer and on each link of a typedef standing in for it: the vtable wrapper is emitted from the implementation row, not from a use site. A use of a generic instance's member uses the template's too, whose walk reports on the body, and each instance -- of a generic type or of a generic unit -- walks and emits only the members used on it (instanceMemberOwed), revisited when a later use reaches another. A use found after the owner walked has its member walked then (walkLateUsedBodies). forceOwnerMember is asked BELOW the gate, because forcing a member mints its return type and would drag the types in regardless. The emitter writes a method body only when the checker walked it. --eager walks everything, which is the point of it.

With the gate, a bodied times on all eight scalars costs ONE line of C in a program that never iterates.

8.4. C Name Generation

C names are the emitter's business -- the type checker composes none. At the start of emitC a single pass over the type registry fills a tid-indexed table on Ctx.cnames, and every emission site reads it back through ctxCname (a hole minted by allocType gets ). The table is built once from a frozen model, so a name cannot go stale, and one function composes every name, so a definition and its references cannot disagree.

The composer is cnameOf (src/zemitterc/emitplan.z). Outside the table builder only two sites call it, both naming a symbol that no registered type owns: the flattened {base}.{member} of a dotted member access, and an as-block constant's {type}.{label}. Variable names go through mangleVarName (src/zemitterc/localnames.z; C-keyword mangling of the emitted identifier only). The test runner's pins kind (run by make test) pins the emitter's by-name resolution sites at their current floors and caps the z_t{id} spelling at the composer itself (src/ztestrunner/expected.z holds each pin).

8.5. Id-based naming

A type's (and a non-native function's) C name is its monotonic id under the z_ namespace prefix: the type point with id 525 becomes z_t525_t, its add method (a function type of its own, id 527) z_t527. Derived symbols append a literal suffix to that base -- z_t525_create, z_t525_destroy, z_t525_meta_create. Because the id is unique by construction, names cannot collide: there is no dedup set and no on-collision suffix.

--readable-names switches the table to cnameOf, which appends the source name to the same base -- z_t525_point_t, z_t527_point_add. Nothing else changes, because the id is the unique part in both schemes and the name is pure decoration; it costs about 16% of the emitted file. A method's owner name comes from ZType.ownerTid, the id newType is handed at mint: the registry stores the id, never a composed string.

Three kinds of symbol keep a source name in both schemes. The hand-written runtime ABI -- native functions (z_io_open, z_String_create, ...) and the C entry point z_main -- must match C written by hand. An as-block constant is named z_t{owner_id}_{type}_{label}, because several constants share their owner's id and only the label separates them. And a struct member has no id space at all: its namespace is the struct, so nothing but a C reserved word can collide with it, and a field named default would emit int64_t default;. Every spelling of a member therefore goes through memberCName -- the declaration, the reads and writes, the constructor parameters, the destructor, the generated _eq, and the four spellings of an interface vtable slot that cSlotName keeps in step. They must agree: a mangler applied at the declaration and not at a read emits b.v_default against a field named default.

Local variables have an id space of their own: a binding the type checker gave a variable id emits z_v{id}, and only a site no id reached falls back to the source name through mangleVarName, which dodges the C reserved words. --readable-names puts the source name in front of the id (n_5). The id is still what makes the name unique: a source name is unique only inside the scope that binds it, while a bare block is flattened into its enclosing C block, so two sibling scopes binding n emit n_5 and n_9. It also keeps a local clear of the macros system headers define -- near and FAR in windows.h, errno and stdin in the C runtime -- which no list of reserved words could cover.

The native C (the rows, templates and fixed files of the nativec.zd files) is written with the canonical type spelling z_@Name@: each @Name@ is a hole, and each @@KEY@@ in a template a key its writer binds. Every native text -- a row's body, a template, a fragment, a fixed file -- is parsed once, when it is first read (RtTexts): cut into literal stretches, holes and keys, with its member sections or row pieces found. A fill walks the stretches once, binding every hole to the id-named cname the registry gives that canon (collection monos, z_CpIter, parse-result monos included) and every key to the text its writer bound, and writes only the sections and pieces the program keeps; a value put in a hole is never searched again. A hole naming nothing the loader can resolve is fatal. Pure-C helpers (z_panic, z_xmalloc, z_siphash_*) spell no hole and are untouched.

8.6. Type Emission

Each zerolang type maps to a C representation:

  • Records → C structs (stack-allocated value types)
  • Classes → C structs, stack-allocated and passed by pointer; single-owner, with a generated destructor when they own heap-backed fields
  • Unions → tagged struct (tag + void* to data), stack-allocated; the active subtype's data is heap-allocated behind the void*
  • Variants → tagged struct with inline data union (stack-allocated)
  • Protocols → vtable struct + instance struct (dynamic dispatch via function pointers)
  • Facets → vtable + inline data union (value-type dynamic dispatch)
  • Enums → integer constants with a tag enum type

8.7. Memory Management

The emitter implements ownership-based memory management without a garbage collector.

String data buffers are heap-allocated and freed via z_String_free(). Class instances with owned fields are freed via generated z_<type>_destroy() functions that recursively free those fields.

The emitter tracks variables that need cleanup in a per-function scope. At scope exit (function return or fall-through), all owned variables are destroyed in reverse declaration order. Each type carries needsFieldCleanup, destructorName, and isHeapAllocated metadata set by the type checker, so the emitter delegates cleanup decisions to the type system.

Temporary values (intermediate results within a statement) are tracked separately and freed at the end of each statement. When a temporary is assigned to a named variable, ownership transfers and the temporary is removed from the free list.

A value that has no address -- a call's result handed to a parameter that takes a pointer, a receiver read through, a value read twice -- is bound to a statement temporary first (hoistForAddress in src/zemitterc/argforms.z). Every such temporary owes a destroy by one rule: exactly when the checker's temporary for that value node still owns what it holds where it dies (scopeOwnsTemp, read from the checker's per-scope temporary record). A borrow the call's result shares, a value moved out on the way, and a pointer into storage something else owns owe none. The emitter never decides ownership from the shape of what it hoists; a hoist with no node to ask about holds a value that owns nothing, and says why where it is written.

A value written where a protocol or a facet is expected, without a projection of its own, stands in for the spec. The type checker records each stand-in that holds (standInOf, keyed by the value's node, with the spec and whether the place owns it), and the emitter boxes that node as the spec wherever a slot spells it -- an argument of any call form, an operator operand, a field, an element, a reassigned value, a return (implementationArgText): the box a P.create from: x of the same value builds, owned where the place owns a protocol value, borrowed otherwise.

The .take operation transfers ownership from one variable to another, nullifying the source to prevent double-free.

8.8. Unrecoverable Errors

All runtime-terminal exits route through a single helper emitted in the stdlib preamble of every program:

  static _Noreturn void z_panic(const char* msg) {
      fprintf(stderr, "zpanic: %s\\n", msg);
      exit(1);
  }

User-level panic msg: ... lowers to a direct call to this helper. Internal unrecoverable exit sites -- allocation failure in z_xmalloc / z_xcalloc / z_xrealloc, bounds checks on arrays, lists, listviews and stringviews, numeric cast overflow, empty-list pop -- all funnel through z_panic too, so every termination produces a zpanic: <msg> line on stderr and an exit code of 1.

Formatted messages (bounds with indices, numeric cast overflow) use a small stack buffer and snprintf at the call site to build the full message before invoking z_panic. The helper itself takes a plain const char* -- no variadic <stdarg.h> is pulled in. _Noreturn is C17 and lets GCC's control-flow analysis eliminate any "control may reach end of non-void function" diagnostics in callers that panic on every path.

Source location (.z file + line) is intentionally not included in the zpanic: output; the panic message text itself is the post-mortem link back to the emitting site.

8.9. Collection Choice

Compiler data structures follow a measured policy. Id-keyed tables (node stamps, declarations, registries) are IdMap / IdSet: a stack struct that costs no allocation while empty, a dense insertion-ordered entry array with no tombstone and no stored hash, and a slot taken from the key's own bits. Nothing is ever removed from one, which is what buys all three. A Map is what remains for the keys an id space cannot express -- a String, or a composite record -- and it is the only container of the two that is a heap object.

The representation crossing is inside the container, not in the code that uses it. An IdMap below its small-mode ceiling has no index array at all and find scans the dense entries; past it the index appears and the scan becomes a probe. So a declaration's namespace is one field that answers both questions asked of it -- children.get is the lookup and the same entries in order are the walk -- and no reader carries the crossing as a branch.

Small, per-instance state that deletes (the emitter's narrowing and alias lists) stays an assoc-list: at a handful of entries a linear row scan beats a probe, and an append-only container cannot serve it at all. Hot String-keyed lookups are avoided outright: resolution goes through interned ids and two-argument (unit, name) probes rather than composed "unit.name" key strings.

8.10. Stamp-Driven Emission

The emitter is a mechanical typed-AST-to-C pass: it reads what the type checker stamped and compares by id, never re-resolving names. An atom reference carries atomVariableId (a local) or refDecl (the declaration it resolved to); a call carries its callKind, which routes constructions to their owning handler ahead of the probe chain. Member types are canonicalized at the end of typechecking (canonicalizeShellChildren), so a field or parameter type id is the real defining type, not a name-minted shell. Ownership, mono-origin and String/StringView tests compare enum values and cached canonical ids (declOwnershipOfId, originIsTid, ctx.strTid / svTid). The residual by-name sites -- generic-template re-emission, the probe-chain fallbacks -- are counted and pinned by the pins kind. Internal impossibilities (an unresolvable typedef base, an unspellable field type) panic with a zemitterc: message instead of emitting a silent fallback type.

8.11. Evaluation Order

A call's arguments and an operator's operands are evaluated in the order they are written (spec: Call Arguments, Operations), and C leaves both unsequenced. The emitter keeps the order with ordered temps: a part is read into an _oN temp ahead of the call, in a comma expression, when something evaluated after it could change what it reads or see what it does. A part that only reads -- no call, assignment, increment, comma or block, as the facts its producer states say -- needs no temp when every part after it only reads too: a + b, p.x + p.y and pair a: y.v b: (y.v + 1) are plain C. A part that may write needs one only when a part that is not constant follows it. h.bump + h.count keeps a temp for h.bump, and x.v + (addTo c: x d: 1) one for x.v. A literal, a folded constant and a plain address never need one. order_pure_parts pins each case by running it.

9. Bootstrapping & self-hosting

The compiler is self-hosted: it is written in zerolang (src/*.z) and compiles itself. A C toolchain is the only requirement to build and test it.

9.1. The bootstrap chain

The sources are compiled by a seed: bootstrap/zc.c, a committed, self-emitted C dump of the compiler. cc bootstrap/zc.c alone yields a working zc.

  • make bin/zc builds the seed (out/zc-seed), then uses it to emit and compile the current src/*.z into bin/zc, the live self-hosted compiler.
  • make test-bootstrap proves the loop converges: the seed builds a compiler, which rebuilds itself to a byte-identical fixpoint (b2 == b3). Under make ci it runs that chain for gcc, clang and the vendored tcc, and asserts the three emit byte-identical C — so "any C toolchain" means they agree, not merely that each works.
  • make bump-seed regenerates bootstrap/zc.c from a fresh bin/zc when the sources have drifted far enough that the seed lags.

9.2. Building and testing

The test runner and the style linter/formatter are themselves zerolang programs (src/ztestrunner.z and src/zl.z), so the whole build-and-test pipeline is portable to any platform with a C compiler.

  • make check -- the fast style gate (zl lint: the parse/token/whitespace checks -- empty clauses, first-argument elision, a first argument written with the name it may leave out (for while), trailing whitespace, final newline, colon and blank-line spacing).
  • make style-lint -- adds the typecheck-tier redundant numeric-suffix check (zl lint --full) and a formatter check (zl fmt --check).
  • make test -- the self-hosted corpus runner (src/ztestrunner.z): behavioural, leak, negative, dump and differential kinds, all driven via os.spawn; the lone kind, which writes one unrelated error into each behavioural case's main and requires that error and no other; the doccode kind, which compiles every zerolang example in the documentation (see the style guide's "Examples in Documentation"); and the docpage kind, which requires each committed docs/*.html to be what the renderer writes from its .pdoc (make docs), and each link from one page to another to name a page that exists and an anchor it defines; and the usage kind, which runs a driver (zl, the runner itself) on a command line it must refuse, and requires the sentence on stderr and the exit code its case states (tests/fixtures/usage/). The runner reads its own command line as strictly: an option it does not declare, an option with no value, a number that is none and an operand are each refused with exit 2, and ztestrunner --help lists its flags.
  • make doc-check -- the doccode and docpage kinds alone.
  • make ci -- the full gate: style-lint, the corpus runner under --heavy (adds the self-host ASan and byte-identity fixpoint kinds), and the seed bootstrap.
