1. Synopsis

zc <command> [arguments] [flags]

2. Description

zc is the self-hosted zerolang compiler. A command is required: it compiles a zerolang unit (.z) and links it into a native executable (build), builds and runs it (run), emits C (emit), dumps the compiler's internal model (dump), explains a diagnostic code (explain), prints resolved settings (env), or lints and formats source (lint / fmt, thin shims for the standalone zl tool).

The compiler operates on units — each source file defines a unit, and dependencies are discovered automatically through the Virtual File System (VFS), which mounts the user source directory over the system library so user units shadow system units of the same name.

The unit named on the command line must declare main: function is { ... }. Compilation is demand-driven: main is the root, and what it reaches is what gets checked and emitted, so a unit without one has nothing to compile it from (E0039). Such a unit is a library — compile the program that opens it instead. Two modes ask a different question and so need no root: dump, which introspects a unit rather than building it, and --eager, which resolves every definition rather than what a root reaches (which is why zl lint --full and the language server are unaffected).

zc is self-locating: run from any directory, it finds its bundled standard library and runtime relative to its own executable (see Tree resolution), so ordinary use needs no flags.

3. Commands

The first argument is always a command. A bare unit name with no command is an error — use zc build <src>.

  • build <src> — compile to a native executable; output is -o OUT or ./<unit>.
  • run <src> [args...] — build to a temporary file, then run it with an inherited terminal, forwarding the trailing args and propagating the program's exit code.
  • emit <src> — emit standalone C source to -o OUT (or stdout).
  • dump <src> — write the typecheck model as SQL (-o or stdout); --canon writes the id-normalized model instead.
  • natives — print the conversions section of src/runtime/natives.tbl, derived from the numeric rule. The table holds the C for every is native declaration, keyed by qualified path, and the 256 numeric conversions are generated rather than written by hand: a bound wrong on a pair no program happens to use is not something the test corpus can catch. make natives-tbl-guard regenerates and diffs, so the table is provably the rule's own output.
  • explain <code> — print an explanation for a diagnostic code, for example zc explain E0200.
  • env — print resolved tool paths and settings (see Inspecting the environment).
  • lint [args...] and fmt [args...] — thin shims that locate the sibling zl binary (the standalone linter/formatter), forward the arguments, inherit the terminal, and propagate its exit code. The rules, flags and formatter semantics live in docs/zl.pdoc. make check invokes bin/zl directly.
  • version — print the version line (see The version line).
  • help [command] — print usage, or detailed help for one command.

For run, flags before the unit configure the build; everything after the unit (or after a -- separator) is passed to the program.

zc build hello                # build ./hello
zc run hello arg1 arg2        # build + run, forwarding arg1 arg2
zc build hello --release -o hello
zc emit hello -o hello.c
zc explain E0200

-h / --help and -V / --version are also accepted in any position, so zc build --help prints the help for build.

4. The source argument

build, run, emit, and dump take a <src> — either a unit name (hello) or a path to a .z file (hello.z, ./sub/hello.z). A path — anything containing / or ending in .z — sets --src to the file's directory and the unit to its base name, unless --src is given explicitly.

Because the command always comes first, a unit whose name collides with a command is reached through the explicit form: zc build run or zc build ./run.z to build a unit named run.

5. Flags

5.1. Global flags

These are accepted in any position.

  • -h / --help — print usage; after a command, print that command's help.
  • -V / --version — print the version line (see The version line).

5.2. Build flags

These apply to build, run, emit, and dump.

  • --src DIR — user source directory (default: the current directory).
  • --system DIR — system library directory (default: self-located).
  • --runtime DIR — C runtime fragment directory (default: self-located).
  • -o OUT — output path (the executable for build, the C file for emit, the model for dump).
  • --release — optimize (-O2); the default is a debug build (-O0 -g).
  • --save-temps — keep the generated C file and print its path (build / run).
  • --cc CC — the C compiler to invoke. A bare tcc resolves to the one this tree vendors (see The vendored tcc).
  • --cc-mode spawn|inproc — how to reach that compiler: run it as a child process (the default), or load it into this one. Orthogonal to --cc, which names the compiler itself. There is no auto and no fallback: an unavailable inproc is an error, not a silent spawn.
  • --tcc-lib DIR — where tcc's runtime payload lives; only tcc reads it (see The vendored tcc).
  • --target TRIPLE — cross-compile (see Cross-compilation).
  • --cflags STR / --ldflags STR — extra compiler / linker flags, split on spaces.
  • --fast-hash — emit Map / Set hashing on the wyhash-style fast path instead of the default seeded SipHash-1-3. Faster, but not hash-flood resistant: use only when map keys are trusted input. Program output is unaffected (iteration order is insertion order).
  • --readable-names — name emitted types and functions z_t{id}_{name} instead of the default z_t{id}. The id alone is unique, so the source name is decoration: it costs about 16% of the emitted file and is worth paying only when reading the C, as when debugging the compiler. Pairs with --save-temps.
  • --eager — resolve every definition of every unit, not only the ones a use site reaches. An error inside a definition nothing references — an unused record's field type, a union arm named only by a generic constraint — is reported by nothing without this. The editor path (zls, zl lint --full) always resolves eagerly. A branch whose condition folds to false is reached by no use site either, so it is resolved only under this flag. That makes --eager over-approximate what a program needs from the toolchain: a guarded f128 branch that an ordinary build elides is resolved here, so the link line may name a library the same build without the flag does not.
  • --strict-call-locks — a :name shorthand argument takes a real call-scoped lock at a lock/borrow parameter, exactly as the written-out name: name form does. Off by default: the compiler's own tree still carries E0200s under the rule, counted per driver in tests/fixtures/strict_locks_baseline.txt and ratcheted by make strict-locks-guard; the flag goes when the rule becomes unconditional.
  • --time — report per-phase wall time (parse / typecheck / emit) on stderr.
  • --canon — dump only: write the id-normalized model.

6. Tree resolution

zc locates its system library and runtime by this precedence, first match wins:

  • an explicit --system / --runtime flag;
  • $ZEROLANG_SYSTEM / $ZEROLANG_RUNTIME;
  • $ZEROLANG_ROOT (a whole tree: $ZEROLANG_ROOT/lib/system and lib/runtime);
  • the executable's own location — os.exePath gives the real binary path (resolving a bin/zc symlink) and the root is its grandparent; <root>/lib/system plus <root>/lib/runtime, falling back to <root>/src/runtime so a dev checkout works too;
  • the current directory (lib/system, src/runtime) — the final fallback.

--src (user code) always defaults to the current directory, never the install tree. The C compiler is chosen as --cc > --target-derived (<triple>-gcc) > $CC > cc.

tcc's runtime payload follows the same chain: --tcc-lib > $ZEROLANG_TCC > $ZEROLANG_ROOT/lib/tcc > <root>/lib/tcc > out/tcc-lib.

7. The vendored tcc

The compiler vendors tinycc (vendor/tinycc) and make install lays it down as bin/tcc beside the three tools, with its runtime payload — libtcc1.a, tcc's own headers — in lib/tcc. --cc tcc finds it: the install symlinks only zc, zl and zls onto PATH, so a plain lookup never would.

tcc cannot locate that payload on its own. The directory is fixed when tcc is configured, so a tree that has moved has to be told, and until it is, tcc cannot resolve even stddef.h. zc passes -B for you whenever the compiler it resolved is a tcc and a payload directory exists; point --tcc-lib at a different one when you are using a tcc of your own.

--cc-mode inproc loads that same tcc into zc rather than running it as a child, through libtcc.so in the payload directory. It applies to tcc and to nothing else, so --cc gcc --cc-mode inproc is an error naming the compiler it resolved, and an unloadable libtcc.so is an error naming the path it tried -- never a silent fall back to spawning. Only the compile happens in-process: the executable is still written to disk and still run as its own process, so exit codes, signals and leaks are what they always were.

tcc compiles the corpus in about a fifth of gcc's time and rejects a handful of programs that use a 128-bit or half-precision type. Where a unit declares what it needs — as system's quadfloat subunit does for __float128 — you get that unit's own message instead of a parse error naming a type you never wrote; tests/tcc-known-failures.txt records which programs are in which state, and make test-tcc holds that set steady.

8. Building and running

build type-checks the unit, emits self-contained C to a temporary file, and invokes the C compiler to produce an executable. Because the runtime is inlined at emit time, the single .c needs no extra include paths. The debug default is -O0 -g; --release is -O2. --save-temps keeps that temporary .c and prints its path.

The link libraries come from the program, not from a fixed list: a unit states what it needs from the host toolchain in a require: block, and the requirement applies only to programs that reach that unit. build and run pass them automatically. emit records them on the second line of the generated C, so a hand-run cc can read them off the file:

head -2 hello.c
/* Generated by zerolang compiler */
/* zlink: */

An empty list means the program needs nothing beyond libc and -lm; /* zlink: quadmath */ means it reaches system's quadfloat subunit and must link -lquadmath.

run builds the same way to a temporary location, then spawns the executable with the parent's stdin / stdout / stderr (a live terminal), forwards the trailing program arguments, and exits with the program's own exit code.

9. Cross-compilation

--target TRIPLE selects a cross compiler: when --cc is not given, the compiler name is <triple>-gcc (for example x86_64-w64-mingw32-gcc). The executable name gains a .exe suffix for *windows* triples.

Caveat: cross-compilation is wiring only. Programs that use POSIX-only runtime natives (os.spawn, io file operations, directory walks) will not link for Windows until those natives gain a Win32 backend — a follow-on. Core, POSIX-free programs cross-build where the cross cc is installed.

10. The version line

zc --version (also -V, also the version command) prints one line: the release number, the commit the binary was built from as SemVer build metadata, that commit's date, and the C compiler that built it.

zc (zerolang) 0.1.0+2ad0b065 (2026-08-07) [gcc 15.2.0]
zc (zerolang) 0.1.0+2ad0b065.dirty (2026-08-07) [gcc 15.2.0]
zc (zerolang) 0.1.0 [gcc 15.2.0]

The .dirty suffix means the tree had uncommitted changes. A build with no git available — a release tarball, an exported tree — carries no build metadata at all and prints the third form; the compiler is always named, since it comes from that compiler's own predefined macros.

zl and zls print the same line under their own names. The date is the commit date, not the build date, so two builds of one commit are identical.

Your own programs can carry the same stamp: os.buildCommit and its companions read it, and --cflags passes the define through. See docs/stdlib_os.pdoc.

zc build myprog --cflags '-DZC_BUILD_COMMIT="a1b2c3d4"'

11. Inspecting the environment

zc env prints the resolved tool paths and settings as KEY=VALUE lines — ZEROLANG_ROOT, ZEROLANG_SYSTEM, ZEROLANG_RUNTIME, ZC_CC, ZC_CC_MODE, ZC_TCC, ZC_TCC_LIB, ZC_TARGET, ZC_VERSION, ZC_COMMIT, ZC_BUILD_DATE, ZC_BUILD_CC, and ZC_EXE. It honours the same flags as a build, so zc env --target x86_64-w64-mingw32 reports the cross compiler that would be used.

Note that ZC_CC and ZC_BUILD_CC answer different questions: ZC_CC is the compiler zc would invoke to build your program, ZC_BUILD_CC the one that built zc. ZC_VERSION is the release number alone; the full build line is what --version prints.

zc env
zc env --target x86_64-w64-mingw32

12. Installation

make install builds the three tools (bin/zc, the zl linter/formatter, and the zls language server) and copies a self-contained, GOROOT-style tree to ROOT (default ~/.local/lib/zerolang), symlinking each into BINDIR (default ~/.local/bin):

make install
make install ROOT=/opt/zerolang BINDIR=/usr/local/bin

The tree contains bin/{zc,zl,zls}, bin/tcc, lib/system, lib/runtime (copied from src/runtime), lib/tcc, docs, and src. Because os.exePath resolves the symlink to the real binary, each installed tool finds its stdlib and runtime from any working directory. (A bare make builds the same three tools without installing.)

13. Exit Codes

  • 0 — Success. For build the executable was produced; for run the program ran (its own exit code is propagated); for emit and dump the output was written.
  • 1 — Compilation failed. One or more errors were found during parsing or type checking. Error messages are written to stderr.
  • 2 — Usage error. Unknown or missing command, invalid unit name, or invalid directory paths.
  • other — for build / run, a non-zero exit from the C compiler or from the program itself is propagated unchanged.

14. Error Format

The compiler uses a rustc-inspired error format designed for readability and tool integration. Each error includes an error code, source location, and the relevant source line with a caret pointing to the error.

14.1. Basic Error Format

error[E0008]: undefined identifier: x
 --> MyFile.z:5:10
     |
   5 |     print x
     |           ^

The first line contains the error code (E0008) and the error message. The second line shows the file path, line number, and column number in the standard File:line:col format used by gcc, clang, and rustc. The source line is displayed with a caret marker pointing to the exact location of the error.

14.2. Notes and Hints

Some errors include additional context as notes (explaining why the error occurred) or hints (suggesting how to fix it):

error[E0200]: a `.borrow` return must borrow from a non-owned parameter --
mark the source `.view` (readonly) or `.borrow` (mutable), e.g.
`t: this.view`, so the returned view has a pinned parent
 --> MyFile.z:3:1
     |
   3 | f: function out String.borrow is { return "hello" }
     | ^
error[E0008]: undefined identifier: pritn
 --> MyFile.z:2:5
     |
   2 |     pritn "hello"
     |     ^^^^^
     = hint: did you mean 'print'?

14.3. Error Code Numbering

Error codes are grouped by category:

  • E0001–E0099: Parser and syntax errors — malformed source code, unexpected tokens, missing delimiters, invalid definitions
  • E0100–E0199: Type resolution errors — type mismatches, undefined types, incompatible assignments
  • E0200–E0299: Ownership errors — invalid take/hold/borrow/view/takex usage, use after ownership transfer, pin violations, reftype aliasing
  • E0300–E0399: Call and argument errors — wrong number of arguments, named argument mismatches, type mismatches in function calls
  • E0400–E0499: Generic and monomorphization errors — missing type arguments, failed type inference, invalid generic constraints
  • E0500–E0599: Emitter errors — a construct the C emitter cannot emit, reported after type checking succeeded
  • E0600–E0699: Compile-time evaluation errors — a value the compiler was asked for at compile time and could not produce: division by a constant zero, a result out of range, a constant defined in terms of itself, or an expression that is not statically evaluable

15. Compiling Emitted C

zc build and zc run invoke the C compiler for you. If you instead emit C, the result is a standalone file that compiles with any C17 compiler — the runtime is inlined, so no extra include paths are needed:

zc emit hello --src examples -o hello.c
gcc -std=c17 -Wno-unused-function -o hello hello.c
./hello

For development, compile emitted C with the sanitizers to catch memory errors:

gcc -std=c17 -fsanitize=address,undefined -Wno-unused-function -o hello hello.c
./hello

16. Examples

Build and run a program:

zc run hello --src examples

Build a release executable at a chosen path:

zc build myapp --src src --release -o build/myapp

Build straight from a file path:

zc build ./examples/hello.z

Emit C and compile it yourself:

zc emit hello --src examples -o hello.c && gcc -std=c17 -o hello hello.c && ./hello

Generate SQL diagnostics:

zc dump hello --src examples | sqlite3 :memory:

Dump the typecheck model of a library:

zc dump mylib --src lib

Explain an error code, and inspect the resolved toolchain:

zc explain E0200
zc env
