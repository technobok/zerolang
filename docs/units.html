1. Units

  • modules are files and packages are directories
    • one file, one module. Cannot spread a module over multiple files, no include
      • but can make a module that exports submodules, so you can control structure and expose it with a single exported var
      • can have a file (with extension) and a directory with the same name but:
        • the file is the one that is loaded from 'outside', ie. the public part
        • the dir is only accessable from the file. It contains private modules so the module can be split up into files but the top level file controls what is exposed to the outside world
        • submodules are searched in the dir first before looking in the global file tree
  • packages (dirs) can only contain modules (files)
  • a name written in a module resolves outward: the module itself, then each module enclosing it up to the file unit, then core. A submodule sees its parents; the restriction is the other way (see privacy below)
  • modules (and packages) 'own' the namespace where they are located
  • modules can shadow vars in other files and dirs (but only within themselves)
    • to find a var definition, look in current module, if not found, go look in the directory tree (first relative, then from the top level module path)
  • a unit's top-level definitions are all public by default. A 'public: unit { ... }' block restricts the unit's public interface to the listed definitions; an unlisted definition is private and unreachable from another unit (E0101). An entry may rename what it exposes -- ':name' exposes 'name' as itself, 'alias: internal' exposes 'internal' under the name 'alias' (see the Visibility section of the language spec).
  • a 'require:' block states what the unit needs from the host toolchain: 'require: unit { library: "quadmath" }'. It is an ordinary inline unit, so it is written and parsed like any other; what is layered over it is a schema. Every entry must be a key the compiler consumes -- today only 'library:', whose value is a plain string literal naming a link library -- and the block must declare at least one requirement, because a key nothing reads would be silently ignored (error E0038). The requirement applies only when the declaring unit is actually reached: a program that never uses the unit does not link its library.
  • modules and packages are never capitalised (to cope with case insensitive filesystems). So they are always public (but see private submodules above)
    • there are other restrictions on module and package names because they must be valid identifiers (up to the extension) eg. can't start with a number
  • modules have no initialisation
    • so they don't need to be imported
    • can't have any special data structures (just static, readonly simple vars and arrays (and dicts, but special simplified dict that are arrays inside and are not O(1) on access ?....)
    • any special state must be provided by an api. Eg. an init function or similar

2. Runtime-backed stdlib units

The core stdlib units (system, core, collections, io, os, cli) are declaration surfaces for the C runtime: their types and is native functions are implemented under src/runtime, while bodied free functions in them are ordinary compiled zerolang (demand-gated). Type methods there cannot carry .z bodies. Details in the compiler doc's "Runtime-backed stdlib units" section.

3. Implementation status

The parser (lib/system/zparser.z -- loadUnit / parse) implements the search path above: core is loaded first, and a referenced name's submodules in a same-named directory are searched before the top-level tree. The type checker's bare-name resolution mirrors the same precedence (current unit first, then the stdlib units) and locks each definition to one canonical type id -- see typechecker.pdoc:Type-name resolution and the canonical-id rule. Real programs (the test corpus and the self-hosted compiler) use flat units with dotted cross-unit references (zast.Node), but the same-named-directory submodule form is typechecked, compiled and run: see tests/fixtures/emitc_corpus/hidden_subunit.z and subunit_depth.z, a subunit with a subunit of its own.

Two visibility rules follow from how each form is reached. An inline unit is an ordinary top-level definition and so is public by default, subject to its unit's public: block. An implementation subunit is private to the unit that owns it: its file is read only because that unit named it, so it is never declared surface, and reaching past a unit into one is an error (E0101). Privacy governs who may reference into a subunit; it says nothing about what the subunit sees. A subunit resolves outward like every other unit: its own definitions, then its parent's, up through the file unit, then core (tests/fixtures/emitc_corpus/subunit_parent_read.z and subunit_grandparent_read.z).
