1. Overview

The declarations themselves live in lib/system/tcc.z, which is the one place they are written. Every definition, field, arm, generic parameter and own-line parameter there carries its own doc comment, and zls surfaces each on hover; the corpus runner ratchets that coverage under make ci. This page is the prose and the worked examples -- read it for how the unit is meant to be used, and the source for the exact surface.

lib/system/tcc.z compiles C in this process, through libtcc. It is what zc --cc-mode inproc uses instead of running a C compiler as a child process, and it is available to any program that wants the same.

It buys the fast compile and nothing else. The result is an executable on disk, never a run in memory, so a program built this way still executes as its own process: its exit code, its signals and its leaks are observed exactly as they would be otherwise, and a program that crashes cannot take its compiler down with it.

Loaded, not linked

libtcc is opened with dlopen at the point of use. tinycc is LGPL-2.1 and this tree is dual MIT/Apache, so dynamic loading is what keeps a binary built here out of the combined-work question; make static-tcc-guard fails the build if a libtcc symbol reaches any binary, rather than leaving the rule to discipline.

The loader is what needs dl, and this unit says so:

  require: unit {
      library: "dl"
  }

A program that never mentions tcc therefore links no dl -- the link line is written from the units a program actually reaches, not from a list of everything the standard library might want.

2. available

Can libtcc be loaded from tccDir and driven from here? Loads and immediately unloads.

For diagnostics, and for a program deciding what to offer. zc does not ask this before building: --cc-mode inproc never falls back, so it has nothing to decide, and asking would make a compile depend on a probe.

3. compileToExe

Compile csrc and link it to the executable exe.

tccDir holds tcc's runtime payload -- libtcc1.a, tcc's own headers, and libtcc.so itself. tcc cannot find it alone: the path is fixed when tcc is configured, so a tcc that has moved cannot resolve even stddef.h until it is told. One directory answers every question, which is why there is one parameter and not three.

cflags is parsed by tcc in the spelling it accepts on the command line. libs are the -l names to link, the same ones the emitted C declares on its own second line; m is added for you.

Return

  • 0 -- the executable was written.
  • 1 -- tcc rejected the program, or the link failed. Diagnostics have already gone to stderr, in the same words the tcc driver would have printed.
  • 127 -- libtcc could not be loaded. This is the code os.spawn already returns for "could not run the compiler", so a caller reports a missing compiler and an unloadable one through one path instead of growing a second.
