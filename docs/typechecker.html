1. Introduction

This document is the architectural map of the zerolang typechecker. It is intended to be read before opening the checker's files -- src/ztypecheck.z and the files of src/ztypecheck/ -- after reading it, a contributor should know which structures the typechecker maintains, how its code is partitioned, and where a particular feature lives.

The compiler overview gives the whole pipeline and the stages around the typechecker. This document is the typechecker's own: the rules it applies while it checks -- demand-driven resolution, ownership and locks, literal coercion, narrowing -- and the structures and code that apply them. Ownership states the ownership rules as a program meets them; this document says how the checker enforces them.

Audience. A new contributor who has already read spec.pdoc, ownership.pdoc, and compiler.pdoc.

2. Pipeline Position

The typechecker sits between the parser and the C emitter:

  zast.ProgramData  (frozen post-parse)
      ↓   typecheck(program)
  ztyping.ZTyping  (mutable, holds all typecheck output)
      ↓
  zemitterc / zsqldump

The parser hands the typechecker a zast.ProgramData -- an immutable tree of Node values, each with a monotonic nodeid. The typechecker does not mutate AST nodes; instead it writes its results into a single mutable container, ztyping.ZTyping, keyed by nodeid. After typecheck() returns, the emitter and SQL dumper read from both the ProgramData (shape) and the ZTyping (types, ownership, locks, monomorphisations) without further analysis.

The emitter takes the AST, the type registry and the ZTyping (emitC program: reg: typing:), never the symbol table, which is the walk's. The checker functions it calls -- the value a body's last line hands back, the declaration that minted a type, a unit's name -- answer from the registry and the ZTyping alone, and its own state, such as the instance being emitted, lives in its Ctx.

Demand-driven, single pass. Resolution starts at main and descends only into names that are actually referenced. Names that are never reached are never typechecked. The same property gives cycle detection for free -- a name that is encountered while it is already on the resolution stack is reported as a circular dependency. See Demand-Driven Resolution.

3. Core Data Structures

The typechecker is built around four core record types, the declaration tree, and one mutable output container. Reading this section first makes the checker's files considerably easier to follow, because nearly every function in them produces, mutates, or consults one of these.

3.1. ZType -- the unified type descriptor

ZType (in src/ztypes.z) is the only type representation in the compiler. There is no separate "kind", "shape", or "schema" object: every type -- record, class, variant, union, protocol, facet, function, unit, numeric, native -- is a ZType with a typetype discriminator (the ztypetype enum) and a set of optional fields.

Key fields:

  • name: the simple name (e.g. Point)
  • typetype: the ztypetype enum (RECORD, CLASS, VARIANT, UNION, PROTOCOL, FACET, FUNCTION, UNIT, numerics, ...)
  • returnTypeId, thisParamNameId: populated for function types
  • generic-state fields: genericOriginId, isTagGenericOrigin, and the specialization trie -- typeChildren keyed by an argument's type id, valueChildren by the value at a numeric parameter level -- with the instance's ordered arguments in genericArgs
  • layout / memory metadata: needsDestructor, isHeapAllocated, isBox (see representation_of_types.pdoc)
  • ownerTid: the type owning this one as a member, or 0. The emitter composes C names from it; nothing else reads it
  • def: the Decl that minted the type, or 0
  • typeId: monotonic id for SQL dumps

A ZType carries identity-data only. Per-member metadata -- parameter ownership annotations, field defaults, the lock-field and function-pointer-slot marks -- lives on the member's own Decl, not on the parent ZType. Member visibility is likewise structural, held by the type's publicNs declaration subtree.

A member's declaration must therefore exist before any metadata write, which is why every synthesis site declares the member and then types it, in that order: declSetMemberType stamps the member's type onto its declaration, and a method's declaration is what claims its own function type, which every later parameter write reaches through.

3.2. ZVariable -- per-binding ownership carrier

ZVariable (src/ztypes.z) is one runtime variable: a row of the registry's variableById, its vid the row index (row 0 is the sentinel). A variable is minted only for named runtime bindings -- function parameters, locals introduced by assignment, with-bindings, for-loop iterators, and synth temps -- and referenced from Decl.varId; type and function definitions carry no variable. newVariable mints the row and returns the vid; the getters and setters on the registry (variableTypeOf, variableOwnershipOf, setVariableBorrowOrigin, ...) are the only access.

  • ztypeId: the variable's resolved type
  • ownership: OWNED or BORROWED (the 2-state model; see Ownership enforcement)
  • isPrivateAccess: carried through .private typedef projections
  • borrowOrigin: the name id of the root of the path this variable borrows from; 0 for an owned variable and for parameters
  • synthOrigin: the rewrite that synthesised the variable (anf for a hoisted call temp; see Synthesis toolkit), unsaid for a written one
  • origin: how the variable came to be -- a parameter, a local binding, or synthesised

Keeping ownership off ZType lets the same type be bound in two scopes with different ownership, which is the common case.

3.3. ZEntry -- an overlay row

ZEntry (src/ztypes.z) is one overlay row of the body walk: a take, a narrowing, or a lock laid over a local while the scope that laid it is open. A local itself is a localDecl in the declaration tree; the row points at it.

  • entryId: monotonic id
  • declId (the local's declaration -- its name, type and variable are read off it), defSeq (the row's place among the scope's locals, for the dump)
  • ztypeId: the type the row presents (a narrowing changes it)
  • hasLock, lockType, lockScope, lockHolder, lockPath: lock state -- the lock kind, whether it is on the leaf or an intent on a prefix, its holder, and the addressable path as name ids (root, f1, f2, ...)
  • narrowedSubtype, excludedSubtypes: type narrowing for union / variant subjects in match arms, as arm name ids
  • originalZtypeId: the un-narrowed type, so the emitter can generate the C-level unwrap
  • isTaken, takenAt: consumed-binding state

Rows live on ZSymbolTable.entries and die with their scope; the local's declaration persists, so the walk can return to it.

3.4. ZTyping -- the typecheck-output container

ZTyping (src/ztyping.z) is the single mutable container holding everything the typechecker computes. It is intentionally ECS-shaped: instead of decorating parsed AST nodes with extra columns, the typechecker writes into a set of per-nodeid component maps.

The declaration tree lives here: decls (every Decl row, id = index, row 0 the sentinel; see src/ztyping.z), declByTypeId, publicNsByOwner, refDecl (reference node -> resolved declaration) and the unit-root anchors (programRoot, coreUnitRoot).

Per-node stamps (each keyed by parsed-node nodeid): nodeType (dense) and nodeConst / memberConst (the compile-time value domain), callKind, atomVariableId, implicitCreate, the dotted-path stamps (dpTaggedParent, dpArmPredicate, dpTagRead), the post-guard and branch-fold stamps (postGuard*, foldedBranch, truthyCondArm), the per-variable facts (variableMutated, variableMoved), and the 2-arm-sum facts (sumPairFirstArm / sumPairSecondArm). The class comment in src/ztyping.z is the authoritative list. The container also carries the error accumulator (errors, isError), the implementation rows, and the singleton types: singletons holds, keyed by its tid, each instance's numeric generic parameter as a type (the instance, the parameter's name and the one value), and singletonAt finds that tid from the instance and the name. ZTyping holds only what is read downstream -- by the emitter, the SQL dump and zls. What the checker records while it walks and reads back itself -- the demand queue (pendingDefs), the pending-borrow slot, the function being walked, an instance's argument bindings (monoParamSubst) -- is a WalkState (src/zenv.z), held by the symbol table as walk.

The SQL dumper (src/zsqldump.z) writes one row per component entry of the tables it projects, so every table has a direct SQL representation.

3.5. ZSymbolTable -- the body walk's state

ZSymbolTable (src/zenv.z) is the body walk's state over the declaration tree. A scope is a scopeDecl under the scope or declaration enclosing it and a local is a localDecl under the scope it is written in, so both persist and can be returned to; the table holds what is transient: the stack of open scopes (open, innermost last, each an openscope with the scope's row, its parent, and where its overlay rows begin), the overlay rows laid over locals (entries, see ZEntry above), the scopes whose remainder proved unreachable, and the rows snapshotted for the dump when a scope closes. Its mode, a walkmode value, is how the walk reads what it meets (a reassignment target, a signature it does not re-bind, a bare name that is not a construction); a walk that changes a mode saves the whole value and puts it back. It owns the type registry and the typing tables outright, so every method reads metadata through this.reg / this.typing. Nothing downstream holds the table: zc hands the emitter its reg and typing.

A local resolves by climbing the open scope chain; a scope's parent that is not a scope -- the function declaration -- ends the climb, so two functions never see each other's locals whatever order their bodies are walked in.

The scope a resolver works in is an explicit scope: argument, never an ambient cursor: a declaration resolves in its parent's scope (declParentIdOf), a body walk opens its base scope under the declaration (push name: parent:), and every resolver it reaches is handed the scope it should resolve from. The table's curScope is the body walk's own position -- the innermost open scope that has a row -- and only pushScope / materialiseTop / pop move it. Key APIs:

  • pushScope / pushBlock / pushCall / pop / popTo -- open and close scopes (a block scope that declares nothing mints no row)
  • defineVar / define / lookup / lookupVarId -- local definition and name -> type / variable resolution
  • tryLock -- attempt to install a lock; returns the installed lock or a conflict description. The multi-granularity rule is in lockAcquireConflict
  • findExclusiveLock, isPathLocked -- access- site enforcement (used by lock-escape checks)
  • narrow, exclude -- install a narrowing or exclusion overlay row in the current scope

The lock conflict logic lives in zenv.z, not in the checker's files. The typechecker only chooses when to install a lock; the rule for whether it conflicts is owned by the scope module.

4. The files of the checker

The checker is one unit, ztypecheck, written in seventeen files: the unit's own file and the sixteen files of the folder src/ztypecheck/. Each file in the folder is an implementation subunit: private to the unit, reading the unit's own definitions by their bare names, and named by the unit's other files as file.name (declare.resolveFunction). Outside the unit only the names of the public: block in src/ztypecheck.z are seen; a name that lives in a subunit is listed there as an alias (name: file.name).

6. Dispatch Mechanism

Per the project convention (CLAUDE.md), the typechecker dispatches on the nodetype discriminator rather than runtime type tests. The pattern appears in two forms:

  • Closed dispatch keyed by #~nodetype"" -- e.g. the definition resolvers. Used where the set of cases is closed and known up front (type-definition resolvers, statement-line kinds).
  • Inline match on node.nodetype -- used inside checkValueArmAt, checkStmtInner, and a few similar high-fan-out helpers where a flat match reads more clearly than a table.

After the discriminator check, cast() narrows the node to the concrete Node arm; see lib/system/zast.z.

7. Demand-Driven Resolution

The type checker is demand-driven: it starts from main and resolves definitions as they are referenced. Types, functions, and definitions that are never reachable from main are never type-checked. This ensures the compiler only processes what is needed, and circular dependencies are detected when a name is encountered that is already on the resolution stack.

There is one environment. Every unit's top-level names are indexed before any resolution (the declaration tree: each unit is a scope whose children are its definitions, each carrying its resolution state -- not yet touched, demanded, being resolved, resolved). A reference resolves by walking the scopes from the inside out: the enclosing namespace, the current unit, then the prelude (core, whose members are re-exports); the first match wins, and a qualified unit.member names its unit directly and walks nothing. The declaration a reference finds is what it demands -- never a bare name -- so a name defined in two units can only ever reach the one the reference could see, and the standard library is resolved by exactly the same rule as any other unit. Demanded declarations are queued in discovery order and resolved from the top level, each one's body scanned for further references only once its own resolution completes.

The rule holds for the unit being compiled exactly as it does for its dependencies, which is why that unit must declare a main at all (E0039): without a root there is nothing to demand from. What a type DECLARES is resolved either way -- its generic parameters, the interfaces it implements, and the namespaces and inline templates that scope it -- because those are properties of the declaration rather than of anything walking a body.

A namespace -- an inline m: unit { }, a hidden subunit, a public: block -- is a scope like a file unit, not a definition resolved whole. Demanding one resolves the namespaces and templates it declares; each other member resolves when a use names it, and its body is walked when it is used. A member of math's bigint subunit that the program never reaches is neither checked nor emitted.

Resolution is outside-in: a type resolves before its fields, its fields before its method signatures, and no method body is walked until that completes. A body walked ahead of its owner would bind this to no type at all, and every check that hangs off the receiver would quietly stop asking.

8. Resolution Stack and Cycle Detection

Resolution is keyed by declaration, not by synthesized dotted-string names. Every definition is one Decl in the tree, found from a reference by walking the scopes outward from the scope the reference was written in, and that Decl carries its own resolution state -- pending (demanded, queued), resolving (grey), defined (its type id is final), walked (its body checked). A reference that reaches a declaration already resolving is a cycle back-edge: a signature reference needs only the DECLARED id, so mutual references between signatures are legal, and a reference that needs the definition complete reports E0023 / E0100. The flow is:

  1. A reference resolves to a Decl (envLookup for a bare name, the qualified walk for unit.member). Defined: return its id.
  2. Not yet defined: mark it pending and queue it (pendingDefs); resolveDemandedDefs drains the queue from the top level, dispatching to the resolve* resolver by nodetype in the declaration's own scope.
  3. A nested resolution that re-enters a resolving declaration takes the declared id (or reports the cycle).
  4. On success the resolver marks the declaration resolved and links its type (declSetType).

The type keyword (in receiver position) resolves to the type at the bottom of the resolving stack, so a method body can refer to its own enclosing type without naming it. this works similarly.

9. Type-name resolution and the canonical-id rule

A bare type name (the i64 in x: i64, the X of an X.implement, a field or parameter type) resolves outward from the scope it is written in: the enclosing namespace or template, the current unit, then the prelude (core, whose members are re-exports of the system units). First match wins, so a type defined in the current unit shadows a same-named stdlib builtin, and there is no list of stdlib unit names anywhere in the resolver. Two functions implement this:

  • envLookup(ty, scope, nameId) -- the scope walk: which declaration nameId denotes for a reference written in scope. resolveAtomType routes a name atom through it, get-or-declaring the ONE canonical id via declareCanonicalType.
  • walkLookupTyperef(ast, ty, reg, unitDecl, base) -- the same walk for a type reference, answering a type id, with the declared id for a declaration still resolving.

Cross-unit references are dotted (zast.Node, io.File), resolved by the named unit; bare names never reach across units except through the prelude. A unit foo.z with a private foo/ directory holds implementation subunits, loaded by the parser when referred to.

The canonical-id rule. A definition resolves once, into one canonical type id keyed by its defn.nodeid (with defined_in_unit recording the owning unit). That id is the type's identity -- not its name. Downstream passes trust the locked id and never re-resolve a type by its name: the C emitter derives a type's C form from the id (via typeRefC / scalarCTypeFor / cTypeForNameTid), never from the name, so a user type that shadows a builtin scalar (i64: record { ... }) emits its struct, while the system i64 reached through the same name keeps the C scalar. Re-resolving by name would collapse the two onto whichever the search-root unit wins -- the bug class the make shadow-guard ratchet prevents from returning.

Mono identity follows the same rule. A generic instance is identified by the specialization trie: each template holds its spec-tree edges in genericChildren, one level per parameter in definition order, keyed by the argument's type id -- or, for an integer-scalar-constrained parameter (str to: 16), by the literal VALUE itself (genericArgIsValue marks such ordinals). Ids cannot collide across same-named types, and the mono NAME (MapRR_String_i64) remains only as the display / C-name stem; a user shadow of a builtin still appends its canonical id to that name (monoValName: optionval_i64_7) so generated wrapper names stay distinct too. That stem's HEAD is the template's own DECLARED name, composed at the mint (getOrMintSpec) from templateId rather than by the caller: a type has one declaration and any number of aliases -- List and ListRef both name collections.ListRef -- so neither the spelling a use site reached it by nor which mint site ran first can decide what it is called.

One lookup, nearest first. The walk outward is the language's one name rule (spec, Names and scope): the nearest scope that declares a name answers for it in every position, whatever the declaration is, and a declaration of the wrong kind is refused as what it is, never skipped. The levels, innermost first:

  • a body's blocks -- its locals and bindings (findLocal), built top to bottom as the walk goes. A definition, a for condition's binding and a with name are bound as their statement begins (zenv.beginLocal), wearing the Decl's grey mark (resolving, the one a declaration wears while it resolves), and completed by defineLocal when the value is done; endLocal binds a failed one typeless. lookup answers none for a grey local, as for a moved one, and a use of one is E0103 (refuseUnreadableLocal, checkLabelValueAt, checkBareCalleeCall). A type position naming a local is refused (refuseLocalAsType, asked by refuseValueTypeArg and refuseLeadingLocalArg).
  • the function -- its parameters, in its signature too (WalkState.sigFnNode while resolveFunction resolves it; refuseParamAsType), and its as generics.
  • the enclosing type -- every member stops a type name (memberStopsTypeName), an alias or a generic parameter answering as the type it is; a bare value or callee in a method body that finds a member function or constant is rewritten to type.name (bodyMemberAsPath), and one that finds a field or arm is refused (refuseBodyFieldRead).
  • the unit, then the prelude, as above.

A :x shorthand is a labelvalue node: its lookup starts outside the declaration it makes, so every leg that would find the declaration itself skips it there.

10. Unit members: three passes, each keyed on the value's ARM

A unit-level definition is dispatched three times, and every one of them matches on the shape of the member's VALUE node. Reading only one of them is how a shape ends up silently registering nothing:

  • indexDeclDef (the Decl tree) -- functiondef -> funcDecl, objectdef -> typeDecl, unitdef -> unitDecl, listblock -> staticListDecl, dottedpath and a non-numeric atomid -> reexportDecl (the alias), everything else -> constDecl.
  • resolveDef (resolution) -- the same definition arms, plus the dotted alias leg; anything else is skipped.
  • resolveConstantDef (post-demand) -- the literal shapes: a numeric atomid, a suffixed literal (1.u32, a dotted path whose parent is the literal), a constant expression. A dotted value whose parent is neither a literal nor a unit, and a parenthesised call, are constructions and are refused here. A suffixed literal is range-checked here by the same checkLiteralFits a body uses: a unit constant that skipped the check emitted a truncated value and only the C compiler's overflow warning noticed.

Two consequences worth knowing before adding a leg. A definition's own unit is NOT resolvable through the typeref walk while this runs, so a same-file type or unit answers only through the Decl tree (declOfUnitDef, declDefTypetype, the Decl's kind) -- the registry says "no". And origin: Point.create x: 0 parses as TWO members, the dotted value Point.create and a separate constant x: 0, so a construction never arrives as a call unless it is parenthesised.

11. The numeric id spaces

Every id the compiler carries is a zero-overhead typedef over its base integer, so one space cannot silently stand in for another: equality is same-space only and a sentinel reads isZero rather than == 0 (notZero for the opposite test).

  • nodeid (u32, zast) -- one node in the single monotonic node space, and the index of its row in Ast.nodes (row 0 is the sentinel placeholder); a synthesized node reads fsnoForNode == 0.
  • nameid (u32, zast) -- an interned identifier's text in the StringPool.
  • tid / declid / vid (u64, ztypes) -- a type, a declaration-tree node, a bound variable.
  • fsno (zvfs) -- a source file.

A typedef stands in for its base as a WHOLE VALUE, never as a COMPONENT: a scalar slot (parameter, field, arm payload) carries the typedef, while containers do not. A (ListVal u32) of child ids and the u64-keyed stamp tables keep their base type, and the id narrows (.u64, .u32) or is minted (zast.nodeid.create from: ...) at that boundary.

Residuals that stay bare by design, because the slot genuinely holds more than one space: genericChildren's key, genericArgs, genericArgAt's return (a tid OR a numeric generic value), zlockholder.id (a vid OR a node id), and the emitter's interpPartNodeId, whose consumers ARE the u64-keyed stamp tables. zvfs carries its own dentryid / providerid pair, out of this scope.

12. Cross-Cutting Concerns

Each subsection below gives a rule the checker applies across the walk and where it lives in the code.

12.1. Ownership enforcement

The ownership status of each expression is one of two states: OWNED (the variable owns the instance and is responsible for its lifetime) or BORROWED (a temporary reference; the variable does not own the instance). The model is enforced at the assignment and call sites:

  • checkAssignment -- definition site. Records the new variable's ownership in a fresh ZVariable, consumes the pending borrow by installing a borrow lock.
  • checkReassignment -- enforces that the LHS variable is currently OWNED and that the RHS provides the appropriate ownership; resets narrowing and re-runs lock escape checks.
  • checkSwap -- symmetric ownership preservation.
  • the argument-site .take -- transfers ownership from the caller's binding into the callee's parameter.

An unmarked parameter does not take its argument: a reftype one borrows it and a valtype one copies it. .take, .borrow and .view are the opt-in annotations. The annotations live on the parameter's own Decl, not on the parameter ZType.

The `:name` shorthand at the argument site. A :name argument parses as a labelvalue node, not an atomid, so walkCallArgsHoist's bare-name leg resolves it explicitly, and from there it is the written-out name: name form: at a .take parameter the shorthand transfers ownership (the source is invalidated; a later use is E0200), and at a lock/borrow parameter it takes the same call-scoped lock through lockCallArg -- EXCLUSIVE unless the parameter is .view -- laid when the call starts, after its arguments, so a readonly binding passed via :name to a mutable-borrow parameter is refused with E0200 exactly as b: b is (tests/fixtures/errors/shorthand_arg_locks.z).

12.2. Lock checking

The typechecker chooses when to install a lock; zenv.z owns the conflict rule (lockAcquireConflict) and the prefix-overlap path test (pathsOverlap).

Lock keys are paths -- tuples of name ids (root, f1, f2, ..., fn). Overlay rows (ZEntry) are keyed by the root local's declaration so the linear scan stays cheap; the full path lives on ZEntry.lockPath and is consulted to apply the prefix-overlap conflict rule. Two lock scopes exist:

  • Call-scoped -- taken on a call's arguments and receiver (lockCallArg, lockCallPath). Each by-reference argument queues its lock while the arguments are evaluated, and the queue is laid, in argument order, when the call starts (layArgLocks): SHARED intent locks on every intermediate prefix of the source path and, on the leaf, EXCLUSIVE when the callee may write through the reference and SHARED when it only reads (a .view parameter); the row records which (mutable). A call nested in an argument has taken and released its own locks by then. The receiver locks the same way at the receiver's strength. When the call returns its scope is popped and its locks are released. For a non-owned parameter the leaf lock transfers to the return value (installed as a borrow-scoped lock in the parent scope).
  • Borrow-scoped -- installed by installBorrowLocks when a binding takes a borrow (.borrow, .view, .stringView, .listView, with, or a .borrow-param transfer): SHARED on each intermediate prefix and on the leaf (EXCLUSIVE when the pin came from a {:this} receiver), in the scope where the borrow variable is defined. It lasts for that scope; released by scope pop or explicit .drop.

Conflict check (multi-granularity): same-path locks dedupe when both SHARED and conflict when either is EXCLUSIVE; a strict ancestor SHARED is intent-shared and permits any lock on descendants; a strict ancestor EXCLUSIVE conflicts with any descendant. Sibling paths (no prefix relation) never conflict. Enforcement for access / mutation sites uses the same prefix-overlap test: any EXCLUSIVE whose path prefix-overlaps the target path is a conflict. Two rules on top of the strengths: inside one call, a second row over the same value conflicts when either row is mutable (two arguments, or an argument and the receiver); and a row whose reference a call handed back (alias false -- it may point inside the value) conflicts with any other holder's mutable row over the same value, in either order.

Key code: tryLock / findExclusiveLock / lockAcquireConflict in src/zenv.z; lockCallArg / installBorrowLocks and the path-tuple builders and access-check helpers in src/ztypecheck/moves.z and src/ztypecheck/valuechecks.z.

The aggregate-lock-escape check runs at storage sites (field writes) and at return sites; it consults isPathLocked on the scope chain to reject a write/return that would let a locked value escape its scope.

Self-overlap during a single call (e.g. f.method bv: f.byteView) is permitted via the call-identity stack and zlockholder tagging: tryLock skips the conflict check when the existing holder matches the current call's identity.

12.3. Borrow correctness for parameters

Deep methods that take a borrow into a return value record the source path on the pending-borrow slot (ZTyping.pendingBorrowPath and its flags); the binding site (checkAssignment or the call-argument check) consumes it with takePendingBorrow and installs the borrow lock against the actual destination scope, and drainPendingBorrow clears it at statement and call boundaries so it cannot leak across statements. The dedicated .take / .borrow / .view / .hold / .drop / .private handling lives in checkDotted.

public: visibility and .private handles are enforced from that same machinery. scanVisibility (run per type in the resolvers) records fields whose declared type is a .private handle on the member declaration (Decl.grantsPrivate); privacy itself is structural -- a member is public exactly when the type's publicNs subtree reaches it. Two gates in checkDotted then apply, both keyed on baseIsPrivateCapable (is the base this / a same-type receiver, a .private-typed variable, or a .private-typed field read): reading a private member from a non-capable base raises E0101, and taking .private of a non-capable base raises E0102. Construction argument labels never reach checkDotted, so naming private fields at construction is unaffected.

12.4. Monomorphisation

Generic types and functions are monomorphised by deep-cloning the original AST subtree, binding the generic parameters to concrete types, and re-running the standard resolvers on the clone.

  • getOrMintSpec -- the one specialization front door. Walks the template's trie level per definition-order parameter (type-id keys, literal-value keys for numeric parameters); a hit returns the existing instance, a miss materializes one via mintMono and links it into the trie with its ordered genericArgs.
  • the instance walk -- a mono's function is walked over its own copy of the template's function (instanceBodyAt): the return type, the parameters and the body, with the instance's arguments bound (monoParamSubst). Every row the walk makes is that instance's own (instanceRows), so what the walk records on a node is the instance's answer and no other's.
  • mintNumericSingletons -- when an instance is minted, each numeric parameter gets its singleton type: a valtype typedef over the bound, owned by the instance, whose one value is the argument. A template written in a generic unit takes the unit instance's singleton types for the parameters it inherits (shareUnitSingletons), so the same parameter of the same instance is one type. A native template mints none.
  • validateGenericTypeArgs -- enforces generic constraints on a candidate argument type.

Node synthesis (the hoist temps, the generator lowering) is described in Synthesis toolkit.

is native methods (the compiler-provided collection methods on array, List, Map, str, etc.) are not special-cased -- they are cloned alongside user methods. The only requirement is that their declaration in lib/system/system.z or lib/system/collections.z carries the is native form. Resolution flows through the standard child-lookup path.

12.5. Type narrowing

Narrowing for union and variant subjects in match arms is implemented via overlay entries. When a match arm narrows subject s to subtype ok, an overlay ZEntry with narrowedSubtype: "ok" is pushed onto the arm's scope. Inside the arm, name lookup for s finds this entry first and returns the narrowed type. The arm scope is popped at end of arm; narrowing resets automatically.

Post-match exclusion is the dual: arms that diverge (return, break, panic) contribute their handled subtypes to an excludedSubtypes entry placed on the parent scope after the match. Subsequent code that re-accesses s as an excluded subtype is rejected.

Assignment-based narrowing (e.g. x: Result.ok 42) places a narrowing entry in the current scope at definition time; reassignment resets it.

Narrowing and exclusion are carried as arm name ids on the overlay row (narrowedSubtype, excludedSubtypes).

12.6. Numeric literal coercion

Bare numeric literals are typed as one of two DECLARED types during typecheck: intliteral or floatliteral, declared is native in lib/system/system.z beside the sixteen scalars and minted as the registry's first two rows, which the declaration then attaches to. Each declares exactly the conversions it can reach -- sixteen for the integer literal, the four float targets for the float one -- so which suffixes a literal accepts is a question for its declaration rather than for the checker. Each also declares its operators, as generic natives bounded by anynumber, anyint or anyfloat, and the integer literal its times, upto and downto. They are compile-time only: create: null says a program cannot construct one, so a binding naming either bare is refused by the same rule any non-constructible type gets, with no literal-specific message. core does re-export the names, so a unit-level alias can refer to one. Constant expressions built from them stay literal-typed too — the binop folder operates at unbounded integer precision when both operands are literal, with no intermediate range check. An intliteral only becomes a concrete numeric when one of the following fires:

  • Typed-location coercion via the literal-coercion helpers in src/ztypecheck/numerics.z. The helper reads nodeConst, applies the rule appropriate to the source/target combination (int→int range check; int→float exact mantissa; float→float round-trip; float→int rejected outright), and on success rewrites nodeType to the target. Wired sites: call arguments (checkCall), function implicit return (checkImplicitReturn), reassignment RHS (checkReassignment), match-arm numeric patterns (checkCase), and if-/match-expression branch unification.
  • Bind-site materialisation via materialiseLiteral. Called from checkAssignment and unit-name resolution so a literal-typed RHS never escapes into long-lived storage (ZVariable.ztypeId, the resolution cache). Also wired into generic-arg inference (inferGenericConstruction, checkBoxConstruction) so the monomorphization key is keyed on the concrete default (e.g. id_i64, not id_intliteral).
  • Default-resolution late pass -- a final walk invoked from the module-level typecheck entry point after resolution returns. Walks ZTyping.nodeType and blindly replaces any remaining literal-typed entry with its concrete default (i64 for intliteral, f64 for floatliteral). No range check fires here — that is the coercion sites' job.

No VALUE of a literal type reaches the emitter: every site that mints a type from a value materialises a literal first, as generic-argument inference does, so a monomorphisation is keyed on i64 / f64 -- a break-carrying do-block's optionval too (wrapDoBreakValue). The late pass is PARTIAL: symbol-table entries keep their literal ids, and nothing reads them afterwards.

A suffix the literal type DECLARES (65.u8) is dispatched through that declaration: the child resolves to the declared method and the target is that method's return type, which is the BARE type and never a resultval -- a literal's fit is settled at compile time, so it either fits or it is an error. The range and exactness checks stay in checkLiteralFits, shared by the in-body and unit-level paths, because a declaration can say which conversions exist but not that 300 does not fit a u8.

Any other member of a literal-typed receiver is looked up on the literal type itself, as any type's member is; one it does not declare is no member (1.nid: type 'intliteral' has no member 'nid'). A literal's operator is a generic native, and its argument binds the parameter by argBindingTid: a literal argument of a native whose bound lists the literal's own type binds the literal itself, so 4 + 5 is computed by the constant folder and an unfolded one is E0600 (refuseUnfoldedLiteral); any other binds its default; a singleton binds its bound. Against a typed operand the receiver then LANDS (landLiteralReceiver): it is checked to fit the type the operator's parameter was bound to, as a literal argument is, its node is stamped with that type, and that type's member of the same name is demanded. The emitter writes a literal type's operator or method as that member -- the operator from the receiver's stamp, a method (times lands in i64, every member of a string literal in StringView) through emitCallByDecl -- so no row of the literal type carries C: its rows in system/nativec.zd are bodyless, there only so each is native declaration names one.

typesCompatible treats literal-vs-concrete-numeric as structurally compatible so multi-arm constructs unify cleanly; the range check happens at the typed-location coercion sites, not in the compat check.

12.7. Synthesis toolkit

The type checker may need to introduce nodes that did not appear in the parsed source -- temporaries introduced by per-call argument hoisting and the generator-lowering rewrites. These nodes are synthesised by the checker where it needs them (there is no separate synthesis module):

  • Fresh temp names -- a monotonic counter, WalkState.nextTempId, yields names of the form _t0, _t1, ... in the order they are requested. The monotonicity matters: tests rely on the numeric suffix to assert source-order evaluation of call arguments.
  • Node construction -- synthesised AST nodes are built with a fresh node id, a defaulted source location, and a synthOrigin stamp.
  • Symbol-table registration -- a synth temp's ZVariable is registered in the current scope so downstream resolution finds it.

A synthesised variable's ZVariable carries a synthOrigin, a zsynthorigin naming the rewrite that introduced it (anf for per-call argument hoisting, discard for a value computed and then discarded; unsaid for a written binding). It is persisted in the SQL dump (src/zsqldump.z) so rewrite provenance survives into post-mortem inspection.

Current consumers:

  • hoistArg in src/ztypecheck/moves.z -- per-call atomic processing rewrites every non-trivial call argument to a synth temp inside a per-call sub-scope. See ownership (Per-Call Atomic Processing) for the model.

12.8. Auto-call coercion

A no-user-arg method dotted path read in value position (v: s.stringView, p1.distance inside a string interpolation) is auto-called to its return type. The coercion lives entirely in checkDotted and is gated by a coerce-to-return flag. checkCall clears the flag when resolving its own callable, so explicit calls (obj.method named: arg) see the function type and dispatch normally instead of constructing the return type. Path resolution itself is context-free: it always returns the FUNCTION type for a method path. Behaviour is identical for is native and user-defined methods.

12.9. Unified call dispatch

A type used in callable position is rewritten through the unified-dispatch route. The bare-name construction call Point x: 1 y: 2 resolves the callee to the Point ZType, then looks up children[create] on that type to get the actual constructor. The mechanics live in the return-call dispatch; meta.create on the parent ZType carries the compiler-generated raw allocator when one is needed. create: null in the type's as block disables bare-name construction (the case for union and variant where subtype selection is required).

A bare type name in a runtime value position (no call at all) is the zero-argument case of the same dispatch. checkAtomid (and the unit-qualified leg of checkDotted) stamps eligible atoms in the implicitCreate side table (nodeid to constructed type id, beside callKind / refDecl); the emitter keys the zero-value emission off that stamp. Eligibility is validated up front -- missingCtorFields must come back empty -- and non-constructible families get targeted E0300 diagnostics instead of a stamp. Two gates keep the rule honest: the atom must name the type (a value alias like true: bool.true resolves to the bool type id but is a value use), and the walk mode suppressBareCtor spans dotted-path base walks so Counter.create value: 99 does not construct its base atom.

The runtime-backed stdlib units (system/core/collections/io/os) implement most of their type methods in the C runtime, but a .z body on one is legal and u8.times is the living example. Bodied free functions are resolved and body-walked like any other unit's, only when the program's demand loop referenced them; a bodied type METHOD is demanded at the granularity of its owner, so it is gated separately (bodiedMemberDeferred) and walked only where the program calls it. See Runtime-backed stdlib units.

13. Error Reporting

Type errors are zast.ErrorData value objects, appended to ZTyping.errors via the addError helper. Errors are never raised as exceptions; the typechecker tries to continue collecting errors past the first failure where the AST permits. Error codes (the err variant in lib/system/zast.z) are grouped:

  • E0001-E0099 -- parser / syntax (raised earlier in the pipeline)
  • E0100-E0199 -- type resolution
  • E0200-E0299 -- ownership
  • E0300-E0399 -- call / argument
  • E0400-E0499 -- generic / monomorphisation

The diagnostic location is taken from the offending AST node's loc / Token. After typecheck() returns, the caller inspects ZTyping.errors to decide whether to proceed to emission.

14. What Lives Elsewhere

  • src/ztyping.z -- the ZTyping container and the Decl tree

15. Reading Order

When opening the typechecker for the first time, read in this order:

  1. src/ztypes.z -- the type definitions in this file are the vocabulary for everything else.
  2. src/ztyping.z -- the ZTyping container makes the component-table architecture concrete.
  3. src/zenv.z -- the scope stack and the lock-conflict rule. The semantics of "what makes two locks conflict" lives here, not in the typechecker.
  4. src/ztypecheck.z -- the public names, the shared types and helpers; then the subunit files, entered by the entry points above. A good first dive is typecheck and resolveDef (resolve.z) → resolveFunction (declare.z) → checkFunctionBody (bodies.z) → checkStatement and checkStmtInner (flow.z) → checkValueAt (ztypecheck.z) → checkCall (memberaccess.z). That path touches almost every cross-cutting concern in turn.
