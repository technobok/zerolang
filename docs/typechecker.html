1. Introduction

This document is the architectural map of the zerolang typechecker. It is intended to be read before opening src/ztypecheck.z -- after reading it, a contributor should know which structures the typechecker maintains, how its code is partitioned, and where a particular feature lives.

The companion document compiler.pdoc covers semantics -- what ownership means, how the multi-granularity lock-conflict rule works, what demand-driven resolution guarantees. This document covers structure: data layout, dispatch, code organisation. The two documents are deliberately split so that semantic rules have a single source of truth (compiler.pdoc / ownership.pdoc) and this one stays a navigation aid that does not rot when rule wording changes.

Audience. A new contributor who has already read spec.pdoc, ownership.pdoc, and the Semantic-Analyser section of compiler.pdoc.

2. Pipeline Position

The typechecker sits between the parser and the C emitter:

  zast.ProgramData  (frozen post-parse)
      ↓   typecheck(program)
  ztyping.ZTyping  (mutable, holds all typecheck output)
      ↓
  zemitterc / zsqldump

The parser hands the typechecker a zast.ProgramData -- an immutable tree of Node values, each with a monotonic nodeid. The typechecker does not mutate AST nodes; instead it writes its results into a single mutable container, ztyping.ZTyping, keyed by nodeid. After typecheck() returns, the emitter and SQL dumper read from both the ProgramData (shape) and the ZTyping (types, ownership, locks, monomorphisations) without further analysis.

Demand-driven, single pass. Resolution starts at main and descends only into names that are actually referenced. Names that are never reached are never typechecked. The same property gives cycle detection for free -- a name that is encountered while it is already on the resolution stack is reported as a circular dependency. See compiler.pdoc:Demand-Driven Resolution for the rationale.

3. Core Data Structures

The typechecker is built around four core record types, the declaration tree, and one mutable output container. Reading this section first makes ztypecheck.z considerably easier to follow, because nearly every function in it produces, mutates, or consults one of these.

3.1. ZType -- the unified type descriptor

ZType (in src/ztypes.z) is the only type representation in the compiler. There is no separate "kind", "shape", or "schema" object: every type -- record, class, variant, union, protocol, facet, function, unit, numeric, native -- is a ZType with a typetype discriminator (the ztypetype enum) and a set of optional fields.

Key fields:

  • name: the simple name (e.g. Point)
  • typetype: the ztypetype enum (RECORD, CLASS, VARIANT, UNION, PROTOCOL, FACET, FUNCTION, UNIT, numerics, ...)
  • returnTypeId, thisParamNameId: populated for function types
  • generic-state fields: genericOriginId, isTagGenericOrigin, and the specialization trie genericChildren (an IdMap keyed by the argument's type id, or by the literal value at a numeric parameter level) with the ordered argument ids in genericArgs / genericArgIsValue
  • layout / memory metadata: needsDestructor, isHeapAllocated, isBox (see representation_of_types.pdoc)
  • ownerTid: the type owning this one as a member, or 0. The emitter composes C names from it; nothing else reads it
  • def: the Decl that minted the type, or 0
  • typeId: monotonic id for SQL dumps

A ZType carries identity-data only. Per-member metadata -- parameter ownership annotations, field defaults, the lock-field and function-pointer-slot marks -- lives on the member's own Decl, not on the parent ZType. Member visibility is likewise structural, held by the type's publicNs declaration subtree.

A member's declaration must therefore exist before any metadata write, which is why every synthesis site declares the member and then types it, in that order: declSetMemberType stamps the member's type onto its declaration, and a method's declaration is what claims its own function type, which every later parameter write reaches through.

3.2. ZVariable -- per-binding ownership carrier

ZVariable (src/ztypes.z) is one runtime variable: a row of the registry's variableById, its vid the row index (row 0 is the sentinel). A variable is minted only for named runtime bindings -- function parameters, locals introduced by assignment, with-bindings, for-loop iterators, and synth temps -- and referenced from Decl.varId; type and function definitions carry no variable. newVariable mints the row and returns the vid; the getters and setters on the registry (variableTypeOf, variableOwnershipOf, setVariableBorrowOrigin, ...) are the only access.

  • ztypeId: the variable's resolved type
  • ownership: OWNED or BORROWED (the 2-state model described in compiler.pdoc:Ownership and Lifetime)
  • isPrivateAccess: carried through .private typedef projections
  • borrowOrigin: the name id of the root of the path this variable borrows from; 0 for an owned variable and for parameters
  • synthOrigin: pass-name string for variables synthesised by a compiler pass (e.g. "anf" for hoisted call temps); none for user-source variables
  • origin: how the variable came to be -- a parameter, a local binding, or synthesised

Keeping ownership off ZType lets the same type be bound in two scopes with different ownership, which is the common case.

3.3. ZEntry -- an overlay row

ZEntry (src/ztypes.z) is one overlay row of the body walk: a take, a narrowing, or a lock laid over a local while the frame that laid it is open. A local itself is a localDecl in the declaration tree; the row points at it.

  • entryId: monotonic id
  • declId (the local's declaration -- its name, type and variable are read off it), defSeq (the row's place among the frame's locals, for the dump)
  • ztypeId: the type the row presents (a narrowing changes it)
  • hasLock, lockType, lockScope, lockHolder, lockPath: lock state -- the lock kind, whether it is on the leaf or an intent on a prefix, its holder, and the addressable path as name ids (root, f1, f2, ...)
  • narrowedSubtype, excludedSubtypes: type narrowing for union / variant subjects in match arms, as arm name ids
  • originalZtypeId: the un-narrowed type, so the emitter can generate the C-level unwrap
  • isTaken, takenAt: consumed-binding state

Rows live on ZSymbolTable.entries and die with their frame; the local's declaration persists, so the walk can return to it.

3.4. ZTyping -- the typecheck-output container

ZTyping (src/ztyping.z) is the single mutable container holding everything the typechecker computes. It is intentionally ECS-shaped: instead of decorating parsed AST nodes with extra columns, the typechecker writes into a set of per-nodeid component maps.

The declaration tree lives here: decls (every Decl row, id = index, row 0 the sentinel; see src/ztyping.z), declByTypeId, publicNsByOwner, refDecl (reference node -> resolved declaration), pendingDefs (the demand queue) and the unit-root anchors (programRoot, coreUnitRoot).

Per-node stamps (each keyed by parsed-node nodeid): nodeType (dense) and nodeConst / memberConst (the compile-time value domain), callKind, atomVariableId, implicitCreate, the dotted-path stamps (dpTaggedParent, dpArmPredicate, dpTagRead), the post-guard and branch-fold stamps (postGuard*, foldedBranch, truthyCondArm), the per-variable facts (variableMutated, variableMoved), the 2-arm-sum facts (sumPairFirstArm / sumPairSecondArm), and the per-instantiation mono stamps (monoNodeType, monoBinopOwner). The class comment in src/ztyping.z is the authoritative list. The container also carries some of the body walk's ambient state (the pending-borrow slot, the suppress flags), the error accumulator (errors, isError), the conformance rows and the build facts (ccPath, ccMode, targetTriple).

The SQL dumper writes one row per component entry of the tables it projects (src/zsqldump.z). The SQL dumper writes one row per component entry, so every table has a direct SQL representation.

3.5. ZSymbolTable -- the body walk's state

ZSymbolTable (src/zenv.z) is the body walk's state over the declaration tree. A frame is a blockDecl under the frame or declaration enclosing it and a local is a localDecl under the frame it is written in, so both persist and can be returned to; the table holds what is transient: the stack of open frames (open, innermost last, each an openframe with the frame's row, its parent, and where its overlay rows begin), the overlay rows laid over locals (entries, see ZEntry above), the frames whose remainder proved unreachable, and the rows snapshotted for the dump when a frame closes. It owns the type registry and the typing tables outright, so every method reads metadata through this.reg / this.typing.

A local resolves by climbing the open frame chain; a frame's parent that is not a frame -- the function declaration -- ends the climb, so two functions never see each other's locals whatever order their bodies are walked in.

The frame a resolver works in is an explicit frame: argument, never an ambient cursor: a declaration resolves in its parent's frame (declParentIdOf), a body walk opens its base frame under the declaration (push name: parent:), and every resolver it reaches is handed the frame it should resolve from. The table's curFrame is the body walk's own position -- the innermost open frame that has a row -- and only pushFrame / materialiseTop / pop move it. Key APIs:

  • pushFrame / pushBlock / pushCall / pop / popTo -- open and close frames (a block frame that declares nothing mints no row)
  • defineVar / define / lookup / lookupVarId -- local definition and name -> type / variable resolution
  • tryLock -- attempt to install a lock; returns the installed lock or a conflict description. The multi-granularity rule is in lockAcquireConflict
  • findExclusiveLock, isPathLocked -- access- site enforcement (used by lock-escape checks)
  • narrow, exclude -- install a narrowing or exclusion overlay row in the current frame

The lock conflict logic lives in zenv.z, not in ztypecheck.z. The typechecker only chooses when to install a lock; the rule for whether it conflicts is owned by the scope module.

5. Dispatch Mechanism

Per the project convention (CLAUDE.md), the typechecker dispatches on the nodetype discriminator rather than runtime type tests. The pattern appears in two forms:

  • Closed dispatch keyed by #~nodetype"" -- e.g. the definition resolvers. Used where the set of cases is closed and known up front (type-definition resolvers, statement-line kinds).
  • Inline match on node.nodetype -- used inside checkExpression, checkValue, and a few similar high-fan-out helpers where a flat match reads more clearly than a table.

After the discriminator check, cast() narrows the node to the concrete Node arm; see lib/system/zast.z.

6. Resolution Stack and Cycle Detection

Resolution is keyed by declaration, not by synthesized dotted-string names. Every definition is one Decl in the tree, found from a reference by walking the frames outward from the frame the reference was written in, and that Decl carries its own resolution state -- pending (demanded, queued), resolving (grey), defined (its type id is final), walked (its body checked). A reference that reaches a declaration already resolving is a cycle back-edge: a signature reference needs only the DECLARED id, so mutual references between signatures are legal, and a reference that needs the definition complete reports E0023 / E0100. The flow is:

  1. A reference resolves to a Decl (envLookup for a bare name, the qualified walk for unit.member). Defined: return its id.
  2. Not yet defined: mark it pending and queue it (pendingDefs); resolveDemandedDefs drains the queue from the top level, dispatching to the resolve* resolver by nodetype in the declaration's own frame.
  3. A nested resolution that re-enters a resolving declaration takes the declared id (or reports the cycle).
  4. On success the resolver marks the declaration defined and links its type (declSetType / ZType.def).

The type keyword (in receiver position) resolves to the type at the bottom of the resolving stack, so a method body can refer to its own enclosing type without naming it. this works similarly.

7. Type-name resolution and the canonical-id rule

A bare type name (the i64 in x: i64, a conformance marker, a field or parameter type) resolves outward from the frame it is written in: the enclosing namespace or template, the current unit, then the prelude (core, whose members are re-exports of the system units). First match wins, so a type defined in the current unit shadows a same-named stdlib builtin, and there is no list of stdlib unit names anywhere in the resolver. Two functions implement this:

  • envLookup(ty, frame, nameId) -- the frame walk: which declaration nameId denotes for a reference written in frame. resolveAtomType routes a name atom through it, get-or-declaring the ONE canonical id via declareCanonicalType.
  • walkLookupTyperef(ast, ty, reg, unitDecl, base) -- the same walk for a type reference, answering a type id, with the declared id for a declaration still resolving.

Cross-unit references are dotted (zast.Node, io.File), resolved by the named unit; bare names never reach across units except through the prelude. A unit foo.z with a private foo/ directory holds implementation subunits, loaded by the parser when referred to.

The canonical-id rule. A definition resolves once, into one canonical type id keyed by its defn.nodeid (with defined_in_unit recording the owning unit). That id is the type's identity -- not its name. Downstream passes trust the locked id and never re-resolve a type by its name: the C emitter derives a type's C form from the id (via typeRefC / scalarCTypeFor / cTypeForNameTid), never from the name, so a user type that shadows a builtin scalar (i64: record { ... }) emits its struct, while the system i64 reached through the same name keeps the C scalar. Re-resolving by name would collapse the two onto whichever the search-root unit wins -- the bug class the make shadow-guard ratchet prevents from returning.

Mono identity follows the same rule. A generic instance is identified by the specialization trie: each template holds its spec-tree edges in genericChildren, one level per parameter in definition order, keyed by the argument's type id -- or, for an integer-scalar-constrained parameter (str to: 16), by the literal VALUE itself (genericArgIsValue marks such ordinals). Ids cannot collide across same-named types, and the mono NAME (Map_String_i64) remains only as the display / C-name stem; a user shadow of a builtin still appends its canonical id to that name (monoValName: optionval_i64_7) so generated wrapper names stay distinct too.

8. Unit members: three passes, each keyed on the value's ARM

A unit-level definition is dispatched three times, and every one of them matches on the shape of the member's VALUE node. Reading only one of them is how a shape ends up silently registering nothing:

  • indexDeclDef (the Decl tree) -- functiondef -> funcDecl, objectdef -> typeDecl, unitdef -> unitDecl, datablock -> dataDecl, dottedpath and a non-numeric atomid -> reexportDecl (the alias), everything else -> constDecl.
  • resolveDef (resolution) -- the same definition arms, plus the dotted alias leg; anything else is skipped.
  • resolveConstantDef (post-demand) -- the literal shapes: a numeric atomid, a suffixed literal (1.u32, a dotted path whose parent is the literal), a constant expression. A dotted value whose parent is neither a literal nor a unit, and a parenthesised call, are constructions and are refused here.

Two consequences worth knowing before adding a leg. A definition's own unit is NOT resolvable through the typeref walk while this runs, so a same-file type or unit answers only through the Decl tree (declOfUnitDef, declDefTypetype, the Decl's kind) -- the registry says "no". And origin: Point.create x: 0 parses as TWO members, the dotted value Point.create and a separate constant x: 0, so a construction never arrives as a call unless it is parenthesised.

9. The numeric id spaces

Every id the compiler carries is a zero-overhead typedef over its base integer, so one space cannot silently stand in for another: equality is same-space only and a sentinel reads isZero rather than == 0.

  • nodeid (u32, zast) -- one node in the single monotonic node space, and the index of its row in Ast.nodes (row 0 is the sentinel placeholder); a synthesized node reads fsnoForNode == 0.
  • nameid (u32, zast) -- an interned identifier's text in the StringPool.
  • tid / declid / vid (u64, ztypes) -- a type, a declaration-tree node, a bound variable.
  • fsno (zvfs) -- a source file.

A typedef stands in for its base as a WHOLE VALUE, never as a COMPONENT: a scalar slot (parameter, field, arm payload) carries the typedef, while containers do not. A (ListVal u32) of child ids and the u64-keyed stamp tables keep their base type, and the id narrows (.u64, .u32) or is minted (zast.nodeid.create from: ...) at that boundary.

Residuals that stay bare by design, because the slot genuinely holds more than one space: genericChildren's key, genericArgs, genericArgAt's return (a tid OR a numeric generic value), zlockholder.id (a vid OR a node id), and the emitter's interpPartNodeId, whose consumers ARE the u64-keyed stamp tables. zvfs carries its own dentryid / providerid pair, out of this scope.

10. Cross-Cutting Concerns

Each subsection below points at where a concern lives in the typechecker. For why it works that way, follow the links to the semantic documents.

10.1. Ownership enforcement

The 2-state ownership model (see compiler.pdoc:Ownership and Lifetime) is enforced at the assignment and call sites:

  • checkAssignment -- definition site. Records the new variable's ownership in a fresh ZVariable, consumes the pending borrow by installing a borrow lock.
  • checkReassignment -- enforces that the LHS variable is currently OWNED and that the RHS provides the appropriate ownership; resets narrowing and re-runs lock escape checks.
  • checkSwap -- symmetric ownership preservation.
  • the argument-site .take -- transfers ownership from the caller's binding into the callee's parameter.

Parameters default to .borrow; .take and .view are the opt-in annotations. The annotations live on the parameter's own Decl, not on the parameter ZType.

The `:name` shorthand at the argument site. A :name argument parses as a labelvalue node, not an atomid, so walkCallArgsHoist's bare-name leg resolves it explicitly. At a .take parameter the shorthand transfers ownership exactly as the written-out name: name form does (the source is invalidated; a later use is E0200). At lock/borrow parameters the shorthand currently takes no call-scoped lock -- the written-out form takes EXCLUSIVE/SHARED via lockCallArg, the shorthand form skips it, so a readonly binding passed via :name to a mutable-borrow parameter is accepted without a diagnostic. Routing the shorthand through lockCallArg is the fix; in the compiler's own tree it surfaces roughly 1,900 E0200s (readonly bindings into mutable-borrow parameters, shared-lock overlaps, aliasing through an enclosing call), each needing a per-callee .view or a mutable caller binding before the shorthand can lock.

10.2. Lock checking

The typechecker chooses when to install a lock; zenv.z owns the conflict rule (lockAcquireConflict) and the prefix-overlap path test (pathsOverlap). Two scopes of locks, both described in compiler.pdoc:Lock Checking:

  • Call-scoped -- installed by lockCallArg inside a CALL scope that wraps argument processing. The leaf is EXCLUSIVE for mutable and owned markers but SHARED for a .view argument (lockCallArg takes shared:); every intermediate prefix is SHARED.
  • Borrow-scoped -- installed by installBorrowLocks when a binding takes a borrow into a BLOCK scope (.borrow, .view, .stringview, with, or a .borrow-param transfer). Persists for the lifetime of the binding's scope; released by scope pop or explicit .release.

The aggregate-lock-escape check runs at storage sites (field writes) and at return sites; it consults isPathLocked on the scope chain to reject a write/return that would let a locked value escape its scope.

Self-overlap during a single call (e.g. f.method bv: f.byteview) is permitted via the call-identity stack and zlockholder tagging: tryLock skips the conflict check when the existing holder matches the current call's identity.

10.3. Borrow correctness for parameters

Deep methods that take a borrow into a return value record the source path on the pending-borrow slot (ZTyping.pendingBorrowPath and its flags); the binding site (checkAssignment or the call-argument check) consumes it with takePendingBorrow and installs the borrow lock against the actual destination frame, and drainPendingBorrow clears it at statement and call boundaries so it cannot leak across statements. The dedicated .take / .borrow / .view / .hold / .release / .private handling lives in checkDotted.

public:/private: visibility is enforced from that same machinery. scanVisibility (run per type in the resolvers) records fields whose declared type is a .private handle on the member declaration (Decl.grantsPrivate); privacy itself is structural -- a member is public exactly when the type's publicNs subtree reaches it. Two gates in checkDotted then apply, both keyed on baseIsPrivateCapable (is the base this / a same-type receiver, a .private-typed variable, or a .private-typed field read): reading a private member from a non-capable base raises E0101, and taking .private of a non-capable base raises E0102. Construction argument labels never reach checkDotted, so naming private fields at construction is unaffected.

10.4. Monomorphisation

Generic types and functions are monomorphised by deep-cloning the original AST subtree, binding the generic parameters to concrete types, and re-running the standard resolvers on the clone.

  • getOrMintSpec -- the one specialization front door. Walks the template's trie level per definition-order parameter (type-id keys, literal-value keys for numeric parameters); a hit returns the existing instance, a miss materializes one via mintMono and links it into the trie with its ordered genericArgs.
  • the instance walk -- a mono's method bodies are re-walked over the TEMPLATE's AST with the instance's arguments bound (monoParamSubst), stamping per-instance types into monoNodeType; nothing is cloned.
  • validateGenericTypeArgs -- enforces generic constraints on a candidate argument type.

Node synthesis (the hoist temps, the generator lowering) is described in compiler.pdoc:Synthesis Toolkit.

is native methods (the compiler-provided collection methods on array, List, Map, str, etc.) are not special-cased -- they are cloned alongside user methods. The only requirement is that their declaration in lib/system/system.z or lib/system/collections.z carries the is native form. Resolution flows through the standard child-lookup path.

10.5. Type narrowing

Narrowing for union and variant subjects in match arms is implemented via overlay entries. When a match arm narrows subject s to subtype ok, an overlay ZEntry with narrowedSubtype: "ok" is pushed onto the arm's scope. Inside the arm, name lookup for s finds this entry first and returns the narrowed type. The arm scope is popped at end of arm; narrowing resets automatically.

Post-match exclusion is the dual: arms that diverge (return, break, panic) contribute their handled subtypes to an excludedSubtypes entry placed on the parent scope after the match. Subsequent code that re-accesses s as an excluded subtype is rejected.

Assignment-based narrowing (e.g. x: Result.ok 42) places a narrowing entry in the current scope at definition time; reassignment resets it.

Narrowing and exclusion are carried as arm name ids on the overlay row (narrowedSubtype, excludedSubtypes).

10.6. Auto-call coercion

A no-user-arg method dotted path read in value position (v: s.stringview, p1.distance inside a string interpolation) is auto-called to its return type. The coercion lives entirely in checkDotted and is gated by a coerce-to-return flag. checkCall clears the flag when resolving its own callable, so explicit calls (obj.method named: arg) see the function type and dispatch normally instead of constructing the return type. Path resolution itself is context-free: it always returns the FUNCTION type for a method path. Behaviour is identical for is native and user-defined methods.

10.7. Unified call dispatch

A type used in callable position is rewritten through the unified-dispatch route. The bare-name construction call Point x: 1 y: 2 resolves the callee to the Point ZType, then looks up children[create] on that type to get the actual constructor. The mechanics live in the return-call dispatch; meta.create on the parent ZType carries the compiler-generated raw allocator when one is needed. create: null in the type's as block disables bare-name construction (the case for union and variant where subtype selection is required).

A bare type name in a runtime value position (no call at all) is the zero-argument case of the same dispatch. checkAtomid (and the unit-qualified leg of checkDotted) stamps eligible atoms in the implicitCreate side table (nodeid to constructed type id, beside callKind / atomUnitDefId); the emitter keys the zero-value emission off that stamp. Eligibility is validated up front -- missingCtorFields must come back empty -- and non-constructible families get targeted E0300 diagnostics instead of a stamp. Two gates keep the rule honest: the atom must name the type (a value alias like true: bool.true resolves to the bool type id but is a value use), and suppressBareCtor spans dotted-path base walks so Counter.create value: 99 does not construct its base atom.

The runtime-backed stdlib units (system/core/collections/io/os/cli) implement their type methods in the C runtime: a type method with a .z body there is E0100, while bodied free functions are legal -- they are resolved and body-walked like any other unit's, only when the program's demand loop referenced them. See the compiler doc's "Runtime-backed stdlib units".

11. Error Reporting

Type errors are zast.ErrorData value objects, appended to ZTyping.errors via the addError helper. Errors are never raised as exceptions; the typechecker tries to continue collecting errors past the first failure where the AST permits. Error codes (the err variant in lib/system/zast.z) are grouped:

  • E0001-E0099 -- parser / syntax (raised earlier in the pipeline)
  • E0100-E0199 -- type resolution
  • E0200-E0299 -- ownership
  • E0300-E0399 -- call / argument
  • E0400-E0499 -- generic / monomorphisation

The diagnostic location is taken from the offending AST node's loc / Token. After typecheck() returns, the caller inspects ZTyping.errors to decide whether to proceed to emission.

12. What Lives Elsewhere

Module boundaries the typechecker relies on:

  • src/ztypes.z -- ZType, ZVariable, ZEntry, ZTypeRegistry, plus the ztypetype / zownership / zparamownership / zlockstate / zlockscope / zcontrolkind / zlockholderkind / zlockholder enums, the numeric-literal parser and the shared mangler mangleVarName
  • src/ztyping.z -- the ZTyping container and the Decl tree
  • src/zenv.z -- ZSymbolTable, the lock-conflict logic (lockAcquireConflict, pathsOverlap), narrowing / exclusion installers

Collection-type predicates (typeIsReftype, typeIsValtype, ...), node synthesis, and the monomorphisation dedup hashing have no separate module -- they live within src/ztypecheck.z itself.

13. Reading Order

When opening the typechecker for the first time, read in this order:

  1. src/ztypes.z -- the type definitions in this file are the vocabulary for everything else.
  2. src/ztyping.z -- the ZTyping container makes the component-table architecture concrete.
  3. src/zenv.z -- the scope stack and the lock-conflict rule. The semantics of "what makes two locks conflict" lives here, not in the typechecker.
  4. src/ztypecheck.z -- enter via the Code Map above. A good first dive is typecheck → resolveDef → resolveFunction → checkFunctionBody → checkStatement → checkExpression → checkCall. That path touches almost every cross- cutting concern in turn.
